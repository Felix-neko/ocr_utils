# Какие проблемы сейчас?

При применении external_ocr_services у меня часто встречается проблема: в финальых md-файлов, представляющих целиковый выпуск, бывает больше заголовков верхнего уровня, чем есть статей в оглавлении.

Иногда эти дублированные заголовки статей верхнего уровня совпадают дословно, иногда немного отличаются.

Возможно, есть и дублирование заголовков рубрик (<rubric>) верхнего уровня.

Такие "паразитные заголовки" в финальных md-файлах выпусков -- очень вредны и опасны, так как мне потом надо будет делать информационный поиск в стиле Long Context Information Retrieval, подавая на вход моей LLM отдельные статьи (чтобы не расплывалось внимание LLM), а подавать половинки или четвертинки статей -- не хочу, т.к. тогда LLM может не понять смысла статьи вообще.

Я понимаю, что чаще всего такие паразитные заголовки идут, когда VLM принимает колонтитул за заголовок.

Также я знаю, что бывают ситуации, когда на странице напечатан заголовок рубрики (см. ![IMG_0016.jpg](../../../../../mnt/dump3/yandex_disk_linux_baby_zergling/%D0%9E%D0%B1%D1%89%D0%B5%D0%B5/%D0%A4%D0%BE%D1%82%D0%BA%D0%B8/%D0%9F%D0%BB%D0%B0%D0%BD%D0%BE%D0%B2%D0%BE%D0%B5%20%D1%85%D0%BE%D0%B7%D1%8F%D0%B9%D1%81%D1%82%D0%B2%D0%BE/%D0%B2%20%D1%80%D0%B0%D0%B1%D0%BE%D1%82%D0%B5/%D0%BF%D0%B0%D0%BA-4%20%28450%20dpi%29/1976/01%20%D0%BE%D0%BF%D0%BB%D0%B0%D1%87%D0%B5%D0%BD%D0%BE/IMG_0016.jpg), правая страница), который похож на реальный колонтитул (см. ![IMG_0017.jpg](../../../../../mnt/dump3/yandex_disk_linux_baby_zergling/%D0%9E%D0%B1%D1%89%D0%B5%D0%B5/%D0%A4%D0%BE%D1%82%D0%BA%D0%B8/%D0%9F%D0%BB%D0%B0%D0%BD%D0%BE%D0%B2%D0%BE%D0%B5%20%D1%85%D0%BE%D0%B7%D1%8F%D0%B9%D1%81%D1%82%D0%B2%D0%BE/%D0%B2%20%D1%80%D0%B0%D0%B1%D0%BE%D1%82%D0%B5/%D0%BF%D0%B0%D0%BA-4%20%28450%20dpi%29/1976/01%20%D0%BE%D0%BF%D0%BB%D0%B0%D1%87%D0%B5%D0%BD%D0%BE/IMG_0017.jpg)) - такое наша VLM легко может перепутать, а ведь этот журнал нам потом тоже придётся обрабатывать.
И там заголовок рубрики может быть попросту "съеден", улетев в колонтитул, а как <rubric> он и не показан.

# <articleheader id="blablabla">Что хочется?</articleheader>`

1) После того, как распознаны страницы оглавления, наш Python-код должен присвоить `article_id` и `rubric_ic` каждой статье и каждой рубрике, которую он нашёл в оглавлении.
2) Когда мы делаем промпт для распознания обычных страниц и подаём туда ранее добытое оглавление со списком статей и рубрик, то хочется:

  - подавать не просто голый список в человекочитаемом виде, а какую-то структуру, где были бы разнесены:
    - для статей: id, title, authors;  
    - для рубрик: id, title.
  
  - когда мы в промпте просим VLM отмечать как <rubric> только то, что есть в списке рубрик -- просить поставить не просто <rubric>замеченное_название_рубрики<rubric>, а <rubric id="id_рубрики_из_переданного_оглавления">замеченное_название_рубрики</rubric>
  - когда мы в промпте просим VLM отмечать как # только то, что есть в списке статей в оглавлении -- то писать не просто `# заголовок_статьи`, но `# <articleheader id=id_статьи_из_оглавления>заголовок_статьи<articleheader>`

  - просить модель: если видит, что колонтитуле написано название статьи из оглавления или название рубрики из оглавления -- то пусть и там пишет <rubric id=...>чего_написано_в_колонтитуле</rubric> или <articleheader id=...>чего написано в колонтитуле</articleheader> (т.е. обёртывает текст колонтитула в тег, по которому можно понять, к какому элементу оглавления это относится).

Возможно, имеет смысл делать id для рубрик в виде каких-то hex-кодов, а для статей в виде другого диапазона hex-кодов, чтобы точно не выглядели как номера, проверь.

Если модель на странице поставила # header без articlehdr id или этот id не совпадает с одним из тех, что был получен в переданном оглавлении -- пробуем повторно до 3 раз. # Итог (20.09.2026)

Сделано в `ocr_utils/external_ocr_services` (промпт v20, `reconcile.py`, `numbering.py`; описание —
README пакета, разделы «Конвенция разметки полосы» и «Сборка выпуска → Сверка с оглавлением»):

- id статей `A1…` и рубрик `R1…` присваивает код при слиянии оглавления (`toc.json`); список в промпте
  идёт с ними.
- id модель возвращает **в полях JSON, не в тегах** (`headings`, `rubrics`, `running_header_article_id`
  / `running_header_rubric_id` и то же для footer): атрибут внутри тега у DeepSeek ненадёжен
  (омоглифы, пробелы), а формат md остаётся прежним. Итог сверки — в sidecar `.pages.json`
  (`articles`, `rubrics` со смещениями) и комментарием `<!-- article A3 -->` / `<!-- rubric R2 -->`
  перед настоящим заголовком и рубрикой.
- Повторов запроса при плохом id нет: при `temperature 0` тот же запрос даёт тот же ответ (и кэш
  вернёт его с диска); `#` без id или с чужим id получает id по названию, доля таких — в логе прогона
  (порог 30 %). Пробник 44 полос × 2: id от модели у 26 из 26 `#`, чужих 0.
- `suggested_page_number` — по смещению «номер − индекс» у ближайших нумерованных соседей с обеих
  сторон; на 1291 полосе 98,8 %; опечатки модели в напечатанном номере помечаются `suspect`.
- Сверка на сборке: настоящий `#` — на странице статьи по оглавлению (иначе ближайший, иначе первый);
  фантом непечатный (колонтитул, верх продолжения) удаляется, печатный (лозунг под фото) → `##`;
  статья без `#` восстанавливается из колонтитула с её id; рубрики — так же, лишние → удалить или
  `<marker>`, «съеденная» колонтитулом — вставляется перед `#` первой статьи раздела. Главное
  наблюдение: фантомы модель ставила с верным названием из списка (id их не отсеивает — отсеивает
  номер страницы); v20 вдобавок убрал сами фантомы на пробнике: статья/рубрика из колонтитула теперь
  уходит в поля id, а не в `#`.
