# Детектор крупного line art: прогон по паку-1

Отчёт о прогоне `ocr_utils.line_art_detection` по бинаризованным PDF пака-1
(`/mnt/system/raw/mts/pack1_pdf/full_pdfs_binary_brightened_bg`), 8 сентября 2026 г.

## Зачем это делалось

FineReader с включённым «исправлением искажений строк» иногда корёжит на странице line
art — эталон дефекта — стр. 80 файла `/mnt/system/raw/full_1967_01_bg_off_ori_off.pdf`:
схема организации диспетчерской службы вышла с чёрными гребёнками вместо рамок и
надписей. Такие страницы при сборке финального PDF надо брать из бинаризации, сделанной
БЕЗ распрямления строк. Детектор нужен, чтобы просмотреть глазами не все девять тысяч
полос, а только те, где крупный штрих есть.

## ВАЖНО: папка была недописана

Прогон пришёлся на идущую выгрузку FineReader из виртуалки. Число PDF в папке за час
менялось **93 → 89 → 90**, число страниц в отчёте — **9170 → 8774**. По самому отчёту это
неотличимо от правки порогов, и на это ушёл один лишний цикл отладки.

Поэтому `scan` теперь пропускает файлы моложе `--min-age-minutes` (10) и говорит о каждом
в stderr. **Числа ниже сняты по 89 выпускам из 93** и подлежат пересчёту, когда выгрузка
закончится:

```bash
find "$INPUT_DIR" -name '*.pdf' -mmin -30 | wc -l   # должно быть 0
bash run_scripts/line_art_detection/run_line_art_pack1.sh
```

## Чего детектор не находит без Surya

Многострочные формулы. Замер по эталонному выпуску: формула занимает **0.4–1.3%** полосы
(стр. 23, 25, 85, 87), то есть порогом, настроенным на рисунки, её не достать никогда.
Связная статистика её тоже не видит: длинных штрихов в формуле нет. Их даёт только
`--use-surya-layout` (класс `Equation`), и выбираются они не порогом, а источником:

```bash
uv run python -m ocr_utils.line_art_detection export \
    --csv line_art_pack1.csv --out-dir line_art_pack1_formulas \
    --min-coverage 0.003 --source surya:Equation
```

Прогон Surya по эталонному выпуску дал 10 блоков `Table`, 7 `Equation`, 1 `Figure`; чистая
прибавка к пиксельному детектору — четыре страницы с формулами. Цена — около 0.7 с на
страницу GPU (порядка двух часов на пак против двух с половиной минут CPU), поэтому
разметка кэшируется на диск.

## Стоимость

0.25 с на страницу в один поток при полных 600 dpi. Весь пак на `--jobs 16` — около
семи минут вместе с чтением с NVMe.

## Как устроен детектор и почему именно так

Подробный разбор с замерами — `ocr_utils/line_art_detection/features.py` (докстринг
модуля) и `reports/line_art_detection_state_of_the_art.md`. Коротко, четыре правила:

1. **Площадь и короткая сторона** — текст распадается на пятна размером с букву.
2. **Вытянутость рамки** — рисунок двумерен, типографская линейка нет. Настоящие находки
   1.1..10.4, линейки и отточия 32..167.
3. **Плотность** — чёрная кайма скана переживает эрозию диском в два штриха (0.64..0.86),
   рисунок исчезает (0.000..0.037). Приём Leptonica, применённый к отдельному пятну.
4. **Различные внутренние линейки** — таблица это сетка, а не рамка вокруг набора: у
   декоративной рамки внутренняя вертикаль одна, у таблицы их две и больше.

Полутоновые фотографии отсеиваются ручной разметкой из базы `scan_markup`, а не пикселями:
признаки из литературы (размер дыр, доля длинных прогонов) на этом материале НЕ разделяют,
и включённое отсечение по дырам стоило нам ровно стр. 80 эталона (покрытие падало с 0.43
до 0.045). Проверка разметки: на 1973/09 стр. 2 полосная фотография рассыпается на **131**
кандидата, и прямоугольник из базы накрывает её точно.
