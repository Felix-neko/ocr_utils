# Многопроцессовый режим `scan_cropping`: анализ и план

Отчёт по задаче «запускать обработку в пуле процессов, GPU — в отдельном процессе
с последовательным доступом». Все числа ниже — замеры на этой машине, а не оценки.

**Стенд:** RTX 5060 Ti 16 ГБ, 16 ядер, 135 ГБ RAM. Кадры 3733×4456×3 = **50 МБ**
(партия МТС «в работе», 3 кадра). Профиль запуска — как в `run_detect_and_crop_mts_1.sh`
(`pixel-exact`, `--protect-text-layout`, `copy-back-layout-zones`, `--bg-fill-method=nearest`).

---

## 1. Выводы коротко

1. **Пайплайн CPU-bound: 73% времени вне GPU.** Замер: 13.3 с/кадр всего, из них
   3.6 с внутри методов `GpuModels`. Значит параллелить есть что, и выбранная вами
   схема (один GPU-процесс + пул CPU-воркеров) — правильной формы.
2. **Потолок ускорения — 3.7×**, потому что GPU-вызовы сериализованы и стоят
   3.6 с/кадр. Больше **4 воркеров ставить бессмысленно** — GPU станет узким местом
   уже на четвёртом. Не 4-6, а именно 3-4.
3. **Наивный RPC съест половину выигрыша.** Через границу `GpuModels` ходит
   **368 МБ на кадр**. Через `mp.Queue` (pickle) это +1.4 с/кадр *на самом дефицитном
   ресурсе* — потолок падает с 3.7× до 2.7×.
4. **Поэтому шаг 0 — сузить интерфейс `GpuModels`, а не выбирать транспорт.**
   368 МБ можно ужать до ~87 МБ **без единого изменения в результатах** (см. §4).
   После этого даже обычный pickle терпим, а с shared memory накладные ~80 мс/кадр.
5. **«По экземпляру GpuModels на воркер» не подходит** — проверено: один экземпляр
   под нагрузкой занимает 6.2 ГБ VRAM. В 16 ГБ влезает два, а не четыре. Ваша
   идея с одним GPU-процессом подтверждается замером.
6. **Из готовых средств для этой задачи по делу подходит ровно одно — Ray**
   (актор = процесс с последовательными вызовами + zero-copy numpy через Plasma).
   Всё остальное (gRPC, ZeroMQ, Celery, FastAPI) сетевое и заставит гонять
   мегабайты через сокеты. Но для одной машины и 4 воркеров я бы **написал свой
   мини-RPC на stdlib** — это ~200 строк, см. §6.
7. **Отдельно:** в CPU-части лежит 20% времени кадра, убираемых одной строчкой.
   `trim_cover_fragments` — 2.7 с, эквивалент через `distanceTransform` — **13 мс**
   (замер в §11). Стоит посмотреть до того, как усложнять архитектуру.

### 2.2 VRAM: сколько стоит один `GpuModels`

| | МБ |
|---|---:|
| Пустой CUDA-контекст процесса | 1428 |
| + веса моделей (YOLO-World ×2, SAM, LaMa, Surya) | 3200 (+1773) |

Пик задаётся не весами, а активациями (LaMa на большом ROI, SAM на полном кадре).
Плюс каждый CUDA-контекст сам по себе стоит 1.4 ГБ: четыре процесса с моделями —
это 5.6 ГБ одних контекстов. **Вывод: GPU-процесс должен быть один.**

### 2.3 Цена IPC (кадр 50 МБ, туда-обратно)

| Транспорт | мс | пропускная | на 368 МБ/кадр |
|---|---:|---:|---:|
| `mp.Queue` (pickle) | 383 | 0.3 ГБ/с | **~1410 мс/кадр** |
| `shared_memory` (запись + чтение) | 47 | 1.1 ГБ/с | **~350 мс/кадр** |

Выигрыш shared memory — **8×**. Но важнее другое: 1.4 с сериализации ложатся
**на GPU-процесс**, то есть на единственный сериализованный ресурс. Это прямой
вычет из потолка производительности.

### 2.4 Сколько нужно воркеров

Цикл одного воркера = 9.7 с CPU + 3.6 с ожидания GPU = 13.3 с.
GPU насыщается, когда `W / 13.3 = 1 / 3.6`, то есть при **W ≈ 3.7**.

| Воркеров | Ожидаемая пропускная | Ускорение |
|---:|---:|---:|
| 1 | 13.3 с/кадр | 1.0× |
| 2 | 6.7 с/кадр | 2.0× |
| 3 | 4.4 с/кадр | 3.0× |
| **4** | **3.7 с/кадр (GPU насыщен)** | **3.6×** |
| 6 | 3.6 с/кадр | 3.7× (лишние 2 процесса простаивают в очереди) |

Про oversubscription можно не волноваться: замер показал, что главный CPU-пожиратель
`cv2.erode` с ядром 201×201 **вообще не параллелится** (1658 мс на 16 потоках против
1596 мс на одном). Основная CPU-работа однопоточная — это и делает multiprocessing
осмысленным. Тем не менее `cv2.setNumThreads(2)` в воркере поставить стоит: часть
операций (resize, GaussianBlur) потоки использует, и 4 воркера × 16 потоков дадут
переподписку на 16 ядрах.

## 3. Целевая архитектура

```
                        ┌──────────────────────────────────────┐
   главный процесс      │ collect_images + фильтр skip-if-exists│
                        │ → список Task(in, out, dbg)           │
                        └───────────────┬──────────────────────┘
                                        │ task_queue
              ┌─────────────┬───────────┴───────────┬─────────────┐
              ▼             ▼                       ▼             ▼
         ┌─────────┐  ┌─────────┐             ┌─────────┐   ┌─────────┐
         │worker 1 │  │worker 2 │     …       │worker 3 │   │worker 4 │
         │ CPU-этапы│  │         │             │         │   │         │
         └────┬────┘  └────┬────┘             └────┬────┘   └────┬────┘
              │  req_queue (мелкие сообщения) │              │
              └────────────┴──────────┬───────┴──────────────┘
                                      ▼
                        ┌──────────────────────────────┐
                        │   GPU-процесс (единственный) │
                        │   GpuModels, цикл по одному  │  ← сериализация «бесплатно»
                        │   запросу за раз             │
                        └──────────────┬───────────────┘
                                       │ resp_queue[worker_id]
              ┌────────────────────────┴──────────────────────┐
              │  большие массивы — не в очередях, а в          │
              │  shared_memory (в сообщении только имя+shape)  │
              └───────────────────────────────────────────────┘

              логи и тайминги → отдельная log_queue → QueueListener в главном
```

Ключевое: **последовательность GPU-вызовов обеспечивается самой конструкцией** —
GPU-процесс это один цикл `while True: req = req_queue.get(); ...`. Никаких
блокировок и семафоров не нужно, и невозможно случайно их забыть.

## 4. Шаг 0 (обязательный): сузить интерфейс `GpuModels`

368 МБ/кадр — это не свойство задачи, а следствие того, что сейчас в методы
передаются полные кадры. Три правки убирают ~280 МБ **без изменения результатов**:

### 4.1 `inpaint`: передавать ROI, а не кадр (−106 МБ)

Сейчас `removal.remove_fingers` отдаёт в `models.inpaint` целый кадр 50 МБ +
маску 16.6 МБ и получает обратно кадр 50 МБ. Но `GpuModels.inpaint`
(`gpu_models.py`) **сам режет ROI** через `mask_components` / `roi_bounds` и гоняет
LaMa только по ним.

Вынесите нарезку ROI на сторону воркера: пусть через границу летят только
вырезанные ROI (обычно единицы мегабайт), а вклейку `blend_roi` делает воркер.
`inpaint_roi.py` уже чисто CPU-шный и для этого готов — метод класса сократится до
«дай ROI → верни заполненный ROI».

**Результат бит-в-бит тот же**: те же ROI, тот же `_lama_fill_roi`, та же вклейка.

### 4.2 `segment_boxes`: паковать битовые маски (−103 МБ)

Метод возвращает `bool (N, H, W)` — по байту на пиксель. Для пальцев это
N × 16.6 МБ, отсюда и 117 МБ в таблице. `np.packbits` даёт **ровно то же самое**
в 8 раз компактнее; распаковка на стороне воркера — единицы миллисекунд.

Ещё дешевле: возвращать не маски, а сразу их объединение (`mask[m_bin] = 255`
всё равно делается у вызывающего) — но тогда пороги по площади должны переехать
внутрь класса, а это уже размывает границу «класс только гоняет сети». Паковки
битов достаточно.

### 4.3 Кадр в общую память один раз (−50 МБ)

`detect_hand_boxes(bgr)` и `segment_boxes(bgr, boxes)` получают **один и тот же**
полноразмерный кадр (см. `masking.neural_hand_mask`). Если кадр лежит в
shared-memory слабе, оба вызова ссылаются на один слаб — 50 МБ вместо 112 МБ,
и без единого копирования.

### Итого

| | сейчас | после |
|---|---:|---:|
| Трафик через границу | 368 МБ/кадр | **~87 МБ/кадр** |
| Накладные при pickle | ~1410 мс | ~330 мс |
| Накладные при shared memory | ~350 мс | **~80 мс** |

**Чего делать НЕ надо** (соблазнительно, но меняет результат): уменьшать кадр перед
`detect_hand_boxes`/`segment_boxes`. Да, YOLO и SAM внутри всё равно ресайзят вход,
но ресайзят **своим** способом, и подсовывание им заранее уменьшенной картинки даёт
другие боксы и другие силуэты. Если захотите — только через побайтовое сравнение
с эталоном (харнес из прошлой задачи: прогон на 5 кадрах + `diff -r --brief`).

## 5. Обзор средств

| Средство | Сериализация вызовов | Zero-copy numpy | Вес | Вердикт |
|---|---|---|---|---|
| **Ray (actors)** | ✅ по умолчанию (`max_concurrency=1`) | ✅ Plasma / shared memory | тяжёлый (~200 МБ + свои демоны) | **Единственный готовый вариант по делу** |
| **stdlib `multiprocessing` + `shared_memory`** | ✅ по конструкции (один цикл) | ✅ вручную | нулевой | **Рекомендую** |
| `multiprocessing` + `mp.Queue` без shm | ✅ | ❌ pickle 0.3 ГБ/с | нулевой | Годится только после §4 |
| `concurrent.futures.ProcessPoolExecutor` | — (нет понятия «актор») | ❌ | нулевой | Для пула воркеров — да; для GPU-сервиса — нет |
| **gRPC / ZeroMQ / FastAPI** | вручную | ❌ через сокет | средний | Мимо: сетевой транспорт для данных, лежащих в одной RAM |
| **Celery / RQ / RabbitMQ** | вручную | ❌ | тяжёлый | Мимо: это про распределённые очереди задач, не про горячий путь на 368 МБ/кадр |
| `torch.multiprocessing` + CUDA IPC | вручную | ✅ но для CUDA-тензоров | средний | Мимо: данные рождаются на CPU из `cv2.imread`, а не на GPU |
| `dask.distributed` | вручную | частично | тяжёлый | Мимо: заточен под массивы/датафреймы, не под RPC к одному ресурсу |

### Почему Ray, если брать готовое

```python
@ray.remote(num_gpus=1)
class GpuActor:
    def __init__(self, **kw):
        self.m = GpuModels(**kw)
    def inpaint_roi(self, roi, mroi):
        return self.m._lama_fill_roi(roi, mroi)
```

Актор Ray — это отдельный процесс с одним экземпляром класса, и его методы
**по умолчанию исполняются строго по одному** (`max_concurrency=1`). То есть ваше
требование «не перегрузить GPU» выполняется без единой строчки синхронизации.
Плюс `ray.put(frame)` кладёт массив в разделяемый object store, и актор читает его
**без копирования**. Плюс `ray.util.ActorPool` и готовая маршрутизация логов
воркеров с префиксами.

Минусы честно: +200 МБ зависимостей, свои процессы-демоны (raylet, GCS), своя
модель ошибок и свой формат логов, который придётся приручать под ваше требование
«не мешать в консоли». Для одной машины, одной GPU и четырёх воркеров это довольно
много инфраструктуры ради `while True: get(); dispatch(); put()`.

### Почему я бы всё-таки написал своё

- Интерфейс — **6 методов**, все с numpy на входе-выходе. Диспетчер по имени метода
  — это 30 строк.
- Полный контроль над жизненным циклом shm (а это главный источник багов, см. §10).
- Ноль новых зависимостей в проекте, где уже стоят torch, ultralytics, surya и docling.
- Гарантия последовательности — не «настройка фреймворка», а свойство кода, которое
  видно глазами.

Оценка: **~200-250 строк** инфраструктуры + правки в вызывающих модулях.

## 6. Рекомендуемая реализация

### 6.1 Новые модули

```
ocr_utils/scan_cropping/
├── mp/
│   ├── __init__.py
│   ├── shm_pool.py      # пул преаллоцированных слабов shared_memory
│   ├── gpu_service.py   # цикл GPU-процесса + прокси GpuModelsProxy
│   ├── worker.py        # тело воркера: получает Task, зовёт process_frame
│   └── logging_mp.py    # QueueHandler/QueueListener + сбор таймингов
└── pipeline.py          # process_frame принимает models — прокси или сам GpuModels
```

Ключ к простоте: **`process_frame` не меняется**. Он уже принимает `models` как
аргумент и зовёт только методы. Прокси реализует тот же набор методов — значит
однопоточный и многопроцессовый режимы гоняют один и тот же код обработки.
Это же даёт бесплатную проверку эквивалентности: два режима обязаны давать
побайтово одинаковый выход.

### 6.2 Протокол

Через `req_queue` летят только маленькие кортежи:

```python
Request  = (worker_id, req_id, method_name, args_spec)
Response = (req_id, result_spec, gpu_ms)
```

где `args_spec` / `result_spec` — обычные Python-объекты, в которых большие массивы
заменены дескриптором `ShmRef(slab_id, shape, dtype)`. Упаковка/распаковка — две
рекурсивные функции по 20 строк.

### 6.3 Пул слабов вместо создания shm на каждый вызов

`SharedMemory(create=True)` — это `shm_open` + `ftruncate` + `mmap`, десятки
миллисекунд на 50 МБ, плюс мусор в `/dev/shm` при падении. Вместо этого —
фиксированный пул, созданный один раз на старте:

```
N_воркеров × 3 слаба × 64 МБ ≈ 768 МБ в /dev/shm при 4 воркерах
```

RAM 135 ГБ, так что можно не мелочиться. Воркер берёт слаб из своего личного набора
(тогда не нужен межпроцессный аллокатор), пишет туда кадр, посылает `ShmRef`,
дожидается ответа, освобождает. Слабы своего воркера — ресурс однопоточный по
построению, гонок нет.

### 6.4 Ответы: своя очередь на воркера

Один общий `resp_queue` заставил бы воркеров разбирать чужие ответы. Проще:
`resp_queues[worker_id]`, GPU-процесс кладёт ответ строго в очередь заказчика.
`req_id` тогда нужен только для сверки (и для отлова рассинхрона).

### 6.5 Задания и `--skip-if-exists`

Сейчас проверка `out_path.exists()` живёт **внутри** `process_frame`
(`pipeline.py`). Для многопроцессового режима её надо поднять в построение списка
заданий, как вы и написали в пункте 1: иначе воркеры будут разбирать из очереди
задания-пустышки, а прогресс-бар покажет неверный масштаб.

Заодно это чинит и однопоточный режим: сейчас `tqdm` считает пропущенные файлы
как обработанные.

```python
@dataclass(frozen=True)
class Task:
    src: Path
    dst: Path
    debug: Optional[Path]
```

Задания сериализуются тривиально (три пути), очередь — обычная `mp.Queue`.

### 6.6 Порядок запуска и остановки

1. Главный: строит список заданий. Если пуст — выходит, не трогая GPU.
2. Главный: поднимает GPU-процесс, **ждёт сигнала готовности** (модели грузятся
   12.4 с — воркеры не должны в это время долбиться в очередь).
3. Главный: поднимает N воркеров.
4. Главный: раскладывает задания + N sentinel'ов (`None`) в `task_queue`.
5. Воркеры завершаются по sentinel; главный делает `join`.
6. Главный: шлёт sentinel в GPU-процесс, `join`, чистит слабы.

Обязательно `mp.set_start_method("spawn")`. С `fork` CUDA-контекст, уже
инициализированный в родителе, наследуется в сломанном виде — классические
`CUDA error: initialization error`. Со `spawn` воркеры стартуют чистыми, а
CUDA живёт только в GPU-процессе.

## 7. Как гарантируется последовательность GPU

Три уровня, и первого достаточно:

1. **Конструкция.** GPU-процесс — один цикл, обрабатывающий по одному запросу.
   Параллелизма нет физически.
2. **Никаких потоков внутри GPU-процесса.** Не поддавайтесь соблазну обрабатывать
   запросы в пуле потоков ради «перекрытия H2D-копирования» — это ровно то, что вы
   просили не делать, и на 6 ГБ пика оно упрётся в VRAM.
3. Если однажды понадобится **пакетирование** (батчить N кадров в один прогон YOLO
   ради скорости) — это надстройка над тем же циклом: копить запросы до таймаута,
   считать батчем, разослать ответы. Архитектура к этому готова, но сначала
   померьте: `detect_hand_boxes` — 361 мс, батч даст выигрыш, а `inpaint` (1719 мс,
   разные размеры ROI) — вряд ли.

## 8. Логи и тайминги

Ваше требование распадается на два разных, и решать их надо по-разному.

### 8.1 Логи: `QueueHandler` + `QueueListener` (stdlib)

Это штатное решение из `logging.handlers`, придуманное ровно под multiprocessing.

- В каждом воркере и в GPU-процессе корневой логгер получает **единственный**
  handler — `QueueHandler(log_queue)`.
- В главном процессе крутится `QueueListener`, который вынимает `LogRecord` и
  отдаёт настоящим handler'ам.
- `LogRecord` — атомарный объект, поэтому **строки физически не могут
  перемешаться посередине**, в отличие от прямой записи в общий stderr.
- Фильтр добавляет в запись поле `worker` (номер воркера / `"gpu"`).

Раскладка по назначениям:

| Куда | Что | Зачем |
|---|---|---|
| Консоль | только `WARNING+` и одна строка на завершённый кадр, через `tqdm.write` | прогресс-бар не рвётся, хаоса нет |
| `logs/worker-N.log` | весь `INFO` этого воркера | `tail -f logs/worker-2.log` — «оперативно посмотреть» |
| `logs/gpu.log` | всё из GPU-процесса | видно очередь и время каждого вызова |

Роутинг по файлам — маленький кастомный handler, выбирающий `FileHandler` по
`record.worker`.

### 8.2 Тайминги: не логами, а структурой

Для вопроса «какие операции теперь сколько занимают» логи — плохой инструмент:
их надо глазами собирать по 4 файлам. Гораздо лучше **вернуть тайминги как данные**.

Сейчас `log_timing` (`timing.py`) пишет строку в лог и держит глобальный стек
`_STACK`. В многопроцессовом режиме стек у каждого процесса свой — это как раз
корректно, но есть нюанс: **цепочка вложенности разорвётся на границе процессов**.
Замер `remove_fingers -> lama_inpaint` в воркере больше не будет включать в себя
детализацию GPU-стороны.

Предлагаю:

1. Добавить `log_timing` необязательный `sink: dict` — помимо лога, класть
   `sink[path] += dt_ms`. Дефолтное поведение не меняется.
2. `process_frame` заводит такой словарь на кадр и возвращает его вместе со
   статусом. Воркер отдаёт это в `result_queue`.
3. GPU-процесс возвращает своё время в `Response.gpu_ms`, прокси приплюсовывает его
   в тот же словарь под именем метода — так GPU-время снова оказывается внутри
   нужной ветки дерева.
4. Главный процесс пишет по строке JSONL на кадр в `logs/timings.jsonl` и в конце
   печатает сводку:

```
операция                     кадров   среднее    медиана    доля
trim_cover_fragments            620      2675 мс   2610 мс   20.1%
[gpu] inpaint                   620      1719 мс   1680 мс   12.9%
compensate_levels               620      1417 мс   1390 мс   10.6%
...
ожидание очереди GPU            620       840 мс    120 мс    6.3%
```

Строка «ожидание очереди GPU» (время между отправкой запроса и получением ответа
минус `gpu_ms`) — главный диагностический показатель всей затеи. Если она большая,
воркеров слишком много; если около нуля — GPU простаивает и воркеров можно добавить.

## 10. Подводные камни

- **`spawn`, а не `fork`.** Иначе CUDA сломается. Побочный эффект: воркеры заново
  импортируют `torch`/`ultralytics` (секунды на старте) — стартовать их надо один
  раз на прогон, а не на задание.
- **Утечки `/dev/shm`.** При `SIGKILL` процесса `resource_tracker` может не убрать
  сегменты. Лечится: фиксированные имена слабов (`ocr_shm_w0_s1`), попытка
  `unlink` существующих на старте, `atexit`+`finally` на выходе. Проверять
  `ls /dev/shm`.
- **Пик VRAM 6.2 ГБ.** Он от активаций и зависит от размера ROI. Если однажды
  добавите батчинг — упрётесь. Стоит поставить в GPU-процессе
  `torch.cuda.set_per_process_memory_fraction` или хотя бы логировать
  `max_memory_allocated` раз в N кадров.
- **`cv2.setNumThreads(2)`** в каждом воркере — иначе 4 × 16 потоков на 16 ядрах.
- **`tqdm` только в главном процессе.** Воркеры не должны ничего писать в stdout
  напрямую — только через `log_queue`.
- **Ошибка в воркере не должна валить пул.** Сейчас `run_batch` ловит исключение
  на кадр и печатает трейс; в MP-режиме исключение надо возвращать как результат
  (`Result(ok=False, traceback=...)`), иначе воркер молча умрёт, и его задания
  потеряются.
- **Ctrl+C.** Нужен обработчик, иначе останутся висеть GPU-процесс и слабы.
  `KeyboardInterrupt` в главном → sentinel'ы всем → `join(timeout)` → `terminate`.
- **Проверка эквивалентности.** У вас уже есть рабочий харнес: прогон на 5 кадрах
  в старом и новом режиме + `diff -r --brief`. Однопоточный и многопроцессовый
  режимы обязаны давать побайтово одинаковый результат — это самый дешёвый способ
  поймать ошибку в упаковке массивов.

## 11. Сначала посмотрите сюда: 20% кадра убираются одной формулой

Прежде чем строить многопроцессовую инфраструктуру, стоит знать: **самая дорогая
операция всего пайплайна — не нейросеть.**

`trim_cover_fragments` (`geometry.py`) — **2675 мс/кадр, 20% времени**. Внутри —
`cv2.dilate` ядром 103×103 и `cv2.erode` ядром 205×205. Замер:

```
erode 201×201, 16 потоков:                                1658 мс
erode 201×201,  1 поток:                                  1596 мс   ← не параллелится вообще
distanceTransform (математически эквивалентная эрозия):     13 мс   ← в 127 раз быстрее
```

Эрозия диском радиуса *r* — это в точности «пиксели, удалённые от фона больше чем
на *r*», а дилатация — «удалённые от объекта не больше чем на *r*». То есть

```python
dilated = cv2.distanceTransform(255 - mask, cv2.DIST_L2, 5) <= d
eroded  = cv2.distanceTransform(dilated,    cv2.DIST_L2, 5) >  2 * d
```

даёт то же самое за два линейных прохода — и даже точнее, потому что
`getStructuringElement(MORPH_ELLIPSE)` строит многоугольную аппроксимацию круга,
а distance transform работает с настоящей евклидовой метрикой. Заодно исчезает
вся возня с `copyMakeBorder`, ради которой в докстринге написан целый абзац про
«язык» у рамки кадра: у distance transform поведение на границе задаётся явно.

**Важно:** результат изменится на единицы пикселей по контуру (другая метрика),
поэтому — только через побайтовое сравнение и с вашими глазами на debug-оверлеях.

Аналогично стоит посмотреть:

- `compensate_levels` — 1417 мс. Сейчас `rescale_intensity` гоняет весь кадр
  во float32 (200 МБ) в несколько проходов. Так как вход uint8 и преобразование
  поканально одинаковое, это ровно **LUT на 256 значений** → `cv2.LUT`, ~20 мс.
- `brighten_finger_zone` — 965 мс. `distanceTransform` и арифметика идут по всему
  кадру, хотя зона пальца — это несколько процентов площади. Считать в bbox
  компоненты + падение — те же единицы миллисекунд.

Суммарно это ~5 из 9.7 CPU-секунд. Если их убрать, кадр станет ~8 с вместо 13.3,
и **соотношение сменится на 45% GPU / 55% CPU** — потолок многопроцессности упадёт
до ~2.2×, а оптимальное число воркеров до 2-3. Порядок работ от этого не меняется
(параллелить всё равно стоит), но ожидания стоит откалибровать заранее.

## 12. Порядок внедрения

1. **Оптимизации из §11** — дёшево, полезно в любом режиме, и меняет расчёт
   параметров. Проверка: побайтовое сравнение + просмотр оверлеев.
2. **Шаг 0 из §4** — сузить интерфейс `GpuModels`. Пока всё ещё однопоточно, но
   результат обязан остаться бит-в-бит. Проверка: `diff -r --brief`.
3. **Вынести `Task` и `skip_if_exists`** в построение списка. Однопоточный режим
   работает как раньше.
4. **Тайминги как данные** (`sink` в `log_timing`) + сводка в конце. Полезно уже
   в однопоточном режиме.
5. **GPU-процесс + прокси, но с одним воркером.** Самый важный шаг: если
   однопоточный и «одноворкерный» режимы дают одинаковые файлы — протокол верен.
6. **Пул воркеров + `QueueHandler`/`QueueListener`.**
7. **Замерить и подобрать `--jobs`** по строке «ожидание очереди GPU» из §8.2.

Критерий успеха, который стоит зафиксировать заранее: на партии из ~50 кадров
многопроцессовый режим даёт **побайтово те же файлы** и ускорение **не меньше 2.5×**
при `--jobs 4`. Если ускорение меньше — смотреть на «ожидание очереди GPU» и на
трафик через границу, а не добавлять воркеров.
