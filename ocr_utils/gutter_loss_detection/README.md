# Детектор ухода текста под корешок

Ранжирует развороты по тому, насколько тугой переплёт съел внутреннее поле полосы, и
отделяет случаи, которые можно восстановить по контексту, от тех, где остаётся только
пересканировать.

```bash
uv run python -m ocr_utils.gutter_loss_detection ПАПКА --recursive \
    --csv отчёт.csv --md-report отчёт.md --link-dir худшие/ --sheet врезки.png
```

Готовые прогоны — `run_scripts/gutter_loss_detection/`.

## Задача

В туго подшитом переплёте полоса не разворачивается до плоскости: бумага уходит в
корешок почти отвесно, и последние знаки строки оказываются ЗА сгибом — их на снимке
нет вовсе. У левой полосы теряются концы строк, у правой — начала.

**Вопрос не «близко ли текст к корешку», а «потерян ли он».** В книге с тугим
переплётом текст подходит к сгибу вплотную на каждом развороте; на размеченной папке
«1926/08» внутреннее поле в пикселях у помеченных вручную кадров и у непомеченных
совпадает. Различает их только то, остаётся ли между последним знаком и сгибом
БУМАГА — то есть успела ли строка кончиться до того, как страница ушла из вида.

Второе важное деление — **чем именно набрана съеденная зона**. Разорванное переносом
слово восстанавливается по контексту: продолжение стоит на следующей строке. Утраченная
цифра таблицы не восстанавливается ничем — догадка о ней была бы подделкой данных.
Поэтому детектор помечает табличные полосы отдельно: их только пересканировать.

## Как это устроено

Всё считает `geometry.py`, один разбор на кадр:

1. **Кадр читается в рабочем масштабе** (ширина ~2000 px) прямо из JPEG-декодера.
   Признак крупный, полное разрешение ему не нужно: папка из 148 кадров по 11 Мпикс
   меряется за 4,6 с на 14 процессах.
2. **Маска краски — полосовой отклик** (DoG на масштабе штриха), а не порог по уровню
   бумаги. У корешка бумага уходит в тень (253 → 200 на полусотне пикселей), и порог
   вида «темнее доли локального фона» записывает саму тень в краску: внутреннее поле
   тогда всюду выходит нулевым и помеченные кадры от чистых не отличаются вовсе.
3. **Из маски вычитаются длинные вертикали и горизонтали** — тёмный след краёв страниц
   и линейки таблиц. Обе структуры лежат ровно там, где мы меряем поле, и обе не текст.
4. **Сгиб подгоняется НАКЛОННОЙ ПРЯМОЙ** по тёмному следу между полосами, и поля
   меряются ПОСТРОЧНО. Съёмка с рук даёт поворот разворота порядка 15 px по высоте
   кадра — усреднённый по всем строкам профиль краски размазывает этим поворотом
   коридор шириной в те же десятки пикселей. Замерено: без построчного замера качество
   ранжирования падает с AUC 0.86 до 0.5, то есть до подбрасывания монеты.
5. **Поле выражается в ШАГАХ СТРОК.** Пак — сорок лет выпусков: кегль и расстояние до
   камеры разные, а шаг строк меняется вместе с ними и потому годится за масштаб.

Балл кадра (`metrics.py`) — насколько СУММАРНЫЙ коридор у корешка (поле левой полосы
плюс поле правой, по 10-му процентилю строк) не дотягивает до нормы в 1.2 шага строки.
0 — поле в норме, 1 — строки обеих полос упираются в сгиб.

Почему по сумме, а не по худшей полосе: тугой переплёт — свойство разворота, он
съедает обе полосы сразу, просто несимметрично. Замерено на размеченной папке:

| признак | AUC |
|---|---|
| поле левой полосы | 0.77 |
| поле правой полосы | 0.84 |
| доля строк, дотянувшихся до сгиба | 0.76 |
| **сумма полей (эта метрика)** | **0.86** |

Берётся 10-й процентиль, а не медиана: строки в наборе разной длины, и вопрос «теряем ли
текст» решают самые тесные из них.

## Валидация

Размеченная папка — `2026-08-22-ПХ/1926/08`, 148 кадров, из них 32 помечены вручную
припиской `тугой_переплёт` в имени файла. Измерено 142 (шесть — вклейки и полосы без
сплошного набора, о них сказано в отчёте отдельной строкой).

| порог | отобрано | из них помечено | полнота |
|------:|---------:|----------------:|--------:|
| 0.35 (по умолчанию) | 87 | 32 | 1.00 |
| 0.80 | 59 | 27 | 0.84 |
| 0.90 | 50 | 26 | 0.81 |

**Ручная разметка неполна, и это видно.** На пороге по умолчанию детектор берёт 55
кадров сверх помеченных. Восемнадцать верхних из них просмотрены по листу врезок: на
всех восемнадцати текст (а на `IMG_0067` — цифры таблицы) доходит до сгиба без поля,
то есть это пропуски ручного прохода, а не ложные срабатывания. Поэтому «точность»
против такой разметки считать бессмысленно, и в таблице её нет: честная величина
здесь — полнота и порядок ранжирования.

**Где метрика недобирает.** На табличных полосах внутреннее поле читается завышенным:
между колонками цифр стоят широкие пробелы, и коридор у корешка выглядит шире, чем он
есть. Четыре помеченных таблицы получили балл 0.44–0.84 вместо ожидаемых 0.9+. Порог по
умолчанию их всё равно берёт, но в рейтинге они стоят ниже, чем заслуживают.

## Что показывает отчёт

* **балл** — 0 … 1, больше = сильнее ушёл текст.
* **вердикт** — `таблица` (только пересканировать), `текст` (восстановим по контексту),
  `ок` (поле в норме).
* **поле L / поле R** — внутреннее поле полосы в шагах строк, приписка `(табл.)` —
  у корешка найдены линейки таблицы.

Плюс `--link-dir` (папка симлинков, пронумерованных по рейтингу) и `--sheet` — лист
врезок вокруг сгиба. Врезка показывает ровно то, по чему принято решение, и полсотни
их просматриваются за минуту: проверять такой детектор, открывая кадры по одному, на
паке в тысячи разворотов невозможно.
