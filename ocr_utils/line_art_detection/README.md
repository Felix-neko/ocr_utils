# line_art_detection — страницы с крупным штриховым рисунком

Находит в бинаризованных PDF страницы, на которых есть **крупный line art**, и выгружает
их картинками для просмотра глазами.

## Зачем

FineReader с включённым «исправлением искажений строк» иногда корёжит line art. Эталон
дефекта — стр. 80 файла `/mnt/system/raw/full_1967_01_bg_off_ori_off.pdf`: схема
организации диспетчерской службы вышла с чёрными гребёнками вместо рамок и надписей.
Такие страницы при сборке финального PDF надо брать из бинаризации, сделанной **без**
распрямления строк.

Чтобы найти их, не листая девять тысяч полос пака, нужен признак «на этой странице есть
сколько-нибудь крупный штрих». Его и считает этот подпакет.

**Ищется:** крупные штриховые рисунки, гравюры, схемы, карты; крупные разлинованные
таблицы; графики и диаграммы; многострочные формулы (только с `--use-surya-layout`).

**Не ищется:** мелочь (виньетки, эмблемы рубрик, буквицы) — покорёженная виньетка никому
не мешает; полутоновые фотографии — распрямление строк их так заметно не портит.

## Команды

Их две, потому что порог подбирается глазами и не с первого раза. `scan` один раз считает
признаки всех страниц; `export` сколько угодно раз применяет к готовому CSV разный порог.

```bash
# 1. Тяжёлый проход: признаки всех страниц -> CSV. Единожды.
uv run python -m ocr_utils.line_art_detection scan \
    --input-dir /mnt/system/raw/mts/pack1_pdf/full_pdfs_binary_brightened_bg \
    --db ~/Projects/mts_markup/pack1_reviewed.sqlite --pack-name пак-1 \
    --csv line_art_pack1.csv --md-report reports/line_art_pack1.md --jobs 16

# 2. Дешёвый проход: порог -> картинки, по папке на выпуск. Сколько угодно раз.
uv run python -m ocr_utils.line_art_detection export \
    --csv line_art_pack1.csv --out-dir line_art_pack1_05 --min-coverage 0.05
```

Готовый прогон с тремя порогами сразу — `run_scripts/line_art_detection/run_line_art_pack1.sh`.

**Формулы — отдельным заходом.** Многострочная формула занимает 0.4–1.3% полосы (замер по
эталонному выпуску: стр. 23, 25, 85, 87), поэтому порогом, настроенным на рисунки, её не
достать никогда. Их выбирают не порогом, а источником находки:

```bash
uv run python -m ocr_utils.line_art_detection scan ... --use-surya-layout --surya-cache .surya_cache
uv run python -m ocr_utils.line_art_detection export \
    --csv line_art_pack1.csv --out-dir line_art_pack1_formulas \
    --min-coverage 0.003 --source surya:Equation
```

Выгрузка выглядит так; на каждой картинке вся полоса целиком и красная рамка вокруг
находки (проверяется не сама картинка, а не поехала ли она **относительно текста**):

```
line_art_pack1_05/
    full_1966_01/full_1966_01_p0078_cov0.461.jpg
    full_1966_02/...
```

## Как это работает

Текст распадается на пятна размером с букву; рисунок даёт одно длинное связное пятно;
типографская линейка — пятно длинное, но **одномерное**; чёрная кайма скана — **сплошная
масса**. Отсюда четыре правила: площадь, короткая сторона, вытянутость рамки и плотность.

* **Вытянутость** отсекает линейки, отточия и потёки вдоль края: у настоящих находок она
  1.1..10.4, у них 32..167.
* **Плотность** отсекает чёрную кайму скана — ту самую «чёрную кляксу по краю страницы».
  Это приём Leptonica (`pixGenerateHalftoneMask` — детектор не картинок, а сплошной
  массы), применённый к отдельному пятну: после эрозии диском в два штриха от рисунка не
  остаётся ничего (0.000..0.037), а от каймы остаётся почти всё (0.64..0.86).

Разлинованная таблица связным пятном не является вовсе — в этой печати её линейки друг
друга не касаются, — поэтому ищется отдельно, по **скоплению линеек обеих ориентаций**.
Условие про обе ориентации отделяет таблицу от полосы содержания: строка отточий даёт
сколько угодно горизонталей и ни одной вертикали.

Краска берётся **глобальным порогом**: страница уже битональная. `adaptiveThreshold` из
`scan_markup.detection.dots` здесь неприменим — он строился под камерные сканы и на
чистой бумаге объявляет краской всю страницу (замер в докстринге `features`).

Полутоновые фотографии отсеиваются **ручной разметкой** из базы `scan_markup` (`--db`), а
не пикселями: пиксельные признаки из литературы (размер дыр, длина прогонов) на этом
материале не разделяют — почему именно, замерено и записано в `features` и в
`reports/line_art_detection_state_of_the_art.md`.

## Недописанная выгрузка

Бинаризованные PDF выгружает FineReader в виртуалке, и выгрузка идёт часами. Прогон
8 сентября пришёлся ровно на неё: число PDF в папке менялось 93 → 89 → 90, а число
страниц в отчёте 9170 → 8774 — и по самому отчёту это неотличимо от правки порогов.

Поэтому `scan` по умолчанию пропускает PDF, которых касались меньше `--min-age-minutes`
(10) назад, и о каждом пишет в stderr. Перед окончательным прогоном стоит убедиться, что
выгрузка закончилась:

```bash
find "$INPUT_DIR" -name '*.pdf' -mmin -30 | wc -l   # должно быть 0
```

## Стоимость

0.25 с на страницу в один поток при полных 600 dpi — около двух с половиной минут на весь
пак при `--jobs 16`. С `--use-surya-layout` — порядка двух часов GPU, поэтому разметка
Surya кэшируется на диск (`--surya-cache`).

## Модули

| Файл | Что в нём |
|---|---|
| `page_layout/line_art/features.py` (переехал сюда из `features.py`) | признаки пятна, правило «это штрих», детектор скоплений линеек; **все замеры и пороги**; вид каждой объединённой рамки (`PageFindings.kinds`: `table` по скоплению линеек / `drawing` по связному пятну, по площади кандидатов) — нужен этапу `scan_markup detect`, который кладёт находки в базу видами `stroke_table`/`stroke_drawing` (`scan_markup/detection/stroke_regions.py`) |
| `render.py` | рендер страницы PDF в numpy |
| `markup.py` | растровые области из SQLite в координатах страницы PDF |
| `layout.py` | предложения Surya (`Figure`/`Table`/`Equation`/`Form`), кэш на диск |
| `analysis.py` | обход папки, пул процессов, `PageResult` |
| `export.py` | выгрузка страниц картинками с рамками |
| `report.py` | CSV, markdown, консольная таблица |
