# page_layout.tables — таблицы и блок-схемы на полосе (бывший scan_markup.table_detection)

Детектор находит на полосе журнала **таблицы с линейками** и **блок-схемы / штриховые
рисунки** (line art) и отдаёт их прямоугольниками в пикселях оригинала. Это четвёртая
версия детектора из исследований (`research/legacy/table_processing`, v4.2), перенесённая в
рабочий конвейер: этап `detect` пакета `scan_markup` кладёт находки в `rect_regions`
видами `table` и `line_art_schema`, `to-cvat` отдаёт их разметчику на уточнение,
`from-cvat` возвращает уточнённые.

Зачем это конвейеру. Таблицу и схему лечат иначе, чем сплошной набор: строки в таблице не
распрямляют распрямителем FineReader, графу таблицы можно расширить под повёрнутый текст, а
блок схемы обязан остаться на месте, и повёрнутый текст вписывают в него. Для всего этого
нужно знать, ГДЕ таблица и ЧТО это — таблица или схема.

## Вход, выход, место в конвейере

**Вход.** Серая копия полосы в рабочем разрешении **150 dpi** — для пака-1 это копия 1/4
от 600-dpi скана «Готовое», та же, по которой этап `detect` гоняет surya и ищет растр. Полоса
берётся **сырой**: до поворота боком напечатанных полос, до размытия фона, до заострения —
детектор калиброван на таких. Размеры в коде — в миллиметрах, а не в долях кадра: полосы пака
различаются по размеру, и доля кадра означала бы разный физический порог на разных полосах;
пересчёт в пиксели (`ruling.mm_to_px`) — единственное место, где живёт dpi.

Вторым входом, **необязательным**, идёт разметка surya layout той же копии
(`layout.PageLayout`: блоки Table, Figure, Picture, Form, Text… с уверенностью). Surya —
источник ВИДА объекта и подсказки протяжённости, а не границ: границы у неё ±1–2 мм, а
таблицей она называет 10 из 38 «не таблиц». Без surya всё работает на CPU, вид решают
линейки. Ответы surya кэшируются на диске (`detection/layout_cache.py`, опция
`detect --layout-cache`): секунда GPU на полосу — это три с половиной часа на пак.

**Выход.** `detector.detect(gray, dpi, layout=…)` отдаёт список `geometry.TableBox`:
рамка `box` (по ней режут), рамка линеек `rule_box` (по ней считались признаки), вид
`kind` («таблица», «схема», «рисунок»), наклон линеек `skew_deg`, балл и словарь метрик.
`to_regions` переводит их в `Region` — координаты оригинала, вид базы (`table`, либо
`line_art_schema` для схемы и рисунка) и JSON `detector_info` с тонким видом и метриками.
`TABLE_DETECTOR_VERSION` — версия алгоритма; она пишется в `Page.table_detector_version` и
решает при `--skip-detected`, надо ли пересчитывать полосу.

**Непристроенные линейки.** `detector.detect_all(gray, dpi, layout=…)` отдаёт
`TableDetection(found, loose_rules)`: те же находки и линейки полосы, центр которых не лежит ни в
одной находке (тени у края кадра не берутся). Линейка — `geometry.LooseRule`: ось ломаной
`points` (через 2 мм по трассе `traces.trace_rules`, так что изогнутая остаётся изогнутой; без
трассы — прямой отрезок), `horizontal`, `thickness_px`. `PageLayout.loose_rules` — они же в родных
пикселях, минус лежащие в line art и растре; `page_layout analyze --json` пишет их ключом
`loose_rules`, оверлей рисует ломаной. Детектор текстовых блоков берёт их барьерами
(`text_blocks`, подсказка `LayoutHints.rules`). Пак-1: 35 331 линейка на 6 920 полосах из 12 135
(медиана одна на полосу, у бланков — сотни); находки детектора от этого не меняются.

**Цена.** Около 60 мс на полосу на CPU (без surya). Этап `detect` считает таблицы в
воркерах пула, если разметка surya нашлась в кэше, и в родителе — если её пришлось считать.

## Пример использования

Готовый пример — `example.py` рядом с этим README. К нему две картинки пака-1 в 300 dpi, обе с
наклонными таблицами, у которых наклон плавает от линейки к линейке (полоса изогнута). Картинки
примера хранятся **только в JPEG и без цвета — в градациях серого** (один канал, качество 85–92):
так они меньше весят в git. Новые картинки сохранять так же (`Image.convert("L")`).

| `--sample` | файл | что на нём | что получается |
|---|---|---|---|
| `clean` (по умолчанию) | `example_table_clean.jpg` | правая колонка 1968/05 с.70, таблицы 4 и 5 | таблица 4: наклон −0,7°, сетка 4 × 5, 18 ячеек, шапки «Должно быть поставлено» и «Фактически поставлено» — ячейки 1 × 2. Таблица 5: наклон +0,44°, волнистая нижняя линейка, 15 ячеек, шапка — одна строка |
| `curved` | `example_table_curved.jpg` | 1968/03 с.4, таблица 1 | наклон −2,5°, у верхней линейки наклон по длине от −5° до +1,5° с изломом, отрезок «начало–конец» отходит от неё на 0,84 мм. Сетка по кривым — 4 × 3, 10 верных ячеек; прежняя сетка по осям (`--axis-grid`) — 6 × 3 с лишними строками |

Запуск без параметров:

```bash
uv run python -m ocr_utils.page_layout.tables.example                               # clean, surya на GPU, окно matplotlib
uv run python -m ocr_utils.page_layout.tables.example --sample curved --axis-grid   # + прежняя сетка по осям для сравнения
uv run python -m ocr_utils.page_layout.tables.example --no-surya                    # только CPU, вид решают линейки
uv run python -m ocr_utils.page_layout.tables.example --image скан.tif --dpi 600 --out /tmp/табл.png
```

Пример печатает рамку таблицы, список рёбер (концы, наклон отрезка «начало–конец», диапазон наклона
по длине, наибольшее отклонение отрезка от кривой, полоса сглаживания) и список ячеек, а потом рисует
всё поверх картинки: линейки — сплайнами, отрезки — пунктиром, ячейки — многоугольниками по кривым.

Детектор и сетка ячеек — **два разных шага в двух разрешениях**: детектор ищет таблицу на копии
полосы в 150 dpi и отдаёт только рамку; рёбра и ячейки строятся потом по вырезке таблицы в
300 dpi (`grid.WORK_DPI`, под него калиброваны пороги). Ниже тот же путь без обёрток примера.

**1. Подать полосу на детектор.**

```python
import cv2
from ocr_utils.page_layout.image import PageImage, Variant
from ocr_utils.page_layout.surya.model import SuryaLayoutModel
from ocr_utils.page_layout.tables import ruling
from ocr_utils.page_layout.tables.detector import detect

gray = cv2.imread("ocr_utils/page_layout/tables/example_table_curved.jpg", cv2.IMREAD_GRAYSCALE)
image = PageImage.from_array(gray, dpi=300, variant=Variant.SCAN)

work = image.gray_at(ruling.WORK_DPI)                 # серая копия 150 dpi — вход детектора
height, width = work.shape
blocks = SuryaLayoutModel().predict_one(image.surya_frame)   # необязательно: None = без surya
layout = blocks.scaled_to(width, height)              # блоки surya — в пикселях той же копии

found = detect(work, ruling.WORK_DPI, layout=layout)  # list[TableBox] в пикселях копии 150 dpi
factor = image.scale_to_native(ruling.WORK_DPI)       # 2.0: во сколько раз оригинал крупнее копии
for table in found:
    print(table.kind, table.box.scaled(factor).as_tuple(), f"{table.skew_deg:+.2f}°")
```

В конвейере surya не зовут на каждую полосу: блоки берут из кэша (`SuryaSource`, см. README
`page_layout`), а весь разбор полосы идёт через фасад `PageLayout(..., {Find.TABLES}).process(surya)`,
который отдаёт таблицы уже регионами (`layout.tables`), а находки детектора — в
`layout.table_findings()`.

**2. Разобрать таблицу на рёбра-кривые и ячейки.**

```python
from ocr_utils.page_layout.geometry import KIND_TABLE
from ocr_utils.page_layout.tables.curved_grid import curved_table
from ocr_utils.page_layout.tables.ruling import mm_to_px

table = next(t for t in found if t.kind == KIND_TABLE)        # у схемы и рисунка сетки нет
box = table.box.scaled(factor).padded(mm_to_px(3.0, image.dpi)).clipped(image.width, image.height)
crop = image.gray[box.slice]                                  # вырезка с полем 3 мм, здесь уже 300 dpi
# (если оригинал не в 300 dpi — привести вырезку к 300 dpi через cv2.resize и учесть масштаб в mapped)

traces, grid = curved_table(crop, 300)                        # трассы линеек и сетка — в пикселях вырезки
traces = [t.mapped(1.0, box.x0, box.y0) for t in traces.all]  # → пиксели страницы
grid = grid.mapped(1.0, box.x0, box.y0)

for trace in traces:                                          # каждое ребро: отрезок и кривая
    (x0, y0), (x1, y1) = trace.chord                          # концы — отрезок «начало–конец»
    along = trace.along_grid(12.0)                            # точки вдоль линейки через 1 мм (12 px)
    angles = trace.angle_deg_at(along)                        # наклон в каждой точке, °
    deviation, _where = trace.max_chord_deviation_px()        # насколько отрезок врёт, px
    print(trace.axis, (round(x0), round(y0)), (round(x1), round(y1)),
          f"хорда {trace.chord_angle_deg:+.2f}°, по длине {angles.min():+.2f}…{angles.max():+.2f}°,"
          f" отклонение {deviation:.1f} px")
    polyline = trace.sample(1.0)                              # (N, 2): сглаженная кривая через 1 мм

for cell in grid.cells:                                       # ячейки: многоугольник по кривым
    print(cell.row, cell.col, f"{cell.row_span}×{cell.col_span}", cell.box.as_tuple(), len(cell.polygon))

region = grid.cell_at(2, 0).extract(image.gray)               # область ячейки по кривым границам
region.image, region.mask, region.box                         # вырезка (вне области — бумага), маска, где стоит
```

Трассы и ячейки переносятся из пикселей вырезки в пиксели страницы `mapped(scale, dx, dy)` (сдвиг и
масштаб; сплайн не перестраивается). Прежняя сетка по осям — `grid.grid_from_lines(find_lines(crop,
300), …)`; её отрезки `Segment` хранят только габарит и средний наклон, и на изогнутой таблице она
ломается (см. раздел ниже). Рабочий разбор таблиц конвейера (`text_layer_fix.zones.analyse_table`)
пока на сетке по осям: перед ней он выравнивает вырезку по линейкам (`deskew_by_rules`).

## Что на выходе: рамки, ячейки, рёбра

Все типы — в `page_layout/geometry.py` и `tables/ruling.py`. Координаты везде целые пиксели того
изображения, которое подавали функции; `Box(x0, y0, x1, y1)` — полуоткрытый прямоугольник:
`x1`, `y1` лежат **за** последним пикселем, как в срезе питона (`gray[box.slice]`).

**Находка детектора — `TableBox`.** Детектор отдаёт только рамки, ячеек и рёбер в ней нет:

| поле | что это |
|---|---|
| `box: Box` | рамка, по которой режут: подвинута до чистого просвета, чтобы не резать буквы |
| `rule_box: Box \| None` | огибающая самих линеек, по ней считались признаки проверки; `None` — совпадает с `box`; удобнее брать `table.rules` |
| `kind: str` | `"таблица"`, `"схема"` или `"рисунок"` (`geometry.KIND_TABLE` / `KIND_DIAGRAM` / `KIND_DRAWING`) |
| `skew_deg: float` | медианный наклон горизонтальных линеек; положительный — таблицу надо повернуть **по часовой**, чтобы линейки легли горизонтально |
| `score`, `metrics` | балл и признаки проверки (`lattice`, `edge_fill`, `cells`, `glyph_of_ink`…) — то, что пишется в `detector_info` |

**Рёбра — `traces.RuleTrace`**, их отдаёт `traces.trace_rules(gray, dpi)` (списки `horizontal`,
`vertical` и маски пикселей линеек) или `curved_grid.curved_table` первым элементом. Трасса —
функция «поперёк от вдоль» (`y(x)` у горизонтали, `x(y)` у вертикали): сглаживающий сплайн по
отсчётам линейки. Все методы берут и отдают пиксели той картинки, куда трассу перенесли `mapped`:

| поле / метод | что это |
|---|---|
| `axis` | `Axis.HORIZONTAL` / `Axis.VERTICAL` |
| `chord` | концы `((x, y), (x, y))` — отрезок «начало–конец»; `chord_angle_deg` — его наклон |
| `across_at(along, extend_px=0)` | положение линейки в любой точке; за концами — NaN (или касательная на `extend_px`) |
| `slope_at(along)`, `angle_deg_at(along)` | наклон в любой точке: производная и градусы в валюте `skew_deg` (положительный — повернуть по часовой) |
| `point_at(along)`, `sample(step_mm=1)` | точки `(x, y)` кривой; `sample` — ломаная через 1 мм с концами |
| `along_grid(step_px)` | координаты вдоль от начала до конца с шагом |
| `max_chord_deviation_px()` | насколько отрезок «начало–конец» отходит от кривой и где |
| `thickness_px`, `coverage`, `gaps` | толщина штриха, доля длины с краской, разрывы (просветы уже 3 мм закрывает ещё поиск фрагментов) |
| `bandwidth_mm`, `residual_rms_px`, `residual_max_px` | выбранная полоса сглаживания и остаток отсчётов от кривой |
| `length_mm`, `start_out`, `end_out` | длина и концы вдоль |
| `mapped(scale, dx, dy)`, `to_json()` / `from_json()` | перенос в другую картинку; JSON — ломаная через 1 мм и компактный сплайн (узлы через 5 мм) |

**Ячейки — `curved_grid.CurvedGrid`** (второй элемент `curved_table`):

| поле | что это |
|---|---|
| `rows`, `cols` | границы строк и колонок — `Boundary`: кривая на всю таблицу (`before`/`after` — две кривые у двойной линейки), трассы, из которых собрана, `is_double`, `is_virtual` (внешняя граница без линейки) |
| `cells: tuple[CurvedCell]` | ячейки по (строка, колонка) |
| `header_rows` | строк шапки: до первой двойной линейки, без неё — первая строка |
| `n_rows`, `n_cols`, `cell_at(r, c)`, `boundary_points(b)`, `mapped`, `to_json()` | удобства |
| `as_axis_grid()` | та же сетка в типах `geometry.Grid` (ячейки — рамки многоугольников) — для потребителей прежней сетки |

Ячейка `CurvedCell`: `row`, `col`, `row_span`, `col_span`, `is_header` — как у `Cell`; `polygon` —
многоугольник `(N, 2)` из кусков четырёх кривых через углы (обход по часовой от левого верхнего);
`inner_polygon` — то же без линеек (кривые сдвинуты внутрь на измеренный край штриха + 0,3 мм);
`box`, `inner_box` — их рамки (только для грубого поиска: сама область — многоугольник);
`extract(image, inner=True)` — **область ячейки**: `CellRegion(image, mask, box)` — вырезка по рамке
многоугольника, где всё вне многоугольника залито бумагой, маска многоугольника и место вырезки на
картинке; `region_area` — площадь области; `mask(shape, inner=False)` — маска на всю картинку; `sides` — по каждой
стороне куски `CurvedEdge(present, fill, thickness, before, after)`: есть ли линейка, какая доля
стороны в краске, толщина и края штриха; `irregular` — объединение «уголком».

**Прежние рёбра — `ruling.Lines`.** `find_lines(gray, dpi)` отдаёт линейки двумя списками,
`lines.horizontal` и `lines.vertical`, и две маски краски линеек (`horizontal_mask`,
`vertical_mask`, `uint8` 0/255 размером с кадр). Каждая линейка — `Segment`:

| поле | что это |
|---|---|
| `box: Box` | габарит штриха — компонента связности маски одной оси |
| `horizontal: bool` | ось |
| `angle_deg: float` | наклон этой линейки (регрессия по её пикселям) в той же валюте, что `skew_deg`: у горизонтали положительный — правый конец ниже левого, у вертикали — нижний конец левее верхнего |
| `length` | длина вдоль оси в пикселях (ширина габарита у горизонтали, высота у вертикали) |

Линейка — это отрезок, а не прямая на всю таблицу: вертикаль, прерванная объединённой ячейкой или
разрывом краски, — два отрезка (в примере `clean` верхняя линейка таблицы 4 приходит двумя
отрезками с наклоном −1,21° и −0,76°). Эти отрезки ищет
открытие по осям ядром 8 мм; детектор на полосе ищет линейки иначе — цепочками фрагментов 3 мм
(`rules.find_rules`, шаг 1 ниже) — и наружу их не отдаёт.

**Прежние ячейки — `geometry.Grid` (УСТАРЕЛО)**, результат `grid.grid_from_lines`: ячейка —
прямоугольник между прямыми разделителями, на наклонной и изогнутой таблице ломается. Оставлена, пока
на ней работает конвейер (`rotated_text.tables`, `text_layer_fix`, проверка находок `verify`); новый
код писать на `curved_grid`:

| поле | что это |
|---|---|
| `xs`, `ys` | координаты разделителей колонок и строк: их на один больше, чем колонок и строк; внешние границы добавлены, даже если внешней рамки нет |
| `cells: list[Cell]` | ячейки, отсортированы по (строка, колонка) |
| `header_rows` | сколько верхних строк — шапка (до двойной линейки; без неё — первая строка) |
| `double_rule_ys` | где стоят двойные линейки |
| `column_cuts` | где резать картинку по вертикали, не рассекая линейку (левый край штриха) |
| `n_rows`, `n_cols`, `cell_at(r, c)`, `shifted(dx, dy)`, `to_json()` / `from_json()` | удобства |

Ячейка `Cell`:

| поле | что это |
|---|---|
| `row`, `col` | левая верхняя клетка решётки, от нуля |
| `row_span`, `col_span` | объединение; объединённая ячейка записана **один раз**, в своей левой верхней клетке, прочие накрытые клетки в `cells` не появляются |
| `box: Box` | геометрия ячейки — рамка по **центрам** её линеек |
| `inner: Box` | внутренность без линеек: отступ от каждой из четырёх линеек по её измеренной толщине плюс 0,3 мм — то, что режут под распознавание |
| `is_header` | ячейка шапки |

Рёбра ячейки по отдельности — положение и толщина линейки на каждой стороне каждой полосы
(`geometry.Edge`: `position`, `thickness`, `present`, `low`/`high` — края штриха) — сетка считает
внутри себя (`grid._edge_tables`, `grid.edge_at`), но в `Grid` не хранит: наружу выходят уже
собранные `box` и `inner`. Если нужны, их даёт
`grid.edge_at(lines.vertical_mask, x, y_top, y_bottom, True, tolerance)` для вертикали на высоте
строки и так же для горизонтали.

**Поведение сетки, которое видно на примере `clean`.** Объединение ищется по отсутствию
линейки вдоль стороны клетки (краска меньше чем на половине стороны): так «Должно быть
поставлено» и «Фактически поставлено» над двумя графами каждая стали ячейками 1 × 2 — одинаково у
обеих сеток. Горизонталь под шестью колонками из семи — сквозная (`GLOBAL_ROW_SHARE` 0,6), и через
неё обе сетки не объединяют: «Месяцы I квартала» таблицы 4 — две ячейки. Шапка ищется по двойной
линейке (две горизонтали ближе 1,5 мм, `DOUBLE_RULE_MM`): у таблицы 5 нижняя линейка волнистая, и
сетка по осям принимала два её куска на высоте 1680 и 1697 px за двойную линейку — все три строки
выходили шапкой; сетка по кривым требует от двойной линейки параллельности, у неё шапка — одна строка.

## Трассы линеек и сетка по кривым

Модули `traces.py` и `curved_grid.py`; детектор и прежняя сетка (`grid.py`) ими не меняются.
Замеры — `reports/curved_table_grid.md` (31 самая перекошенная таблица пака-1, стенд
`research/table_traces`, прогон `run_scripts/table_traces/run_eval.sh`).

**Зачем.** Сетка по осям на изогнутой таблице ломается: разделитель строки — одна координата y, а
линейки ищет открытие ядром 8 мм, и линейка толщиной 2–3 px при наклоне 2,5° уходит со своей строки
через 5–7 мм. Верхняя линейка 1968/03 с.4 находится тремя обрывками на высоте 258, 305 и 313 px,
каждый даёт свой разделитель — лишние строки, ячейки шапки разрезаны вдоль наклона. Выравнивание
вырезки (`deskew_by_rules`) не помогает: левая часть таблицы наклонена круче правой. На 31 таблице
отрезок «начало–конец» отходит от линейки ≥ 30 мм в медиане на 0,19 мм, у 40 % — больше толщины
линейки (0,25 мм), наибольшее — 1,75 мм; наклон вдоль одной линейки меняется в медиане на 1,8°, у
p90 — на 4,2°.

**Трасса** (`trace_rules`). Пиксели — фрагменты 3 мм детектора и их цепочки
(`rules.fragment_layers`, `rules.chain_groups`): открытие коротким ядром держит линейку одной
компонентой во всю длину, пока толщина штриха больше L·tg θ — при 300 dpi и 4 px до 6,5°. Берутся
пиксели именно фрагментов цепочки, не всё в её габарите. По каждому столбцу — пробег, ближайший к
предсказанию (второй проход — по первой кривой), и центр тяжести **тёмности серого** в нём с запасом
в пиксель: середина бинарного пробега ходит лесенкой ±0,5 px с периодом 1/наклон, и сплайн рисовал
по ней ложную волну ±2°. Пробеги толще 1,8 медианы (пересечения, прилипшие буквы) отброшены; по
1,5 толщины у концов в подгонку не идут (угол, косой срез). Кривая — `make_smoothing_spline` с двумя
итерациями весов Тьюки; полоса h — наибольшая из `SMOOTH_LADDER_MM` (6, 4, 3, 2, 1,5 мм), при которой
остаток, усреднённый в окне 3 мм, не выше max(2σ, 0,5 px). Автоматический выбор GCV не годится: он
идёт за лесенкой пикселей. Сшивка (`join_traces`) продолжает концы кривых по касательным и сливает
совпадающие куски одной линейки.

*Продолжение за концы.* Фрагмент 3 мм не переживает наклона круче ~6,5°, а у края полосы линейка
загибается сильнее: боковая таблица 1976/08 IMG_0067_1L за последней вертикалью уходит вниз под
10–13° на 7 мм, и эти куски не находились вовсе. Трасса продолжается от каждого конца шагом в
столбец: предсказание — по касательной к последним 3 мм, в окне ±0,4 мм берётся тонкий пробег,
касательная обновляется по новым отсчётам (до 45°). Просвет бумаги — не больше 0,5 мм (у строки
текста просветы между буквами шире, и по ней трасса не утечёт); просвет с пересечением
перпендикулярной линейки внутри — узел таблицы — до 3 мм: линейка часто обрывается за 1–1,5 мм до
вертикали и продолжается за ней. Продолжение короче 1 мм отбрасывается.

**Сетка** (`curved_table`, `curved_grid_from_traces`):

1. *Линейки таблицы* (`table_rules`). Линейки таблицы — одна связная сеть. Опорные — не короче
   половины охвата своей оси (края и сквозные линейки); к ним по цепочке касаний добавляются
   остальные: линейка от 8 мм — если хоть где-то касается принятой перпендикулярной (1,5 мм +
   толщина), короткая (4–8 мм) — если оба конца вплотную к принятым (0,5 мм + толщина) или она встык
   продолжает принятую. Нелинейка толще 1,5 медианной толщины опорных не берётся вовсе. Так отпадают
   штрихи крупных букв заголовка (10–13 px против 3–4 px), рамка штампа (5 px, опирается сама на
   себя), номер «6» и «ИЮНЬ 1971» на обложке, черта дроби и тире в графе.
2. *Границы.* Трассы на одной высоте (медиана разности ≤ 1 мм) — одна граница; кривые, идущие ближе
   2 мм (`MIN_CELL_MM`: клетки уже не бывает), — тоже одна: колонка, прерванная строками, или
   карандашная черта у рамки (обложка 1971/06, «XX 15» давала графу в 15 px). Кривая общей границы —
   среднее трасс с весом по длине. Двойная линейка — 1–1,5 мм и параллельно (p95 − p5 ≤ 0,4 мм), её
   слияние не касается. Неполная граница продолжается на всю таблицу «параллельно» соседним длинным.
3. *Внешние границы* без линейки — копия крайней кривой у края вырезки; пустая крайняя полоса
   отбрасывается, как и строки без внутренних вертикалей.
4. *Углы* — пересечение `y = fh(x)` и `x = fv(y)` простой итерацией; *сторона есть*, если краска
   линейки стоит на ≥ 50 % её длины; *объединения*, сквозные строки и шапка — как в `grid.py`.
5. *Многоугольники* — куски кривых между углами через 1 мм; внутренность — кривые, сдвинутые на
   край штриха + 0,3 мм (как `Cell.inner`).

**Точность.** Синтетика с истинными кривыми (S-изгиб до 4,6°): положение в среднем 0,26 px, у концов
до 1,5 px (0,13 мм); наклон — до 1,1° внутри, до 1,9° у концов. Предел наклона на коротком участке —
около 1°. На паке профили наклона соседних параллельных линеек при полосе 4 мм коррелируют на
0,8–0,99 — общий изгиб бумаги трасса видит. Около 1,5 с на таблицу (до 8 с на таблице в 250 ячеек).

**Чего не умеет.** Черты дробей, стоящие в каждой графе на одном x (1973/08 с.62, боковая таблица),
цепочки сшивают через строки в «линейки» по 27 мм, касающиеся линеек строк, и сетка делает из них
колонки. Боковая таблица разбирается как есть: строки и колонки меняются ролями. Линейка, целиком
наклонённая круче ~6,5° (при штрихе 4 px), не находится вовсе: продолжение идёт только от уже
найденного куска; кусок загиба, оторванный от линейки просветом бумаги без пересечения, тоже остаётся
ненайденным (строка «10» боковой 1976/08). Декоративное подчёркивание, не касающееся ни одной линейки
(«Год издания» на обложке 1970/11), границей не считается. Полоса без внутренних вертикалей у края
(заголовок журнала на обложке) ячейкой не становится — как и в `grid.py`. В конвейер (`text_layer_fix`)
сетка по кривым не подключена.

## Как работает детектор, по шагам

Порядок: линейки → ядра → затравки → вид и проверка → рост по виду → рамка по рёбрам →
граница без разрезанных букв → слияние схем → дедупликация. Модули названы по шагам.

### 1. Линейки: фрагменты и цепочки (`rules.py`)

Бинаризация Otsu (`ruling.binarize`), затем морфологическое открытие **коротким** ядром
3 мм (`FRAGMENT_MM`) по каждой оси: остаются фрагменты, которые тянутся по одной строке
пикселей три миллиметра. Компоненты связности фрагментов получают ось, наклон (регрессия
по окну компоненты) и площадь.

Фрагменты одной оси **сшиваются в цепочку** (`chain`), если:

* зазор вдоль оси не больше 8 мм (`CHAIN_GAP_MM`); через зазор шире 2 мм
  (`CHAIN_SHORT_GAP_MM`) сшиваются только фрагменты не короче 5 мм (`CHAIN_LONG_MM`) —
  стебель буквы «ф» в 6 мм над таблицей стоит ровно на оси вертикали графы и иначе
  пришивался к ней, поднимая рамку на строку абзаца;
* на стыке они расходятся поперёк не больше 0,35 мм (`CHAIN_OFFSET_MM`) с учётом наклона
  первого — два пикселя при 150 dpi;
* наклоны согласны в пределах 2° (`CHAIN_ANGLE_DEG`).

Цепочка становится линейкой, если набрала 8 мм (`ruling.MIN_RULE_MM`) и не толще 1 мм
(`ruling.MAX_RULE_THICKNESS_MM`; толщина — площадь, делённая на длину, а не габарит: у чуть
наклонной линейки габарит вдвое шире штриха). Так линейка идёт вслед за изгибом полосы, и
загнутый конец не отрезается, как его отрезало открытие ядром 8 мм в прежних версиях.

**Кляксы.** Ядро недосвета у корешка бинаризуется в тонкую тёмную полосу и проходит пороги
линейки. Толщина её не отделяет (279 из 4301 линеек настоящих таблиц тоньше 1,5 px); отделяет
СОСЕДСТВО: доля не-линеечной краски в полосах шириной 1 мм по обе стороны
(`ISOLATION_BAND_MM`). Линейка с долей выше 0,55 по меньшей из сторон (`MAX_ISOLATION`)
отбрасывается: подчёркивание под словом темно с одной стороны, клякса — с обеих.

**Краевые линейки** (`refine.drop_border_rules`): длинная вертикаль ближе 10 мм к краю кадра
(`BORDER_MM`), не короче 0,4 стороны кадра и без единого пересечения — тень корешка, а не
линейка. Она выбрасывается до кластеризации. Для заливки схем (шаг 5) берутся линейки ДО
этого отсева: линейку колонтитула у самого верха надо вырезать из штриховой краски, а отсев
её уже потерял.

### 2. Ядра и затравки (`rules.cores`, `ruling.cluster_tables`)

Скопление линеек — **связное ядро**: линейки, которые пересекаются (допуск 1,5 мм,
`CROSS_TOL_MM`) или продолжают друг друга. Одиночная линейка ядром не является и ни к кому не
клеится — так отпадают колонтитул, подчёркивание в соседней колонке, линии бланка, дробная
черта формулы.

Две стопки линеек (шапка, отбитая от тела просветом) сливаются в одно ядро, если
перекрываются по длинной оси на 0,8 (`STACK_OVERLAP`) и стоят не дальше 6 мм (`STACK_GAP_MM`),
и при этом:

* одна из них неполна — меньше трёх сквозных горизонталей (`COMPLETE_LONG_RULES`): одна
  строка шапки, бланк без тела; либо
* графы обеих стоят на одних x (`ALIGNED_SHARE` 0,5 при допуске 1 мм); либо
* между ними лежат сирые горизонтали внутри общей ширины стопки — «мостик» бланка
  («Периодичность завоза ___»); в соседней колонке линии бланка мостиком не считаются; либо
* они стоят ближе 2,5 мм (`STACK_TOUCH_MM`): две разные таблицы вплотную не печатают.

Две ЦЕЛЫЕ таблицы в 5 мм друг от друга остаются двумя (1975/05 с.96).

Дальше общий отбор скоплений (`ruling.cluster_tables`, политика `detector.POLICY`):
размеры — «обе стороны ≥ 25 мм» ИЛИ «длинная ≥ 40, короткая ≥ 10» (широкие короткие шапки
бланков: 126×25, 130×16, 91×21 мм); не меньше двух горизонталей и одной вертикали; доля краски
в рамке не выше 0,25 (`MAX_INK_SHARE`; у таблиц 0,08–0,17, у штрихового рисунка 0,31–0,38).
Требование «сквозных линеек ≥ 2» на затравки не накладывается: оно было отсевом рисунков до
проверки, а здесь рисунок — находка со своим видом. Сквозные считаются позже и только для
таблиц (`MIN_LONG_RULES_FOR_TABLE = 2`, сквозная — линейка любой оси длиной от 0,8 стороны).

### 3. Вид объекта (`kind.py`) и surya

По линейкам затравки считаются признаки решётки (`kind.features_of`): плотность пересечений
(пересечения на пару «горизонталь × вертикаль»), выравнивание вертикалей по x и горизонталей
по y, доля сквозных горизонталей (≥ 0,8 ширины), доля высоких вертикалей (≥ 0,35 высоты).
У таблицы каждая горизонталь пересекает почти все вертикали, у блок-схемы из k коробок —
только две свои (плотность около 1/k), сквозных горизонталей нет, вертикали короткие.

**Схема** (`kind.is_diagram`): линеек ≥ 12 (`DIAGRAM_MIN_RULES`), вертикалей ≥ 6, плотность
пересечений ≤ 0,45, сквозных ≤ 0,3, меньшая сторона ≥ 30 мм; в строгом варианте ещё
высоких вертикалей ≤ 0,45 (у таблиц с многоярусной шапкой 0,76–1,0; у 15 схем из 19 не выше
0,37) и сквозных линеек любой оси ≤ 3 (бланк «Оперативная справка» 1974/04 с.75 при
редких пересечениях имеет девять сквозных). **Рисунок** (график, чертёж) — пол третьей
версии: букв в краске меньше 0,12 (`verify.FLOOR_GLYPH_OF_INK`) и заполненных ячеек
меньше 0,40 (`FLOOR_FILLED_CELLS`). Иначе — таблица.

Если есть разметка surya (`detector._layout_kind`): блок, накрывающий затравку не меньше
чем на 0,7 (`LAYOUT_COVER`) с уверенностью ≥ 0,3, решает вид. Figure/Picture — схема (или
рисунок, если букв мало); Table — таблица; Form — бланк ИЛИ россыпь коробок («Схема 1»
1970/06 с.62): вид решают линейки по нестрогому признаку схемы. Surya побеждает линейки —
это её главная польза: на CPU вид ошибается на небольших схемах из одного ряда коробок и на
схемах с длинными вертикалями.

### 4. Отсев баннеров и проверка таблицы (`verify.py`)

**Заголовок рубрики в рамке** («ПИСЬМА ЧИТАТЕЛЕЙ», рамка 60×22 мм с двумя вертикалями)
цепочки находят вместе со стеблями буквицы, и ячеек получается четыре. Отделяет высота
букв: девяностый процентиль высоты компоненты краски внутри рамки у 98 размеченных таблиц не
выше 2,54 мм, у баннеров 3,2–4,1 мм; порог 3,0 мм (`BANNER_GLYPH_P90_MM`) при высоте рамки
до 35 мм (`BANNER_MAX_HEIGHT_MM`) либо при любой высоте, если линеек не больше четырёх
(`FRAME_MAX_RULES`, заголовок статьи в рамке). Проверяется до вида: surya зовёт баннер
Figure.

**Проверка таблицы** (`verify.is_table_v3`) считается по вырезке ровно по `rule_box` и
пяти признакам: внутренние вертикали и горизонтали (середина дальше 4 мм от края,
`INNER_MARGIN_MM`), просветы между графами (столбцы без краски глифов от 1,5 мм), длина
строк, доля предсказанных пересечений с краской (`lattice`), число ячеек и доля
заполненных (по сетке `grid.grid_from_lines`), доля глифов в краске, доля внутренних рёбер
сетки, под которыми есть линейка (`edge_fill`). Правило, калиброванное на 61 размеченной
находке (0 ошибок):

* внутренних горизонталей нет и ячеек ≤ 3 → одна строка, баннер;
* букв в краске < 0,12 и заполнено ячеек < 0,40 → сетка графика или чертёж;
* ячеек ≥ 40 при решётке ≥ 0,9, рёбрах ≥ 0,45 и заполнении ≥ 0,5 → пустой бланк, таблица;
* иначе правило второй версии: нет внутренних вертикалей → рамка; одна вертикаль → нужны
  ≥ 4 ячеек и глифов ≥ 0,50; рёбер ≥ 0,70 → решётка есть; глифов ≥ 0,50 при рёбрах ≥ 0,45
  или ≥ 8 колонках; глифов ≥ 0,41 при рёбрах ≥ 0,45.

Затравка вида «таблица», не прошедшая проверку, отбрасывается — если только линейки не
говорят «россыпь коробок» (нестрогий признак схемы: тогда это схема с высокими боковыми
коробками, 1974/12 с.42) или surya не назвала её Figure (тогда рисунок).

### 5. Рост по виду (`detector.grow_table`, `grow_diagram`)

Соседи известны только теперь, поэтому рост идёт вторым проходом. Таблице преграда — любая
соседняя находка; схеме — только таблицы: две затравки одной схемы (верх с пунктирными
связями и низ) обязаны срастись, а не резать друг друга.

**Таблица** растёт в ореоле 20 мм (`HALO_MM`) и только по СВОИМ линейкам: линейка полосы,
пересекающая ребро таблицы, или фрагмент, продолжающий ребро через зазор до 3 мм
(`CONTINUATION_GAP_MM`; 4 мм уже тянули подчёркивание соседней колонки). Внутри Table-блока
surya линейка берётся и без связности (так достаётся графа, чью линейку порвал изгиб полосы);
в Text-блоки surya рост запрещён. Три прохода (`GROW_PASSES`), потолок 40 мм на сторону
(`GROW_CAP_MM`), и **абсолютное вето по чужому тексту**: если доля чужого текста в рамке
(`quality.foreign_text` — краска строк, не попадающих в просветы граф) выросла больше чем на
0,02 (`MAX_FOREIGN_GAIN`), рост отвергается, и проверка «это всё ещё таблица» его не
перебивает.

**Схема** растёт заливкой по штриховой краске (`line_art_mask`: компоненты выше 4 мм или
шире 12 мм — не буквы) с дилатацией 5 мм (`DIAGRAM_GLUE_MM`): пунктирные связи рвутся на
1–2 мм, стрелка отстоит от коробки на 1–3 мм, а до соседнего абзаца 8–12 мм. Компонента
раздутой маски, в которой лежит затравка, и есть схема; чужие таблицы из маски вырезаны.
Потолок 60 мм (`DIAGRAM_CAP_MM`) отсчитывается от затравки ВМЕСТЕ с Figure-блоком surya
(у сетевого графика 1967/05 с.66 затравка — нижняя треть схемы), рамка добирает Figure-блок
и не выходит за него дальше 10 мм (`FIGURE_SLACK_MM`). Сирые горизонтали не короче половины
ширины полосы (`PAGE_RULE_SPAN`) из маски вырезаны: линейка колонтитула в 4 мм над схемой
делала её рамку шириной с полосу (1973/07 с.66).

Кусок блок-схемы, прошедший проверку как маленькая таблица и доросший по связям до целой
схемы, получает вид заново по выросшей рамке (если surya не сказала своего слова).

### 6. Рамка по рёбрам и граница без букв (`refine.py`)

`fit_rows` **только зажимает** верх и низ рамки таблицы по крайним линейкам внутри неё
(концы линеек тоже зажаты в рамку: чужая вертикаль с центром внутри может торчать наружу).
Ни строки сверху, ни строки снизу рамка не добирает — так решил человек по второй раскладке
(см. историю, v4.1): строку «Итого» без рёбер лучше оставить снаружи, чем захватить заголовок,
подпись или номер страницы.

`push_edges` двигает стороны так, чтобы **ни одна не пересекала компоненту краски**
(`quality.glyph_components`, компоненты крупнее 3 px). Компонента, лежащая снаружи больше
чем на 0,6 (`OUTSIDE_SHARE`), — чужая: граница уходит внутрь, но не дальше крайней линейки
(за линейкой — тело таблицы). Если внутрь нельзя, решает СТРОКА компоненты
(`_line_inside_share`): полоса высотой в компоненту по всей длине стороны; если её краска
лежит внутри рамки не меньше чем на 0,7 (`LINE_INSIDE_SHARE`) — компонента своя (первая
буква строки открытой таблицы, торчащая за линейку, 1971/03 с.38), и граница уходит наружу за
ней, но не дальше 6 мм (`OWN_LIMIT_MM`, размер слова); иначе наружу только на 1,5 мм
(`SLIGHT_MM`, граница задела край буквы), а дальше — граница ставится вплотную к линейке и
чужое отрезается по ней. Иначе граница уходит наружу до чистого места, не дальше 12 мм
(`PUSH_LIMIT_MM`; столько занимают крупные буквы заголовка на линейке рамки). Положение
ищется до ЧИСТОГО места (`_settle`): один шаг внутрь на верх чужой строки ставил границу
ровно на буквы своей, и она колебалась между двумя положениями. Сторона, где чистого места
нет, остаётся на месте и считается в `push_failed`.

### 7. Слияние и дедупликация

Две находки-схемы (или рисунка), которые перекрываются или стоят ближе зазора заливки, —
одна схема, выросшая из двух затравок; «таблица» без единой внутренней горизонтали (ряд
коробок под общей линией) вплотную к схеме — её нижний ярус. Сросшаяся схема получает
границу заново через `push_edges`. Дедупликация убирает вложенные находки одного вида.

## История версий

Детектор развивался в `research/table_processing` (теперь `research/legacy/…`) с
разметкой по папкам-диагнозам: человек раскладывал оверлеи по папкам с именем дефекта,
`labels-from-folders` собирал их в `labels/detector_pages.csv` (209 полос), `compare-detector`
мерил версии на этой разметке, `check-detector` — на всём паке против таблиц FineReader.

### v1 — линейки и склейка (2 недели после старта)

Бинаризация Otsu, открытие длинным ядром 8 мм по каждой оси, компоненты связности —
отрезки; скопление — дилатация на 6 мм. Пороги: толщина как площадь/длина, ≥ 2 сквозных
горизонталей (0,8 ширины), доля краски ≤ 0,25. На десяти полосах 13 таблиц из 13.

### v2 — проверка признаками

Линейки бывают не только у таблиц: из 27 находок на полосах без таблицы в DOCX 12 были
рамками объявлений, колонтитулами, чертежами, блок-схемами. `verify.is_table` по пяти
признакам, калибровка на 61 находке: 0 ошибок. По паку добыча 229 → 249 таблиц.
Отдельно — заголовок рубрики в рамке («внутренних горизонталей нет, ячеек ≤ 3»).

### v3 — про рамку, а не про распознавание

105 оверлеев разложены по диагнозам: почти все дефекты — про рамку (режет буквы, хватает
соседний абзац, берёт половину таблицы или кусок блок-схемы). Пять правок, каждая замерена
до написания: сквозная линейка любой оси; пара размеров 40×10; тень корешка выбрасывается до
кластеризации; доращивание в ореоле 20 мм по связным рёбрам (зазор 12 мм, слабый порог
4 мм); границы прилипают к чистому просвету (≤ 3,5 мм). Две рамки у находки (`rule_box` и
`box`). Пол по буквам и пустым ячейкам и ветка пустого бланка в проверке. На 163 полосах:
найдено 60 из 62 (было 43), границ по буквам 17 (было 94). По паку: 699 полос с таблицей и у
нас, и у FineReader (было 670), ни одной потери против v2.

### v4 — связные рёбра, вид объекта, граница без разрезанных букв

59 проблемных полос v3 разобраны пошаговой печатью её конвейера. Диагноз: обрезка
пересобирала рамку из линеек всей полосы и откатывала доращённое (или расширяла на бланк
в соседней колонке); доращивание клеило любую линейку в 12 мм — колонтитул (есть на трети
полос пака), подчёркивание, линии бланка; прямое ядро 8 мм теряло загнутый конец линейки;
прилипание считало сторону чистой при < 1 % краски и не могло дальше 3,5 мм; ядро кляксы
проходило как вертикаль. Семь правок: цепочки фрагментов 3 мм; клякса по соседству; связные
ядра вместо дилатации; рост таблицы только по своим рёбрам с абсолютным вето; строки по
просветам граф; граница не пересекает компонент; вид объекта (таблица/схема/рисунок) и рост
схемы заливкой с дилатацией. Surya layout — опционально, с кэшем на полосу. На 190 полосах:
ложных таблиц 34 → 22, пересечённых букв 210 → 1, целых блок-схем 0 → 13 из 13, вид верен
86 из 90. По паку: 897 таблиц, 188 схем, 55 рисунков; 31 «потеря» против v3 — 27 из них
теперь схемы и рисунки, которые v3 звала таблицами. Заголовок рубрики в рамке — второй раз:
по высоте букв (34 из 42 новых срабатываний).

### v4.1 — рамка строго по рёбрам

Человек отсмотрел ~40 % оверлеев v4 и разложил 24 полосы: главная беда — чужой текст в
рамке. Догадка «первичную область даёт surya, потому и неточна» не подтвердилась: Table-блок
surya ни на одной из 17 полос не добавил росту ни миллиметра. Чужой текст добавляли два
последующих шага — «строки без вертикалей» для «Итого» (полоса текста принималась строкой,
если не задевала просветов граф; замер по 209 полосам: 41 из 48 таких расширений — заголовок
«Таблица N», подпись, номер страницы в одной графе) и выталкивание, отодвигавшее границу ещё
дальше ради уже прихваченной строки. Оговорка «текст хотя бы в двух графах» не спасала
(последняя строка абзаца и подпись на одной высоте, 1968/06 с.38). Решение человека: строку
«Итого» без рёбер лучше оставить снаружи, чем захватывать чужое. Рамка теперь строго по
крайним линейкам, расширять её вправе только выталкивание — на доли миллиметра, если задет
край буквы; чужая компонента за линейкой отрезается по линейке. Заодно: стебель буквы не
пришивается через широкий зазор; потолок роста схемы от Figure-блока; схема и рисунок одного
объекта сращиваются; заголовок статьи в рамке отбрасывается при любой высоте; Form с
россыпью коробок — схема. На всех 24 полосах рамки таблиц совпали с линейками (≤ 1 мм).

### v4.2 — два остатка

1971/03 с.38: первая буква «М» открытой таблицы торчит за линейку на 73 % и считалась чужой
— теперь компонента судится по своей строке (`LINE_INSIDE_SHARE`, `OWN_LIMIT_MM`).
1973/07 с.66: линейка колонтитула в 4 мм над схемой прилипала к заливке и тянула рамку на
всю полосу — сирые горизонтали во всю полосу вырезаны из штриховой краски, Figure-блок
surya служит потолку с запасом 10 мм. На 209 размеченных полосах правки изменили рамку у
пяти, все — улучшения. Прогон по сырым TIFF «Готовое» с кэшем surya по ним же
(`reports/прогон детектора таблиц v.4.2`): 901 таблица, 173 схемы, 49 рисунков; полос с
таблицей и у нас, и у FineReader 696 (у v3 694); потеряно против v3 25 полос, новых 6.
Человек отсмотрел оверлеи и принял; этот прогон и лёг в `rect_regions`.

### v4.4 — открытые таблицы, мост, таблица в две графы (`TABLES_VERSION = 3`)

Три правки, все — по пикселям и линейкам, без surya.
* **Открытая таблица** (`rules.extend_open_bodies`): шапка в линейках, в теле — только вертикали
  граф, разорванные подзаголовками разделов. Ядро тянется вниз по кускам вертикалей на своих
  внутренних графах (≥ 2 графы одновременно, зазор ≤ `OPEN_BODY_GAP_MM`), а также забирает
  следующий раздел, ставший своим ядром (двойная линейка над «Итого»), если его вертикали стоят на
  тех же графах и у него нет своей верхней линейки во всю ширину — иначе это «Таблица 2» под
  «Таблицей 1» (первая попытка без этого условия склеила 8 пар таблиц). 1970/12 с.87, 1975/02 с.75,
  1966/02 с.55, 1973/08 с.20 (вместе с итоговой строкой), 1972/11 с.36.
* **Мост** (`rules.split_bridged`): ядро режется по длинной линейке, если без неё оно распадается на
  две и больше ПОЛНЫХ таблиц (≥ 3 сквозных) одна над другой, которые правило стопок не слило бы.
  Первая попытка без условия полноты резала стрелки блок-схем (схема 1970/11 с.82 пропадала).
  1967/06 с.48 теперь две таблицы вместо одной. 1969/02 не лечится: нижний объект — рисунок, не
  таблица, а связь в заострённой копии не через мост.
* **Таблица в две графы** (`verify.is_two_column_table`): одна внутренняя вертикаль, но замкнутая
  рамка или шапка (верхняя линейка + отбивка шапки), разделитель на ≥ 0,9 высоты тела, текст по обе
  стороны и ≥ 3 строк. Проверяется до правила баннера и до «колонтитула». 1966/06 с.85, 1974/01
  с.21, 1967/12.

Весь пак (заострённые копии): таблиц 909 → 914, схем 168 → 168, рисунков 56 → 57; изменения на 10
полосах, все отсмотрены — верные. `compare-detector`: 83 → 84 из 84, «ложных» 23 → 23; эталон
`geometry_regression regress` — без изменений; тесты потребителей — 661 проходят. Под блоками
surya Table отказов проверки 17 (v4.2) → 9 (v4.3) → 3.

## Что пробовали и отвергли

* **Дилатация 6 мм как способ собрать скопление** (v1–v3). Клеила к таблице всё в шести
  миллиметрах: подчёркивание соседней колонки, линии бланка в другой колонке, линейку
  колонтитула. Заменена связными ядрами; дилатация осталась только там, где была права, —
  в правиле про стопки (шапка над телом), и то с оговорками.
* **Открытие ядром 8 мм** для поиска линеек. Отрезало загнутый конец линейки на
  искривлённой полосе (1975/07 с.42) — последняя графа оставалась снаружи. Заменено
  фрагментами 3 мм с цепочками. Зазор цепочки 2 мм проверялся и не годится: 625 линеек из
  7600 оставались без пары.
* **Толщина как признак кляксы.** 279 из 4301 линеек настоящих таблиц тоньше 1,5 px, а
  кляксы бывают тонкими. Заменена соседством (доля краски в полосах по обе стороны).
* **Обрезка по полосам без вертикалей** (`trim_ruleless`, v3). Пересобирала рамку из линеек
  всей полосы и молча откатывала всё, что нашло доращивание; умела и расширять на бланк в
  соседней колонке (1974/06 с.97: с 65 до 131 мм). Оставлена в legacy.
* **Доращивание «клей всё в 12 мм» с откатом «verify ИЛИ прирост чужого ≤ 0,02»** (v3).
  Пропускало рост с чужим текстом 0 → 0,74: проверка по-прежнему говорила «таблица».
  Заменено ростом только по продолжениям и пересечениям своих рёбер с абсолютным вето.
* **Разделитель «не расти через полосу сплошного текста»** (v3). У зазора до продолжения
  своей таблицы максимальная доля строки 0,53 по медиане, у зазора до соседней таблицы 0,40 —
  распределения перекрываются полностью.
* **Прилипание границы к просвету по доле краски < 1 %** (`snap_edges`, v3). Один процент —
  это три срезанные первые буквы на высокой таблице (1973/12 с.86); предел 3,5 мм не пускал
  за «Продолжение» на линейке рамки. Заменено выталкиванием по компонентам краски.
* **Строки без вертикалей по просветам граф** («Итого», v4.0). 41 из 48 расширений
  оказались заголовком, подписью или номером страницы. Промежуточная оговорка «текст хотя бы
  в двух графах» тоже не спасала. Убрано полностью по решению человека.
* **Выталкивание чужой компоненты наружу** (v4.0). Граница уходила за прихваченную чужую
  строку целиком. Теперь чужое отрезается по линейке (`SLIGHT_MM`), своё — по строке.
* **Поглощение шапки без вертикалей в ядро** (сирые горизонтали в 5 мм над телом, 1972/10
  с.36). Тянуло за собой линейку колонтитула у верха полосы; вычеркнуто как неэффективное,
  случай остаётся неумением.
* **Один шаг внутрь при выталкивании.** Ставил границу на буквы своей строки, и граница
  колебалась между двумя положениями (1973/12 с.85). Заменено поиском до чистого места.
* **Surya как источник границ.** Границы ±1–2 мм, 10 из 38 «не таблиц» помечены Table,
  бланк целиком бывает одним Form без таблицы внутри. Осталась источником вида и
  подсказкой протяжённости (Table-блок разрешает рост, Text — запрещает, Figure — потолок).
* **Потолок роста схемы от затравки** (v4.0). У сетевого графика затравка — нижняя треть
  схемы, и потолок 60 мм резал верх, который surya уже показала. Потолок — от затравки
  вместе с Figure-блоком.
* **Отдельный детектор блок-схем по пунктирным связям.** Не понадобился: заливка штриховой
  краски с дилатацией 5 мм берёт и пунктирные связи (разрывы 1–2 мм).
* **Правило баннера «внутренних горизонталей нет, ячеек ≤ 3»** (v3) против цепочек не
  работает: они находят и рамку, и стебли буквицы, ячеек четыре. Заменено высотой букв.
* **Порог «правдоподобной решётки» на 0,006 ниже** ради 1967/03 с.9 — подгонка под один
  случай, не сделано. Полоса остаётся неумением.

* **Сетка по осям на изогнутой таблице** (`grid_from_lines` по `find_lines` 8 мм) — обрывки
  наклонной линейки на разной высоте дают лишние строки (1968/03 с.4: 6 × 3 вместо 4 × 3). Для
  разбора геометрии заменена сеткой по кривым; конвейер пока на прежней.
* **Выбор сглаживания трассы по GCV** — идёт за лесенкой пикселей: остаток 0,03 px, наклон ровной
  линейки скачет ±25°. **Многочлен степени 3–5** — S-изгиб 108 мм: 3,9 / 1,9 px ошибки, раскачка на
  концах. **`make_splrep`** без естественных концов — наклон у концов врёт на 3–23°.
* **Середина бинарного пробега как отсчёт трассы** — лесенка ±0,5 px, ложная волна наклона ±2°;
  заменена центром тяжести тёмности серого. **Порог остатка 0,35 px** — 158 из 525 длинных линеек
  уходили на полосу 1,5 мм и повторяли шум (волна соседних линеек коррелирует лишь на 0,5–0,7);
  при 0,5 px — 92, излом 1968/03 прослежен.
* **Опора разделителя «оба конца упираются»** — теряла линейку под «Годы» 1967/10 с.33 (не доходит
  до вертикали 6 мм); **«касается хоть где-то» для коротких** — пропускала черты дробей 6 мм в узких
  строках 1973/08 с.62 (зазор до линеек 1–2 мм). **Своя граница на каждый кусок колонки** — колонка,
  прерванная строками, давала 3–5 границ в 2–9 px друг от друга (1973/08: 17 × 26).

* **Опора разделителя «касается любой трассы»** — рамка штампа опиралась сама на себя, штрихи букв
  заголовка — друг на друга (обложки 1971/06, 1970/11: границы по буквам «ИЮНЬ», по штампу); заменено
  связной сетью от длинных линеек и порогом толщины. **Толщина 2 медианы** — пропускала штамп (5 px
  против 3 px); порог 1,5.

**Чего детектор не умеет.** Шапка бланка без вертикалей в 5 мм над телом (1972/10 с.36);
таблица в одну строку (1975/01 с.43) отвергается проверкой; дуги, соединяющие две схемы на
развороте (1967/10 с.74), режутся границей; на CPU без surya вид «схема» не ставится
небольшим схемам (< 30 мм по меньшей стороне) и схемам с длинными вертикалями; чертёж с
подписями бывает назван схемой (1973/04 с.55). Правая часть таблицы 1975/07 с.42 остаётся
снаружи: линейки крайних граф продавлены настолько, что их не находит и фрагмент 3 мм.

## Как проверять

* Трассы и сетка по кривым: `test_traces.py` (изогнутая по S синтетика с истинными кривыми —
  положение, наклон, хорда, JSON, буква на линейке, пунктир и отточие), `test_curved_grid.py`
  (объединения, двойная линейка, волнистая — не двойная, графы без внешних линеек, штамп и жирные
  буквы — не границы, черта у рамки — не графа, область ячейки — ровно многоугольник, внутренность без
  краски линеек, настоящая `example_table_curved.jpg` — 10 ячеек), `test_rules_refactor.py`
  (вынос `fragment_layers` / `chain_groups` не меняет выхода детектора). Стенд на паке —
  `run_scripts/table_traces/run_eval.sh`, оверлеи «по осям | по кривым» и CSV — в
  `reports/curved_table_grid/`.
* Тесты на синтетике: `uv run pytest tests/ocr_utils/page_layout/tables` — каждая
  проверка отвечает одной поломке прежних версий (изогнутая линейка, клякса, колонтитул и
  подчёркивание, «Итого» снаружи, граница без букв, коробки схемы с пунктиром, буква за
  линейкой, колонтитул над схемой) плюс перевод в регионы базы.
* Стенд исследований в `research/legacy/table_processing` берёт детектор отсюда:
  `compare-detector --versions v3,v4 --layout-dir <кэш surya>` мерит его на 209 размеченных
  полосах по классам диагнозов, `check-detector --layout-dir` — по всему паку против таблиц
  FineReader с оверлеями (`run_scripts/table_processing/run_check_detector_v42_source.sh`).
  Оверлеи прогонов лежат в `reports/прогон детектора таблиц v.4.2/`,
  `reports/сверка детектора v4/`, `reports/детектор v4/` (папки картинок в `.gitignore`).
* В конвейере: `python -m ocr_utils.scan_markup detect --layout-cache <кэш> …` пишет
  регионы, `--debug-dir` рисует их на оверлеях своими цветами (тёмно-синий — таблица,
  коричневый — схема), как метки в CVAT.
