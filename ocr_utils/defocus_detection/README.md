# defocus_detection — поиск расфокусированных кадров в папке

Инструмент **скрининга**: сканирует папку со сканами газетных полос и выводит **два
отчёта**, отсортированных от худшего к лучшему. Задача — вытащить наверх те 3–5 % кадров,
которые стоит переснять.

1. **Общее качество фокуса** — насколько плох кадр целиком.
2. **Зональный расфокус** — насколько сильно резкость проваливается внутри кадра.
   Кадр может быть хорош в среднем и всё равно требовать пересъёмки, если поплыла его
   часть; в первый отчёт такой кадр по построению не попадёт.

Это не классификатор: он ранжирует кандидатов, финальное решение — за человеком.
Второй отчёт особенно: у него заметная доля ложных срабатываний (см. «Валидация»).

---

## Быстрый старт

```bash
# все файлы папки с метрикой, худшие сверху
uv run python -m ocr_utils.defocus_detection "/путь/к/выпуску"

# типовой режим «что переснять»: по 5 % худших в каждом отчёте
uv run python -m ocr_utils.defocus_detection "/путь/к/выпуску" --worst-percent 5 --zonal-percent 5

# ровно 15 худших по общему фокусу и 10 по зональному
uv run python -m ocr_utils.defocus_detection "/путь/к/выпуску" --worst-count 15 --zonal-count 10

# только первый отчёт
uv run python -m ocr_utils.defocus_detection "/путь/к/выпуску" -p 5 --no-zonal

# другой алгоритм + отчёты
uv run python -m ocr_utils.defocus_detection "/путь" -a combo \
    --md-report defocus.md --csv defocus.csv

# замер ТОЛЬКО по областям строк текста (surya-ocr): «читается ли мелкий текст»,
# зональный расфокус — по сетке 3x3. Нужна видеокарта, см. раздел ниже.
uv run python -m ocr_utils.defocus_detection "/путь" --use-surya-lines \
    --debug-dir defocus_debug --csv defocus.csv

# все опции и список алгоритмов
uv run python -m ocr_utils.defocus_detection --help
```

Принимает `.RAF`, `.tif`, `.tiff`, `.png`, `.jpg`, `.jpeg`. Из RAF берётся встроенное
JPEG-превью 4416×2944: полноразмерный RAW распаковывается ~8 с против ~0,2 с у превью,
а разрешения превью хватает (см. «Валидация»). Папка обходится нерекурсивно, `--recursive`
включает обход вложенных.

> **Запускайте по одному выпуску.** Пороги здесь не абсолютные: файлы ранжируются
> относительно друг друга внутри переданной выборки.

**Нагрузка на машину.** Прогон по выпуску идёт минутами, и всё это время компьютером надо
продолжать пользоваться, поэтому по умолчанию: процессов берётся на `--reserve-cores`
меньше, чем ядер (по умолчанию на два); каждому воркеру понижается приоритет (nice +10);
внутренняя многопоточность OpenCV и BLAS в воркерах отключается. Последнее важнее всего:
без него каждый из полутора десятков процессов вправе развернуть по потоку на ядро, и
машина оказывается занята целиком, считая при этом не быстрее. Замерено на 16 ядрах:
14 воркеров по одному потоку каждый, около 1000 % CPU из 1600 %.

## Как читать вывод

```
 #  балл (1/σ)  σ края, px  файл
--  ----------  ----------  -------------------------------
 1       1.544      0.6478  DSCF0180_defocus_ultralight.RAF
 2       1.563      0.6400  DSCF0311_defocus_light.RAF
 3       1.570      0.6370  DSCF0320_defocus_light.RAF
 4       1.590      0.6289  DSCF0120.RAF
...
Показано 16 из 317 файлов; сортировка — от худшего фокуса к лучшему.
```

- **балл** — качество фокуса, **больше = резче**; сортировка по возрастанию.
  В режиме `combo` это средний нормированный ранг в [0, 1] (0 — самый мягкий файл выборки).
- **вторая колонка** — тот же балл в естественных единицах метрики: для `edge_width` это
  ширина края σ в пикселях, меньше = резче. Читать её как «физическое размытие» нельзя,
  величина относительная (оценщик занижает σ на плотном тексте — см. отчёт о валидации).
  В режиме `combo` вместо неё показываются баллы отдельных метрик.

Второй отчёт выглядит так:

```
 #  перепад  σ резч.  σ мягч.                          где мягче  файл
--  -------  -------  -------  ---------------------------------  -------------------------------
 1     +20%    0.456    0.545          низ (rows 11/12, резче 6)  DSCF0196_defocus_light.RAF
 2     +14%    0.491    0.561  правый верхний угол (anti 9/25, резче 16)  DSCF0132.RAF
```

- **перепад** — на сколько процентов шире штрих в самой мягкой полосе кадра, чем в самой
  резкой. Это и есть мера «перекоса»; сортировка по её убыванию.
- **где мягче** — куда пришёлся провал: сторона или угол кадра, а в скобках направление
  профиля, номер мягкой полосы из общего числа и номер самой резкой. Полезно для понимания
  механики: одна и та же сторона из раза в раз — значит завалена плоскость съёмки.

Отбор в каждый отчёт задаётся своими опциями: `--worst-percent` / `--worst-count` для
первого, `--zonal-percent` / `--zonal-count` для второго. Без них печатаются все файлы.

`--md-report` пишет обе таблицы в markdown со ссылками на файлы. `--csv` пишет **все**
файлы папки со всеми метриками и зональными колонками: это рабочий материал для
калибровки, а не для чтения.

`--link-dir` раскладывает отобранные кадры **симлинками** (подпапки `overall/` и
`zonal/`) — эту папку открывают просмотрщиком и листают стрелками в порядке отчёта.
Имя симлинка — `<позиция>_<метрика>_<исходное имя>`:

```
overall/  01_0.6905_0020_1.RAF   02_0.7135_1200_1.RAF   …   47_0.7687_1320_2.RAF
zonal/    01_+41%_1240_1.RAF     02_+28%_0020_1.RAF     …
```

Позиция идёт первой и с ведущими нулями (ширина — по длине списка), чтобы алфавитный
порядок в просмотрщике совпал с порядком отчёта. Метрика печатается той же функцией, что
и в таблице, так что число в имени файла всегда совпадает с числом в отчёте: для первого
отчёта это балл алгоритма, для второго — перепад в процентах.

Опция существует потому, что на ссылки в markdown полагаться нельзя:
PyCharm и Chrome рендерят превью в Chromium, а он **запрещает переход из документа на
`file://`** — клик молча не срабатывает, и обойти это со стороны разметки невозможно.
Повторный прогон чистит свои прежние симлинки; если в папке окажется обычный файл,
инструмент остановится с ошибкой, ничего не удалив.

## Абсолютные пороги и теги тяжести (`--tag-preset`)

`--worst-percent` отвечает на вопрос «кто в этой папке хуже остальных». Спрашивают же
обычно другое — «что переснимать», и это разные вопросы: доля брака от съёмки к съёмке
гуляет от 0 % до 10 %, так что фиксированные 15 % то гонят на просмотр полсотни заведомо
хороших кадров, то обрезают список там, где брак ещё не кончился.

```bash
# что объективно плохо + привычные худшие 10 % — оба списка за один прогон
python -m ocr_utils.defocus_detection ПАПКА --tag-preset dom-si --worst-percent 10

# только список по порогам
python -m ocr_utils.defocus_detection ПАПКА --tag-preset dom-si --tagged-only

# какие пресеты есть, с порогами и происхождением (папку указывать не надо)
python -m ocr_utils.defocus_detection --tag-preset list
```

Кадр получает тег `defocus_heavy` / `defocus_medium` / `defocus_light` /
`defocus_ultralight` — от тяжёлого расфокуса к едва заметному. Тег виден колонкой во всех
отчётах и в CSV, попадает в имя подпапки `--link-dir` и в список `--retake-list`.

**Четвёртый уровень читается иначе, чем три первых.** `ultralight` — это «посмотреть», а
не «переснять»: на отсмотренной глазами и признанной чистой подшивке СИ 1988/01-03 он
метит 9 кадров из 304, то есть его список заведомо содержит хорошие кадры. Так и задумано,
и поднимать порог выше нельзя — уже на 3.08 в том же списке оказывается 112 кадров из 304.
Разметка «Экономической газеты» 1982 показала, почему уровень всё же нужен: из 11
помеченных вручную кадров три попадают именно в эту полосу и без неё остались бы
безымянными. В `--tag-thresholds` уровень необязателен: без него полоса пуста.

**Пресет задаёт не только числа.** Порог — это точка на шкале КОНКРЕТНОЙ метрики при
КОНКРЕТНОЙ агрегации, поэтому `--tag-preset` сам подставляет `--algorithm` и
`--aggregate`, под которые откалиброван. Заданное явно и не совпадающее — ошибка, а не
повод посчитать не то. Свои пороги задаются отдельно:
`--tag-thresholds heavy=2.90,medium=2.94,light=2.98` (по шкале выбранного алгоритма).

**Почему абсолютный порог вообще возможен.** Это измерено, а не предположено: на десяти
съёмочных сессиях «Социалистической индустрии» общий порог 2.970 по `dom` дал ровно ту же
полноту, что и порог, настроенный по каждой сессии отдельно, — совпадение до процента во
всех десяти. Причина в устройстве метрики: DOM есть отношение двух сумм, линейных по
контрасту, поэтому экспозиция в нём сокращается. У контраст-зависимых метрик
(`laplacian`, `hf_mid`, `moire`) такого свойства нет, и вешать на них абсолютный порог
нельзя. Разбор — в `defocus_validation_si_report.md`, раздел 5.

**Что абсолютным НЕ становится.** Уровень размытия — да, чувствительность к чужому
вкусу — нет. Полнота по сессиям всё равно гуляет от 0 до 100 %, потому что в разные дни
брак помечался разной тяжести. Тег отвечает «насколько размыт этот кадр», а не
«забраковали бы вы его в тот день».

## Алгоритмы (`--algorithm`)

| имя | что меряет | AUC¹ | зависит от кол-ва текста | от кегля | от ISO |
|---|---|--:|:--:|:--:|:--:|
| `edge_width` **(по умолчанию)** | субпиксельную ширину края штриха | **0.901** | **нет** | **нет** | **нет** |
| `combo` | средний ранг `edge_width` + `reblur` | 0.877 | нет | нет | нет |
| `laplacian` | дисперсию лапласиана (наивная база) | 0.871 | **да** | **да** | **да** |
| `moire` | муар типографского растра | 0.860 | нет (нормирован) | слабо | слабо |
| `reblur` | сколько кадр теряет от повторного размытия | 0.832 | нет | нет | нет |
| `hf_mid` | долю ВЧ-энергии спектра | 0.798 | нет | **да** | слабо |

¹ качество ранжирования на размеченной папке 1979 года (317 файлов, 15 размеченных);
подробности и оговорки — в `defocus_detection_validation_report.md`. Разница меньше
0.03 на такой выборке незначима.

### `edge_width` — ширина края (Marziliano / JNB / CPBD)

Опорный метод, и именно он прямо отвечает на вопрос «насколько расплылись штрихи».
Строки и столбцы кадра режутся на монотонные участки между локальными экстремумами
яркости; каждый такой участок — один край. Ширина края считается не в целых пикселях,
а как СКО профиля градиента внутри участка:

```
σ² = Σ (k − центр)² · |ΔI_k| / Σ |ΔI_k| − 1/12
```

Для ступеньки, размытой гауссианой σ, это в точности даёт σ — субпиксельно (вычитаемая
1/12 — дисперсия пиксельной апертуры). Это тот же принцип, что в slanted-edge измерении
MTF по ISO 12233, только вместо специальной миры используются случайные края текста.

Почему метод подходит под все три оговорки из постановки задачи:

- **Разное заполнение текстом.** Плотность текста меняет ЧИСЛО замеров, а не их среднее:
  полоса в одну колонку и полоса-простыня при одинаковой оптике дают одну и ту же
  среднюю ширину края.
- **Крупные заголовки.** У большой буквы переходов мало, но каждый переход такой же
  крутой — ширина края та же. Ломаются здесь именно энергетические метрики, которые
  считают суммарную энергию, а не геометрию.
- **Разные ISO и освещение.** Ширина края — геометрия профиля, а не его амплитуда.
  Порог отбора перепадов берётся относительно контраста самого кадра (доля от p95
  амплитуд), поэтому уезжает вместе с экспозицией.

Литература: Marziliano et al. (ICIP 2002), Ferzli & Karam JNB (IEEE TIP 2009),
Narvekar & Karam CPBD (IEEE TIP 2011).

### `reblur` — метрика Crete «The Blur Effect»

Кадр размывается ещё раз, и меряется, какую долю перепадов между соседними пикселями
он при этом потерял. Резкому терять есть что, уже размытому — нечего. Величина
нормирована на собственную энергию перепадов кадра, поэтому не зависит ни от контента,
ни от контраста, и не требует ни одного порога. Второй голос в `combo`.

Ограничение: меряет относительную мягкость, а не абсолютную ширину штриха, поэтому на
очень мелком тексте ближе к насыщению, чем `edge_width`.

### `moire` — муар типографского растра

Газетный растр — это готовая мира, отпечатанная прямо на странице. Уменьшение кадра
методом NEAREST даёт на резком растре сильный алиасинг, на размытом — нет; меряем
`std(NEAREST − AREA) / std(AREA)`. Знаменатель убирает зависимость от количества краски
(корреляция с количеством контента падает с +0.5 до −0.1 — замерено в
`defocus_moire_improvement_plan.md` в корне репозитория).

Ограничение: требует наличия растра. Обложки, картонные переплёты, рукописные этикетки
метрика ранжирует бессмысленно.

### `hf_mid` — доля ВЧ-энергии спектра

`E(высокие частоты) / E(средние частоты)` по тайлам. Расфокус обрушивает ВЧ (тонкие
штрихи), оставляя СЧ («рисунок» полосы — шаг строк и букв), который и служит
нормировкой. Метод валидирован в этом репозитории на зональных расфокусах
(`detect_zonal_defocus.py`).

Ограничение, подтверждённое тестом: **к кеглю он не устойчив**. Крупный шрифт сдвигает
вниз обе полосы спектра сразу, и отношение падает без всякого расфокуса. Поэтому в
`combo` по умолчанию он не входит.

### `laplacian` — наивная база

Дисперсия лапласиана из всех туториалов. Оставлена **не потому, что хороша**, а чтобы
было с чем сравнивать: она честно воспроизводит все три проблемы из постановки задачи.
Тест `test_known_metrics_are_fooled_by_font_size` фиксирует этот дефект намеренно.

## Как ищется зональный расфокус

Кадр режется на сетку вдвое мельче основной (по 18 тайлов в ширину), по каждому тайлу
считается ширина края σ, затем строится **профиль по полосам** — и метрика — относительный
перепад между самой резкой и самой мягкой полосой.

### Направление профиля (`--zonal-axis`)

Провал приходится куда попало: снимают с рук, и плоскость съёмки заваливается каждый раз
по-своему. В одной подшивке встречается и мягкий верх, и мягкий бок, и один заваленный
угол. Поэтому полоса — это не ряд сетки, а **бин проекции тайлов на произвольное
направление**, и таких направлений четыре:

| значение | полосы | что ловит |
|---|---|---|
| `rows` | горизонтальные | мягкий верх или низ |
| `cols` | вертикальные | мягкий левый или правый край |
| `diag` | ⟂ главной диагонали | левый верхний и правый нижний **углы** |
| `anti` | ⟂ побочной диагонали | правый верхний и левый нижний углы |
| `all` **(по умолчанию)** | все четыре | берётся худшее |

Диагонали нужны именно ради углов. Завал угла размазывается по всей длине и
горизонтальной, и вертикальной полосы; на синтетике мягкий правый верхний угол даёт
по `anti` перепад +34 %, а по обеим осям сетки — всего +17…20 %, то есть кадр без
диагоналей остался бы в середине списка (тест `test_diagonal_direction_earns_its_place`).

**Где мягче** называется не по победившему направлению, а по смещению самих мягких
тайлов. Направления сильно коррелированы: крайние полосы диагонали — это те же правые
углы, что и крайние полосы `cols`, и на мягком правом крае `cols` даёт +38.3 %, а `diag`
+38.0 % — победитель скачет от кадра к кадру. Поэтому зона определяется отдельно: берётся
центр тяжести десяти процентов самых мягких тайлов и **вычитается центр тяжести всего
текста** (у ровного кадра пятно само по себе смещено от геометрического центра — текст
на полосе расположен несимметрично). Смещение больше 0.11 доли кадра по оси и даёт
«верх», «право», «правый нижний угол» и так далее.

### Отбор тайлов и полос

1. **В профиль идут только однородно набранные тайлы.** σ зависит не только от фокуса,
   но и от того, чем набран кусок полосы: узкая колонка мелким шрифтом, жирный курсивный
   лозунг и полутоновое фото дают большую σ и при идеальном фокусе. Поэтому тайл проходит,
   только если у него И число краёв, И средняя длина штриха лежат в коридорах перцентилей
   этого же кадра, И доля белой бумаги не ниже 0.18 (последнее отсекает фотографии —
   у них фона нет вовсе, а у самой плотной полосы его пятая часть).

2. **Сглаживание профиля и разнос полос — в долях кадра.** Оптический завал это плавный
   градиент через полкадра, а не скачок между соседями, поэтому профиль сглаживается, а
   самая резкая и самая мягкая полосы обязаны отстоять друг от друга на четверть кадра.
   Обе величины задаются долей от числа полос. Раньше они были прибиты к числу 3, что
   молча означало «четверть кадра» на альбомном превью 4416×2944 с его двенадцатью
   полосами — и всего одну девятую кадра на портретном 2944×4416, где полос двадцать
   восемь, то есть на портретных сканах метрика срабатывала на локальном шуме. На исходной
   альбомной сетке новые доли дают ровно прежние 3 полосы, так что калибровка 1979 года
   сохранена.

3. **Короткой полосе — пропорциональный порог.** Полоса участвует, если в ней набралось
   4 однородных тайла, но у диагональных направлений крайние полосы состоят из двух-трёх
   тайлов по построению — требовать от них четыре значит выбросить сам угол. Поэтому от
   короткой полосы требуется половина того, что в ней вообще есть, но не меньше двух.

### Шум по направлениям

Направления не равноценны по шуму, и это надо знать, читая отчёт. Горизонтальная полоса
пересекает все колонки разворота и усредняет вёрстку; вертикальная целиком лежит внутри
одной колонки и наследует её кегль. Именно поэтому в старой версии инструмента столбцовый
профиль был признан бесполезным: в топ стабильно лезли кадры из-за узкой колонки другим
шрифтом у правого поля. Фильтры однородности снимают этот перекос лишь частично — это
цена за возможность вообще увидеть мягкий бок.

Кроме того, `all` берёт максимум по четырём коррелированным величинам, а максимум смещён
вверх и на ровном кадре. На синтетике смещение мало (ровный кадр: +0.5 % по одному
направлению против +1.1 % по максимуму из четырёх), но на реальном материале с живой
вёрсткой оно больше.

Практический вывод: **если известно, что завал в выпуске всегда одинаковый — задайте одно
направление**, список тогда чище. `--zonal-axis all` нужен, когда заранее неизвестно, куда
поплывёт. Перепад по каждому направлению отдельно пишется в CSV колонками
`zonal_drop_rows`, `zonal_drop_cols`, `zonal_drop_diag`, `zonal_drop_anti` — по ним видно,
систематический это завал плоскости съёмки или разовый шум вёрстки.

### Чего этот отчёт по-прежнему не умеет

Фильтр однородности отбирает тайлы по числу краёв и по длине штриха, а обе величины сами
зависят от размытия: у сильно расфокусированного тайла краёв меньше, а штрих длиннее, и
он вылетает из коридоров. То есть **самые мягкие тайлы зоны в профиль не попадают**, и
перепад занижен — на синтетике с сильным размытием угла в профиль не проходит ни один
тайл из самого угла. Расширение коридоров это чинит (перепад на настоящих зонах растёт
втрое), но ломает главный защитный случай: смена кегля в трети полосы начинает давать
+29 % вместо +4 %, то есть ровно то ложное срабатывание, ради борьбы с которым коридоры
и заведены. Поэтому коридоры оставлены узкими, а зона детектируется по своей более мягкой
периферии. Для скрининга этого достаточно (запас над ложными срабатываниями семикратный),
для измерения силы расфокуса — нет.

## Как считается балл файла

1. Кадр режется на сетку в девять тайлов по ширине — на превью RAF это ~490 px, то есть
   примерно газетная колонка на треть высоты полосы. Сетка задаётся числом тайлов, а не
   пикселями, чтобы на кадрах другого разрешения тайл покрывал ту же ДОЛЮ полосы;
   явный размер можно задать через `--tile-size`.
2. Тайлы без краски отсекаются: из кадра вычитается сильно размытая копия (уходит
   неравномерность освещения), берётся RMS остатка, порог — доля от 75-го процентиля
   **этого же кадра**. Относительный порог не зависит ни от экспозиции, ни от того,
   насколько плотно набрана полоса. На боевой крупной сетке этот шаг обычно ничего не
   отсекает (тайл размером в колонку почти всегда чем-то занят) — он начинает работать
   при мелком `--tile-size` и на кадрах с большими пустыми полями.
3. Метрика считается по каждому печатному тайлу и сводится в балл файла — по умолчанию
   как резкость **самых мягких 20 % тайлов** (`--aggregate worst --quantile 0.8`).

Про пункт 3 подробнее — это главное решение здесь, и оно важнее выбора самого алгоритма
(AUC 0.90 против 0.81 у того же `edge_width` при другой агрегации). Проверено на
размеченной папке:

- **медиана по тайлам** — заложница вёрстки: тайлы с крупным заголовком, полутоновым фото
  или широким полем дают низкую резкость и при идеальном фокусе;
- **самый худший тайл** — это шум и артефакты вёрстки, AUC проваливается до 0.59–0.81;
- **самые резкие тайлы** («есть ли на полосе хоть один участок чёткого мелкого текста»)
  — правдоподобная гипотеза, которая на данных не подтвердилась: AUC 0.81 против 0.90.
  Реальные промахи фокуса при съёмке с рук почти всегда неравномерны по кадру, и видно их
  по мягкому краю распределения, а не по резкому. Режим оставлен как `--aggregate best`.

В режиме `combo` баллы отдельных метрик переводятся в нормированные ранги [0, 1] и
усредняются. Именно ранги, а не значения: шкалы метрик несопоставимы (пиксели, доли
энергии, [0,1]-мера), а порядок файлов сравним всегда.

## Валидация

Прогон по размеченной папке `…/ЭГ/в работе/1979/7-12 дофотать лёгкие расфокусы/` —
317 файлов RAF, из них 15 помечены вручную суффиксами `_defocus_light` (4 шт.) и

(σ от 0.357 до 0.648 px по всей папке).

```
в худших 5 % (16 файлов):   6 из 15 размеченных
в худших 10 % (32 файла):   9 из 15
медианный ранг размеченного файла: 24 / 317 (у неразмеченных — 166)
```

Скорость: 317 файлов RAF за 2 мин 38 с на 16 процессах.

Полные цифры, таблицы подбора параметров и разбор пропусков — в

### Зональный отчёт

Проверить его так же строго не на чем: подтверждённый зональный случай в папке ровно
один — `DSCF0196_defocus_light`, разобранный отдельно (§ 8 отчёта о валидации). На нём
детектор даёт **1-е место из 299 с перепадом +20 % при медиане по папке около +5 %** —
второй в списке отстаёт вдвое. Ещё три размеченных файла попадают в верхние 15.

Размеченного бокового и углового случая в этой папке нет вовсе, поэтому направления
`cols`, `diag` и `anti` проверены только на синтетике (`tests/.../test_zonal.py`:
четыре угла, мягкий бок, мягкий верх и низ — против ровного кадра, смены кегля,
полутонового фото и равномерно промазанного кадра). На реальном материале их ложные
срабатывания не измерены — читайте верхушку этого отчёта как список на просмотр.

**Ложные срабатывания в этом отчёте реальны.** Ниже первой строки в топе встречаются
кадры, у которых крайняя полоса занята шапкой, фотографией или выделительным шрифтом,
и фильтры однородности их не отсеяли. Каждый случай в топе проверялся глазами по кропам
полноразмерного RAW, и часть оказалась именно такой. Поэтому второй отчёт — список на
просмотр, а не приговор; ориентируйтесь в первую очередь на величину перепада и на то,
повторяется ли «где мягче» из кадра в кадр (систематический завал плоскости съёмки).

Из-за фильтров однородности часть кадров остаётся без зональной оценки (в выборке 18 из
317: обложки, полосы-таблицы, кадры с малым количеством тела-текста) — они перечисляются
отдельной строкой.

Что эта папка **не** проверяет:

- **Разброс ISO и освещения** — 310 файлов из 317 сняты на ISO 2000, все на f/8.
  Устойчивость к экспозиции проверена только на синтетике
  (`tests/ocr_utils/defocus_detection/test_metrics.py`).
- **Обложки и переплёты.** Кадры без текста (картон, дерево) инструмент ставит в *самый
  резкий* конец списка: краёв мало, но все контрастные и крутые. На поиск худших это не
  влияет, но расфокус на самой обложке замечен не будет.

## Режим по строкам текста (`--use-surya-lines`)

По умолчанию резкость меряется по равномерной сетке тайлов, и это отвечает на вопрос
«резкий ли кадр в среднем». Флаг `--use-surya-lines` меняет вопрос на более узкий и
более практичный: **читается ли на кадре мелкий корпусный текст.** Области строк
находит surya-ocr (`DetectionPredictor`), и метрика считается только по ним.

Требует видеокарты. Первый прогон по папке идёт дольше тайлового (детекция ~4 с на кадр
против ~1 с на весь замер), зато её результат ложится в дисковый кэш, и повторные
прогоны — с другой агрегацией, сеткой, метрикой — GPU уже не трогают.

### Два балла

| Колонка | Что мерит | Зачем |
|---|---|---|
| `σ края, px` | **оптику** — до какой ширины объектив размазал перепад | от кегля почти не зависит, поэтому на ней строится зональная карта |
| `σ/высота` | **читаемость** — размытие в долях высоты строки | одно и то же размытие не мешает заголовку и убивает петит; общий балл файла считается по ней |

Раздельная оценка размытия и кегля — приём из [Rodin et al., «Document Image Quality
Assessment via Explicit Blur and Text Size
Estimation»](https://link.springer.com/chapter/10.1007/978-3-030-86337-1_19) (ICDAR 2021).
Замер именно по текстовым областям, а не по всему кадру, — общее место в document image
quality assessment, ср. [CG-DIQA](https://arxiv.org/abs/1807.04047) (ICPR 2018), где
градиент считается по символьным патчам из MSER.

Нормировка на кегль осмысленна только у метрик с размерностью длины
(`Algorithm.length_scaled`); у безразмерных отношений вроде `reblur` эта колонка пустая.

### Наклонные строки (трапециевидные искажения)

Съёмка с рук заваливает плоскость кадра, строки идут под углом в несколько градусов, и
угол меняется по кадру. Surya отдаёт **полигон из четырёх углов**, так что наклон
известен точно. Дальше есть три пути, и выбран третий:

1. **Охватывающий прямоугольник.** Прихватывает бумагу сверху и снизу тем больше, чем
   сильнее наклон, — то есть вносит в замер ровно ту пространственную зависимость,
   которую мы потом собираемся измерять как зональный расфокус. Негодно.
2. **Поворот кропа (`minAreaRect` + `warpAffine`).** Смертельно для метрики резкости:
   интерполяция сама размывает край примерно на треть-половину пикселя, и тем сильнее,
   чем дальше угол от кратного 90°. Наклон по кадру меняется плавно — получился бы
   идеально гладкий ложный зональный сигнал, неотличимый от настоящего завала фокуса.
3. **Резать строку на короткие куски и брать вписанный прямоугольник каждого.** Ни
   одного пересчитанного пикселя, кроп — срез массива. Ширина куска подстраивается под
   наклон, чтобы он съедал не больше четверти высоты строки.

Куски — это только способ вырезать; замер копится по ним и сводится в один балл
**строки** (взвешенное гармоническое среднее, потому что усреднять физически осмысленно
саму σ, а она есть среднее по измеренным перепадам). Строка со своим центром тяжести и
относится к тайлу зональной сетки.

Проверяется это в `tests/.../test_line_measure.py::test_slanted_lines_measure_the_same_as_straight_ones`:
наклонная и прямая полосы нарисованы из одних и тех же штрихов, сдвинутых на целое число
пикселей, и измеренная σ обязана совпасть.

### Зональная карта 3×3

Строки относятся к тайлу по центру тяжести, балл тайла — медиана по его строкам (медиана,
а не среднее: один жирный лозунг не должен утащить тайл), метрика кадра — перепад между
самым резким и самым мягким тайлом. Формула и шкала те же, что у направленного отчёта
(`σ_мягкого / σ_резкого − 1`), поэтому обе колонки печатаются рядом и читаются одинаково.
Они считаются независимо и по-разному ошибаются — расхождение само по себе повод
посмотреть кадр глазами.

Тайлов намеренно мало: вопрос, на который отвечает метрика, — «какую часть кадра
переснять», и ответ «правый нижний угол» полезнее карты из сотни ячеек.

**Коридор «мелкого текста» (`--line-height-percent`) считается внутри каждого тайла, а
не по кадру.** Трапеция систематически увеличивает кегль на ближнем краю, и общий на
кадр коридор выкосил бы оттуда все строки — то есть выбросил бы из зональной карты целую
сторону, причём ровно ту, где искажения сильнее всего.

### Детекция: почему тайлами

`DetectionPredictor` ужимает вход до размера своего процессора (~1024 px по стороне), а
режет кадр только по высоте. Ширина превью (2944 px у портретного скана) давится втрое, и
корпусная строка высотой ~17 px приходит в сеть высотой в пять пикселей. Замер на пяти
полосах «Социалистической индустрии» 1985 г. (`scripts/check_surya_line_detection.py`):

| режим | строк | высота p10/p50/p90 | строк в самом бедном тайле 3×3 | время |
|---|--:|---|--:|--:|
| `page` | 542–761 | 15 / 17–24 / 26–49 px | 2–30 | 1.3 с |
| `tiles` | 1533–2110 | 15 / 16–20 / 27–31 px | 4–94 | 3.9 с |

Дело не в количестве, а в том, **каких** строк: у `page` заметно выше p90 высоты — он
размечает полосу преимущественно по заголовкам и пропускает корпус, то есть ровно тот
текст, ради которого всё затевается. Мельчить тайлы тоже вредно: при стороне 800 px строк
нашлось *меньше* (1554 против 1904) — строка чаще перерезается границей тайла.

**На новом материале прогоняйте `run_scripts/defocus_detection/run_check_surya_lines.sh`
заново:** другая газета, другая оптика, другой масштаб — и вывод может смениться.

### `--debug-dir`

Прогон по незнакомому материалу без отладочных наложений смотреть бессмысленно: по одному
числу в таблице не отличить «замер идёт по корпусному набору» от «детектор нашёл одни
заголовки». В наложении видно сразу всё: границы тайлов, рамка каждой найденной строки
(зелёная — резче медианы кадра, красная — мягче, серая — не измерена), балл и число строк
в углу каждого тайла, общий балл в углу кадра. Числами подписана выборка строк поровну от
каждого тайла — на полосе их за тысячу, и подписать все значило бы залить кадр текстом.

### Что этот режим не чинит

- **Кадр без текста** (обложка подшивки) даёт горстку строк и никакой зональной карты —
  как и в тайловом режиме, судить о нём не по чему.
- **Сильный наклон при мелком кегле.** Вписанный прямоугольник тем ниже, чем больше
  наклон; при 6° и высоте строки 16 px замеров остаётся мало, и часть строк честно
  отдаёт NaN. Для «слегка наклонных» строк (до ~3°), ради которых режим и делался, это
  не проявляется.
- **Калибровки на размеченной выборке у этого режима пока нет.** AUC 0.901 из раздела
  «Валидация» относится к тайловому замеру. Числа выше — это замеры покрытия детекции,
  а не качества ранжирования.
