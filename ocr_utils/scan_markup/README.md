# scan_markup — растровые области и библиотечные печати

Подсистема готовит разметку полос журнала для сборки финальных PDF: находит растровые
(полутоновые) изображения и обложки, отдаёт их на ручную правку в CVAT и забирает
уточнённый результат обратно в SQLite.

## Зачем

Финальный PDF выпуска собирается из двух бинаризованных слоёв:

* полный PDF — бинаризация в FineReader **с распрямлением строк**;
* PDF `pages_with_raster_pics` — только полосы с растром, бинаризация **без распрямления**,
  чтобы не поехала геометрия картинок.

Дальше из оригиналов вырезаются растровые области и вклеиваются поверх бинаризованного
слоя второго PDF, а его страницы замещают соответствующие страницы первого. Чтобы это
собрать, нужно заранее знать по каждой полосе: где растр, какого он типа (`color` даёт
JPEG втрое тяжелее `grayscale`) и где библиотечные печати под закраску через LaMa.

Автодетектор печатей отсутствует как класс, а границы растровых областей автодетектор
угадывает лишь приблизительно — поэтому результат обязан пройти ручную правку.

## Команды

```bash
# 1. Предварительная детекция по оригиналам -> SQLite
uv run python -m ocr_utils.scan_markup detect \
    --pack-dir "/mnt/.../Готовое/пак-1" \
    --db ~/Projects/mts_markup/pack1.sqlite \
    --debug-dir ~/Projects/mts_markup/debug

# 2. Уменьшенные копии в share + проект/задачи/джобы CVAT с предразметкой
uv run python -m ocr_utils.scan_markup to-cvat \
    --db ~/Projects/mts_markup/pack1.sqlite --pack-name пак-1 \
    --share-root ~/Projects/mts_markup/cvat_share --jobs 16

# 3. Уточнённая разметка обратно в базу той же схемы
uv run python -m ocr_utils.scan_markup from-cvat \
    --db ~/Projects/mts_markup/pack1.sqlite \
    --out-db ~/Projects/mts_markup/pack1_reviewed.sqlite \
    --pack-name пак-1
```

## Иерархия

| В файлах | В базе | В CVAT |
|---|---|---|
| `пак-1/` | `packs` | проект |
| `пак-1/1974/` | `year_packages` | задача (task) |
| `пак-1/1974/01/` | `issues` | джоб (job) |
| `пак-1/1974/01/a.tif` | `pages` | кадр (frame) |

Джобы по границам выпусков задаются параметром `job_file_mapping` — единственным способом
описать их явно. Разбиение по `segment_size` режет задачу на равные куски и границы
выпусков не соблюдает, а сочетать одно с другим сервер запрещает.

## Детекция растра

**Surya предлагает, пиксели уточняют.** Первичный детектор — модель разметки вёрстки; она
даёт блоки `Picture`. Пиксельные проверки идут после и отвечают на три вопроса, на которые
модель ответить не может: где настоящая граница картинки, растр это или штриховой рисунок,
и цветная ли она.

### Почему именно такой порядок

Замер по 144 полосам пака-1:

| | Surya даёт `Picture` |
|---|---|
| полосы с настоящими фотографиями | **63 из 63** |
| полоса с отточиями в оглавлении | **0 из 1** |
| полосы без картинок вовсе | 0 из 2 |
| полосы со штриховым рисунком | 28 из 31 |

Верхние строки — то, чего не умеют пиксели. Строка отточий в оглавлении состоит из мелких
круглых пятен одинакового размера, то есть даёт ровно ту статистику, по которой опознаётся
растровая печать. Отсечь её не вышло ни по размеру (настоящие фотографии доходят до 0.57 %
полосы), ни по заполнению прямоугольника растровыми клетками (0.44 у отточий против 0.09 у
светлого снимка). Surya же видит там список, а не картинку.

Нижняя строка — то, чего не умеет Surya: штриховой рисунок она уверенно считает картинкой.
Поэтому её блоки обязаны проходить пиксельную проверку, и первичность роли этого не отменяет.
По той же причине блоки берутся **сырыми**, без фильтра `layout.is_raster_block`: тот меряет
полутон по копии 1/4, где штрих от растра неотличим.

### Пиксельная часть

Считается по **полному кадру** и смотрит на **размер связных пятен краски**, а не на яркость.

1. `cv2.adaptiveThreshold` окном ~31 px (при 600 dpi) — маска краски. Порог локальный: у
   камерного скана яркость бумаги плывёт по кадру на десятки уровней.
2. Связные компоненты. Пятно «точечное», если умещается в 300 px площади и 24 px стороны.
3. Кадр режется на клетки по 128 px. Клетка **растровая**, если почти все её пятна точечные
   (≥ 0.88), крупных нет вовсе (< 4400 px) и самих точек хватает (≥ 6).
4. Морфология по карте клеток (замыкание 4, размыкание 2). **Связность** решает карта после
   морфологии, а **границы и размер** — карта до неё: замыкание раздувает пятно в две клетки
   до восьми, и по площади после него сквозь любой порог проходит крапина.

Все пороги заданы при 600 dpi и пересчитываются в `dots.params_for_dpi`: длины линейно,
площади квадратом, доли и счётчики никак. Паки бывают 300, 450 и 600 dpi.

### Как блок Surya превращается в область

* **Блок сел на связные области растровых клеток** — область есть, и её граница это
  **объединение** блока и этих клеток. Именно объединение, а не замена блока клетками.
  Соблазн заменить есть: блок в медиане в 1.69 раза крупнее картинки и хватает бумагу вокруг.
  Но у карты клеток обратная беда — по краю картинки клетка наполовину занята бумагой, точек
  в ней не набирается, и замена уводит рамку внутрь фотографии. Замер на замене (1966/02
  IMG_0095_2R и IMG_0096_1L, 1966/04 IMG_0030_2R, 1966/05 0210_1L): справа и снизу совпадение
  с блоком, а слева срезано 228…348 px и сверху 184…300 px — по сантиметру с лишним настоящей
  картинки на двух сторонах. Лишняя бумага не стоит ничего, срезанный кусок фотографии теряется
  навсегда; то же правило и по той же причине записано в `background_smoothing.layout`.
  Слияние при этом сохраняется: два блока над одной связной областью дают пересекающиеся
  объединения и схлопываются в один прямоугольник, а разделённые белым полем остаются
  раздельными.
* **Клеток под блоком нет** — это либо тёмный растр, у которого точки в тенях слиплись в
  крупные пятна, либо штрих. Решает p99 площади пятна внутри блока.

Готовое объединение ещё и **подрезается по бумаге**, но не глубже блока Surya. Край клеточной
области округляется наружу до целой клетки — при 600 dpi это 128 px, около 5 мм, — и в этот
последний ряд попадает подпись под фотографией. Замер, 1974/03 IMG_0140_1L: фотография
кончается на y=3365, блок Surya на 3396, а рамка доходила до 3456 и накрывала «рис. 1».
Подрезка идёт тем же признаком бумаги, что и рост страховочной рамки, только внутрь, и
упирается в блок: спорить с моделью пикселями значит вернуть срезание светлых краёв. На паке-1
она сняла 0…36 px, полосы с двумя фотографиями не задела.

### Цветная полоса целиком

Обложку разрывает то, что само картинкой не является: сплошная плашка заголовка растровых
клеток не даёт, компонента на ней рвётся, и полоса распадается на куски. Замер по
1967/11 IMG_0052_2R (обложка 2): две области, 4.3 % и 68.4 % полосы, между ними 588 px
(2.5 см), а красная плашка между ними не попала в разметку вовсе.

Увеличить зазор слияния нельзя — 2.5 см на внутренней полосе это обычный просвет с подписью
между двумя **разными** фотографиями. Отличает обложку не зазор и не размер, а то, что она
**цветная целиком**; метрика та же, что решает `color`/`grayscale` у областей, только
посчитанная по всей полосе:

| полоса | разброс цвета по полосе |
|---|---|
| 1967/11 IMG_0052_2R — обложка | **33.7** |
| 1966/03 IMG_0104_2R — обложка 1 | **26.4** |
| 1969/12 IMG_0150_2R — обложка 3, две ч/б фото | 4.1 |
| 1969/11 IMG_0093_2R — две ч/б фото | 4.8 |
| 1970/03 IMG_0141_2R — две ч/б фото | 5.1 |

Правило: если охватывающий прямоугольник **всех** найденных областей занимает ≥ 75 % полосы
**и** разброс цвета по полосе выше того же порога 8 — вместо них выдаётся одна область во
весь кадр. Оба условия обязательны: без проверки площади цветная полоса с одной маленькой
картинкой и текстом уехала бы в разметку целиком, без проверки цвета слиплись бы две ч/б
фотографии, разнесённые по полосе.

Номер полосы правило не смотрит намеренно: обложки 2, 3 и 4 бывают чем угодно, а цветная
заливка во весь кадр — измеримый признак, который работает и на обложке, и на цветной
вклейке внутри выпуска.

### Штрих против растра

По настоящим границам картинок признак разделяет классы полностью (67 областей с
фотографиями против 39 со штрихом):

| признак | фотографии | штрих | точность |
|---|---|---|---|
| p99 площади компоненты | 100 … 4439 | 4761 … 550783 | **100 %** |
| доля компонент размером с точку | 0.699 … 0.993 | 0.128 … 0.926 | 97 % |

**Но по границам блоков Surya — хуже** (95 %): блок прихватывает окружающий текст, чьи
длинные компоненты поднимают p99 у фотографий. Полосы со штрихом, у которых p99 равен 989,
2728 и 4220, оказываются ниже тёмного портрета 1969/12 IMG_0140_2R (4439), который терять
нельзя, — порога, который делит эти четыре числа правильно, не существует. И хуже того: под
штриховым рисунком РАСТРОВЫЕ КЛЕТКИ находятся исправно (плотная штриховка распадается на
такие же мелкие пятна, что и сетка), а ветка «клетки есть — значит растр» p99 не смотрит
вовсе. Поэтому чертежи попадали в разметку и мимо этого порога.

#### Тона и растровая сетка

Разбирается это тремя признаками по окончательной рамке (`detection/tone.py`), и решает их
**конъюнкция** — по отдельности не разделяет ни один. Замер по 31 штриховой области против
75 с подтверждёнными фотографиями (обложки исключены — у них своё правило):

| признак | штрих | фотографии | порог |
|---|---|---|---|
| доля средних тонов | 0.032 … 0.322 | 0.111 … 0.568 | < 0.25 |
| энтропия гистограммы | 4.245 … 7.170 | 5.770 … 7.721 | < 6.5 |
| выступ пика растровой сетки | 1.100 … 2.156 | 1.054 … 49.796 | < 3.0 |

Каждый признак закрывает слепое пятно двух других:

* пересвеченную фотографию (1969/01 IMG_0033_2R: средние тона 0.111, энтропия 5.77 — обе
  внутри штрихового диапазона) спасает **сетка**: выступ пика 4.05;
* фотографию, у которой сетка смазана и пика нет вовсе (1969/09 IMG_0122_2R и соседние,
  выступ 1.05…1.19), спасают **тона**: энтропия 6.87…7.08;
* штрих проваливает все три сразу.

Пороги стоят посередине замеренных зазоров: энтропия 6.5 при верхе штриха 6.37 и ближайшей
фотографии 6.66, выступ 3.0 при верхе штриха 2.16 и ближайшей фотографии 4.05. На них правило
ловит 30 штриховых областей из 31 и не задевает ни одной фотографии из 75.

Выступ пика — стандартный приём descreening: AM-растр кладёт точки периодической решёткой и
даёт в спектре дискретный пик, которого у текста и штриха нет (US7365882B2, US6360009).
Считается по плиткам 256 px: радиальный профиль мощности делится на СВОЁ ЖЕ сглаживание
медианой, иначе спектр, падающий как 1/f, топит полосу целиком. Полоса периодов 5.5…11 px при
600 dpi — это 55…110 lpi; при другом разрешении она масштабируется вместе с ним.

Признаки считаются в воркере по картам клеток (гистограмма 256 корзин на клетку плюс выступ
пика на плитку) и агрегируются в родителе по готовой рамке. Замер стоимости на 1969/01
IMG_0029_2R: карта спектра 0.27 с, карта гистограмм 0.07 с при 0.11 с у этапа пятен, то есть
около четырёх минут на весь пак в 16 воркеров. Перечитывать полосу третьим проходом ради
точных границ дороже: 600 полос с NTFS-3G — девять минут.

**Чего делать не надо** (всё проверено замером):

* буквальный подсчёт точек растра, как в патентах по сегментации сканов, — плотность вышла
  1…11 точек на клетку 128 px и у фотографий, и у штриха, и у чистого текста;
* «доля пикселей крупных компонент» — краска смыкается в сплошную сеть, доля 0.5…0.7 везде;
* `dot_frac` как порог штриха — стоил бы 40 настоящих областей из 402;
* энтропия ТОЛЬКО ПО КРАСКЕ, без бумаги, — разделяет наоборот: у плотных рисунков она выше
  (7.9), чем у фотографий (от 6.7), потому что вклад дают края штрихов;
* гистограмма после сильного уменьшения (до 7.5 и до 30 dpi) — ни разброс, ни энтропия, ни
  доля тёмного у двух групп не расходятся;
* расширение полосы поиска пика до 4…24 px — фотографии без сетки пика так и не дают, зато
  в полосу начинает попадать штриховка, и штрих поднимается с 1.5 до 2.25.

**Известный предел.** Плотный перспективный рисунок 1968/12 IMG_0139_2R (стеллаж с
баллонами) правило не ловит: средние тона 0.322 и энтропия 7.17 — внутри диапазона
фотографий. Порог, который достаёт его, начинает задевать настоящие снимки.

### Правила пометки

| источник области | цвет | размер | краска | что пишем |
|---|---|---|---|---|
| растр | серый | любой | любая | `grayscale` |
| растр | цветной | любой | любая | `color` |
| штриховой рисунок | цветной | ≥ 15 % полосы | любая | `color` |
| штриховой рисунок | любой | < 15 % полосы | бледная | `stamp_suspect` |
| штриховой рисунок | цветной | < 15 % полосы | любая | `stamp_suspect` |
| штриховой рисунок | чёрный | любой | чёрная | **в разметку не включается** |

Цветной штрих бинаризовать нельзя: полполосы уйдёт в чёрное, полполосы останется цветной,
и на странице получится каша. Чёрный, наоборот, бинаризуется как текст, и вырезать из него
картинку не нужно.

**Про `stamp_suspect`.** Оттиск библиотечной печати — это мелкий штрих, и от рисунка его
отличает размер: замер по паку-1 дал у печатей 2.12 % и 2.15 % полосы (1966/01 IMG_0004_2R,
1966/02 IMG_0055_2R) против почти 100 % у синего рисунка обложки. Без разделения по размеру
каждый оттиск становился бы «цветной картинкой» и уезжал в PDF как иллюстрация.

Одного размера, впрочем, мало: мелкий штрих — это ещё и виньетка рубрики, которых в паке три
десятка, и их в разметке быть не должно. Разделяет их **плотность краски**: мастика бледная и
выгорает, типографская краска чёрная. Замер контраста «бумага минус краска»: у 10 оттисков
79…220, у 33 виньеток 231…254, порог 225 посередине зазора. Без него фиолетовая печать,
выцветшая до серого, уезжала в разметку полноценной `grayscale`-картинкой — таких по паку
нашлось 12 сверх 33, опознанных по цвету.

Печать не выбрасывается, а помечается отдельным типом: закрашивать её через LaMa всё равно
предстоит, и знать заранее, где она стоит, полезно. В CVAT для этого заведена четвёртая
метка — **«Подозрение на печать»**, прямоугольник (оранжевый). Прямоугольник, а не маска,
потому что автодетектор находит только рамку; разметчик по ней либо обводит оттиск кистью под
метку «Библиотечная печать», либо снимает прямоугольник, если это оказался не оттиск.

`KIND_STAMP_SUSPECT` не входит в `PICTURE_KINDS`, поэтому потребители, вырезающие картинки в
PDF, его не увидят. Команда `recolor` такие области тоже обходит стороной: у них `kind`
означает не цвет, а происхождение.

### Страховка от пропусков модели

Всё, что Surya не предложила, при чистой схеме терялось бы навсегда. Поэтому области
детектора точек, которых не коснулся ни один блок, остаются, если они крупнее 3 % полосы:
отточия занимают 0.70 % и под порог не проходят, а самая мелкая настоящая неподтверждённая
область — 19.78 %.

Такая область — единственная, у которой границу не с чем объединить, поэтому она **растёт по
бумаге**: пока полоса вдоль края светлее бумаги на `--grow-paper-margin`, край сдвигается
наружу шагом 64 px. Растровые клетки по краю снимка не добирают точек, и без роста рамка режет
светлые участки. Замер: 1973/12 IMG_0271_1L (640,1408,3200,3072) -> (384,1152,3200,3072).
Рост останавливается перед подписью и перед текстом: они темнее бумаги.

Из-под страховки отдельно выбиваются **отточия** — строка точек в оглавлении или таблице даёт
ту же статистику пятен, что и растровая сетка (см. выше, чего не умеют пиксели). Их узнают два
признака сразу, и оба нужны: доля пустых строк внутри рамки (у отточий между строками бумага,
у растра сплошная заливка) и периодичность строк по автокорреляции. Третий признак — разброс
тонов после уменьшения области примерно в 20 раз: у настоящего растра усреднение проявляет
полутон, у отточий остаётся почти белое поле. Область, похожая на отточия по всем трём,
отбрасывается. Не сработали и записаны как отрицательный результат: `dot_frac`, шаг между
точками и коэффициент вариации их размера.

**Замер по паку-1.** Прогон по 586 полосам, где прошлая версия детектора нашла хоть что-то:
областей стало 596 вместо 610, полос с областями — 577 вместо 586. Все девять исчезнувших
полос проверены глазами, и все девять — правильные снятия: шесть отточий в оглавлениях и
таблицах, один штриховой чертёж плана склада (1976/11 0380_2R) и две таблицы с точечными
заполнителями. Настоящей фотографии не потеряно ни одной. Заодно починилось слияние: на
1967/11 IMG_0052_2R две области схлопнулись в одну, как и должны были.

**Сколько это стоит, замерено.** Surya прогнана по всем 570 полосам пака-1, где прошлый
детектор нашёл хоть что-то (кроме обложек). Она молчит на 102 из них:

| что видят пиксели на этих 102 полосах | |
|---|---|
| тоже ничего — это были ошибки прошлого детектора (логотип на содержании, тень разворота, штрих) | 80 |
| крупную область, спасает страховка | 22 |
| мелкую область, потеряли бы | **0** |

То есть на паке-1 первичность Surya не стоит ни одной картинки. На новом паке это надо
перепроверять командой `validate`.

### Пул и GPU

`--use-surya-layout` **не** схлопывает прогон в один процесс. Работа разбита на два этапа
(`detection/page.py`): воркеры читают файл и считают всё пиксельное, родитель зовёт GPU и
собирает области. Между ними едет разбор на несколько мегабайт — рабочая копия 1/4, карты
клеток и статистика пятен, — а не 21-мегапиксельный кадр. Сериализуется только инференс.

Оттуда же следует, что цвет меряется по копии 1/4: разброс хроматичности на ней даёт у ч/б
областей до 5.19 при 9.03 у цветных — тот же промежуток, что и на полном разрешении.

### color / grayscale

Решает **разброс** хроматичности области — `hypot(std(a), std(b))` в Lab после снятия налёта
бумаги, порог 8.

Прежняя метрика — доля хроматичных пикселей после баланса белого — не работает, и это не
вопрос порога. Поканальный баланс выправляет ровно один уровень яркости, бумагу; у ч/б
фотографии в средних тонах оттенок свой (у камерного скана тени уходят в зелень или синь), и
после «коррекции» она хроматична целиком:

| метрика | ч/б области (66) | цветные обложки (20) |
|---|---|---|
| доля хроматичных пикселей | 0.110 … 0.811 | 0.089 … 0.749 |
| **разброс хроматичности** | **2.2 … 6.5** | **9.3 … 19.6** |

Порог 0.10 калибровался по одному 1966 году, где обложки отстояли далеко; по всему паку
промежутка нет вовсе, и он резал сплошное распределение пополам — 342 «цветных» области при
примерно 123 настоящих. Число продолжает считаться и писаться в `chroma_frac`, чтобы старую
разметку было с чем сравнить.

### Обложки

Их в выпуске четыре: полосы 0 и 1 и две последние. Предсказуема ровно одна — полоса 0 занята
цветным изображением во весь кадр во всех 123 выпусках пака-1. Её и помечает
`--first-page-is-cover`, не декодируя пикселей вовсе.

Остальные три идут обычной детекцией: там бывает и текст, и пара ч/б фотографий с подписями,
и штриховой рисунок. Эвристика «мало текстовой краски, много сплошной» заперта на полосу 0 в
графе вызовов (`cover.cover_decision`): раньше она звалась на каждой полосе и объявила
обложками две внутренних, накрыв обе фотографии одним прямоугольником во весь кадр
(1969/11 IMG_0093_2R, 1969/12 IMG_0150_2R).

## Проверка детекции

Пороги крутятся не полным прогоном (полтерабайта, часы), а по валидационной выборке:

```bash
uv run python -m ocr_utils.scan_markup validate \
    --pack-dir "/mnt/.../Готовое/пак-1" \
    --cases-dir ~/Projects/mts_markup/"некоторые проблемные картинки" \
    --out-dir ~/Projects/mts_markup/validate \
    --db ~/Projects/mts_markup/pack1.sqlite --pack-name пак-1 --jobs 16
```

Выборка — папки с примерами неправильной разметки, разобранными из `--debug-dir` глазами;
имя папки называет тип дефекта (список — в `validation/cases.py`). Сотня файлов, полминуты.
Сверх выборки прогоняются случайные полосы, где области уже находились, — страховка от
обратной ошибки: чинили одно, потеряли другое. В `--out-dir` ложатся оверлеи, `report.md` и
`measurements.csv` со всеми измерениями по каждой области: следующую итерацию порогов по нему
можно откатать вообще без чтения TIFF.

Текущий счёт: **109 дефектов из 110 починены**. Единственный оставшийся — 1970/03
IMG_0104_2R: на нём находится область `stamp_suspect`, а папка-эталон ждёт, что не найдётся
ничего. Это расхождение ожидания, а не дефект: на полосе действительно стоит библиотечная
печать (по ней же назван порог в `_classify_regions`), и подозрение на неё — правильный
ответ.

Из сорока контрольных полос область не пропала ни у одной. На более ранних порогах пропадала
у четырёх — все четыре были проверены глазами и все четыре оказались ошибками прошлого
детектора: логотип журнала на полосе содержания и тень разворота у края.

Прогон гоняет ту же связку, что и боевой, включая Surya, — то есть требует GPU. Проверить
одни пиксели можно флагом `--no-use-surya-layout`.

### Правка готовой базы

Две команды меняют разметку, не перечитывая пак:

| Команда | Что читает | Зачем |
|---|---|---|
| `recolor` | только полосы с областями (693 из 12 135) | пересчитать `color`/`grayscale` после смены порога |
| `mark-covers` | ничего | пометить первые полосы обложками по данным базы |

Обе трогают только разметку `source='auto'` и не касаются ручной из CVAT.

**Версия детектора.** `Page.detector_version` пишется вместе с разметкой, и `--skip-detected`
сравнивает её с `detection.DETECTOR_VERSION`. Без этого правка алгоритма не доехала бы до базы
вовсе: файлы не менялись, и весь пак был бы молча пропущен.

## Следы шариковой ручки

На части полос поверх текста есть пометки синей пастой. Это дефект **исходника**: в
бинаризованный PDF пометка попадёт независимо от разметки, и текст под ней будет потерян.

```bash
uv run python -m ocr_utils.scan_markup fix-pen-marks \
    --pack-dir "/mnt/.../Готовое/пак-1" \
    --out-dir "/mnt/.../Готовое/пак-1-починенные" \
    --page 1968/01/IMG_0045_2R.tif
```

Гасится линейной комбинацией каналов `0.9·B + 0.8·G − R`. Одного канала не хватает — задача
двухсторонняя: клякса должна уйти к уровню бумаги, а текст **под** ней остаться тёмным.
Уровни по замеру 1968/01 IMG_0045_2R после приведения «бумага 245, текст 30»:

| комбинация | клякса | текст под кляксой | |
|---|---|---|---|
| только синий | 151 | 79 | клякса ещё видна |
| только красный | 0 | — | клякса чернее текста |
| `B − 0.47·R` (точное гашение) | 243 | 148 | текст под ней выцвел |
| **`0.9·B + 0.8·G − R`** | **217** | **118** | компромисс |

Веса найдены перебором по сетке при двух ограничениях: клякса не темнее 215 и шум бумаги
после преобразования не выше 9 уровней. Второе ограничение существенно — комбинации вида
`G − 0.8·R` делят классы по средним лучше, но вычитают друг из друга два похожих канала,
и бумага после них идёт пятнами.

Комбинация подмешивается **только внутри маски кляксы** с растушёванным краем: на всю полосу
она поднимала бы шум ради пятна в сантиметр. Маска — хроматичность выше 30 в Lab после снятия
налёта бумаги (тот же `color_kind.balanced_lab`, что и в классификации областей), раздутая
на 2 мм. На 1968/01 IMG_0045_2R затронуто 0.42 % площади полосы.

Результат кладётся в отдельную папку с тем же относительным путём — подкладывать в пак
руками. Рядом с оригиналом класть нельзя: лишний файл стал бы лишней полосой в выпуске и
сдвинул бы порядок остальных.

## Уменьшение для CVAT

CVAT не масштабирует кадры сам: `image_quality` — только качество JPEG, разрешение чанка
всегда 1:1 с исходником. Поэтому копии готовятся заранее, по умолчанию до 75 dpi
(`--cvat-dpi` у `to-cvat`).

Делитель у каждой полосы свой, из DPI файла: 600 dpi → 8, 450 dpi → 6. Считается он на
шаге `to-cvat`, а не на `detect`: разрешение разметки тогда меняется без повторного чтения
пака, ценой лишней записи в базу на каждом прогоне. Полосе, уже залитой в CVAT, делитель
не меняют — её разметка нарисована в прежнем масштабе; чтобы перевести и её, задачу-год
надо завести заново. **Сначала обрезка**
справа и снизу до размера, кратного делителю, и только потом деление — иначе 3492 → 436
даёт масштаб 8.0092, и обратный пересчёт промахивается тем сильнее, чем правее объект (на
правом краю — на 40 px).

Потерянная при обрезке полоска шириной не более `делитель - 1` (≤ 7 px) разметчику не
видна. Объект, доведённый им до края кадра, при пересчёте назад **растягивается** до
полного размера оригинала — иначе у фотографии, свёрстанной в обрез, останется незакрытая
кромка. Правило одно и то же для прямоугольников и для масок (`geometry.py`).

## Хранение масок печатей

Маска хранится ровно в том виде, в каком её отдаёт CVAT, — серия длин пробегов (RLE) плюс
охватывающий прямоугольник, — но **пересчитанная в разрешение оригинала**, поэтому читается
без коэффициентов:

```python
from ocr_utils.scan_markup.cvat.export import mask_from_row
mask = mask_from_row(row, page.width, page.height)   # bool-массив во весь кадр
```

`source_divisor` фиксирует, что маска рисовалась на копии 1/divisor, то есть реальная
точность её краёв — 6–8 пикселей оригинала. Потребителю под LaMa это важно: маску всё
равно надо дилатировать.

## Обновление пака по частям

Сканы пересчитывают: выпуск перескали, полосу переобрезали в ScanTailor, кривой кадр
заменили. Чтобы понять, какие полосы это затронуло, у каждой хранится отпечаток файла:

| Колонка | Что это |
|---|---|
| `file_hash` | sha256 файла, каким он лежит на диске сейчас |
| `file_size`, `file_mtime` | дешёвый признак: совпал — файл не читаем вовсе |
| `cvat_file_hash` | тот же хеш, но снятый **в момент заливки в CVAT** |

Расхождение `file_hash` и `cvat_file_hash` и есть ответ на вопрос «чья разметка больше
не относится к делу».

**Почему sha256, а не blake2b.** Замер на реальном скане 40.6 МБ с прогретым кешем:
sha256 — 2116 МБ/с, blake2b-128 — 1209, md5 — 949. sha256 выигрывает за счёт аппаратных
инструкций SHA-NI. Дайджест не укорачиваем: полные 64 символа стоят 780 КБ на весь пак и
позволяют проверить строку из базы руками — `sha256sum файл.tif` выдаёт ровно её.

**Почему `stat` перед хешем.** Пересчитать хеши пака — это перечитать полтерабайта с
NTFS-3G, то есть часы. Поэтому `--skip-detected` сперва сравнивает размер и время правки
и читает файл, только если они разошлись; хеш при этом вполне может совпасть (файл просто
скопировали заново), и тогда разметка остаётся на месте. Размен осознанный и выключается
флагом `--rehash-all`.

### Чего не умеет CVAT

**Отдельный джоб удалить нельзя.** Сервер отвечает `"Only ground truth jobs can be
removed"` (`cvat/apps/engine/views.py`, `JobViewSet.perform_destroy`), а границы джобов
задаются один раз при создании задачи через `job_file_mapping`. Наименьшее, что вообще
можно пересоздать, — задача, то есть целый годовой комплект.

Выбрасывать год целиком из-за одной подменённой полосы недопустимо, поэтому
`--recreate-stale` делает не это:

1. забирает разметку старой задачи и раскладывает по **именам** кадров;
2. пишет её в JSON-бэкап (`--backup-dir`, по умолчанию `cvat_backup` рядом с базой);
3. создаёт новую задачу под временным именем `<год> (пересоздание)`;
4. заливает в неё перенесённую разметку — со всех кадров, **кроме** изменившихся, — плюс
   свежую автоматическую предразметку на сами изменившиеся;
5. и только теперь удаляет старую задачу и переименовывает новую.

Для разметчика это неотличимо от «удалили только те джобы, где менялись картинки»: работа
на неизменившихся полосах остаётся на месте. Порядок шагов выбран так, чтобы сбой на любом
из них оставлял старую задачу целой — сначала создаём, потом удаляем. Прерванное
пересоздание опознаётся по временному имени и сносится следующим прогоном.

Геометрию при переносе не пересчитываем: уменьшение делается тем же делителем из базы,
значит кадр в новой задаче попиксельно совпадает со старым, и координаты — что углы
прямоугольников, что RLE масок — остаются верными.

Без флага `to-cvat` ничего не трогает, а только печатает отчёт: какие выпуски (джобы)
задеты, сколько полос изменилось и сколько добавилось.

```bash
# посмотреть, что разошлось
uv run python -m ocr_utils.scan_markup to-cvat --db ... --pack-name пак-1 --share-root ...

# перед пересозданием — снять текущую разметку в базу
uv run python -m ocr_utils.scan_markup from-cvat --db ... --out-db ... --pack-name пак-1

# пересоздать задетые годы, сохранив ручную разметку неизменившихся полос
uv run python -m ocr_utils.scan_markup to-cvat --db ... --pack-name пак-1 \
    --share-root ... --recreate-stale
```

## Требования к окружению CVAT

Картинки не грузятся по сети — задачи заводятся из share-каталога (`ResourceType.SHARE`).
Поэтому `--share-root` должен лежать внутри `IMAGES_DIR` из `docker/.env` (или совпадать
с ним): сервер видит ровно то, что смонтировано в `/home/django/share`.

Адрес, учётка и организация читаются из `docker/.env`; опции `--cvat-*` их перекрывают.
