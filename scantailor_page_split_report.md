# Как ScanTailor Advanced разбивает разворот на две страницы

Разбор кода `/home/felix/Projects/scantailor-advanced` (стадия `page_split`) и оценка того,
как на неё влияет заливка «ушей» в нашем `scan_cropping --crop-mode=pixel-exact`.

Все ссылки — на `scantailor-advanced/src/`.

---

## 0. Краткий ответ на три вопроса

1. **Только ли верхняя и нижняя полосы кадра?** — Нет. Обе процедуры поиска границы
   работают **по всей высоте кадра**. Единственное пространственное ограничение —
   горизонтальное: поля 3.5 мм слева и справа (`VertLineFinder.cpp:113-116`). Никаких
   «полос» сверху/снизу в коде нет. Ощущение «полос» может возникать из-за того, что
   найденная линия задаётся двумя точками — на `y=0` и `y=height`
   (`VertLineFinder.cpp:140`), — но это лишь параметризация прямой, голоса же
   накапливаются со всех строк изображения.

2. **Зачем нужна разбивка?** — Это вторая стадия конвейера ScanTailor
   (`StageSequence.cpp:10-13`: fix_orientation → **page_split** → deskew →
   select_content → …). Она решает, одна на кадре страница или две, и, если две,
   проводит прямую линию реза по корешку. Дальше каждая половина живёт как отдельная
   логическая страница: у неё свой угол выравнивания, своя область контента, свои поля
   и свой выходной файл. Результат стадии передаётся дальше как `preCropArea`
   (`page_split/Task.cpp:186-190`), т.е. режет область, видимую последующим стадиям.

3. **Сильно ли мешает наше растущее с расстоянием размытие?** — **Практически нет.**
   Численный расчёт (§4.6) показывает, что голоса Хафа в лучшей корзине падают с 32-35
   до 28-33 на строку при пороге **9** на строку, то есть запас остаётся 3-4-кратным.
   Причём отклик **насыщается уже при σ≈16 px**: значения 32 и 48 дают численно
   одинаковый результат. `--crop-fill-blur-px` — не тот параметр, который решает
   исход разбивки; куда важнее DPI в метаданных, угол наклона книги и то, что заливка
   продолжает линию **прямо** (`replicate`, а не `voronoi`). Подробности — §4-6.

## 1. Общая схема

Точка входа — `PageLayoutEstimator::estimatePageLayout()`
(`filters/page_split/PageLayoutEstimator.cpp:175-189`):

```
estimatePageLayout()
├── layoutType == SINGLE_PAGE_UNCUT → выходим сразу, резать нечего
├── tryCutAtFoldingLine()      ← ОСНОВНОЙ путь: искать тёмную линию корешка (Хаф)
└── cutAtWhitespace()          ← РЕЗЕРВНЫЙ путь: искать самый широкий белый промежуток
```

Резервный путь вызывается **только если основной вернул `nullptr`**, т.е. ни одного
кандидата-линии не нашлось. Резервный путь никогда не возвращает `nullptr` — он всегда
выдаёт какой-нибудь рез (в худшем случае ровно по середине кадра,
`PageLayoutEstimator.cpp:650-651`).

### Сколько страниц ожидать

`numPages()` (`PageLayoutEstimator.cpp:153-172`) при `AUTO_LAYOUT_TYPE` спрашивает
`ProjectPages::adviseNumberOfLogicalPages()` (`core/ProjectPages.cpp:205-214`):

```cpp
if (size.width() * dpi.height() > size.height() * dpi.width()) return 2; else return 1;
```

То есть **«физически шире, чем выше» → 2 страницы**. Это единственный критерий: ни
содержимого, ни линий здесь ещё не смотрят.

> Для нас важно: холст `pixel-exact` больше исходного bbox по обеим осям
> (`W' = W·cosθ + H·sinθ`, `H' = W·sinθ + H·cosθ`). При θ < 45° знак `W' − H'`
> совпадает со знаком `W − H`, поэтому landscape-разворот остаётся landscape и
> решение «2 страницы» не переворачивается. Расширение холста этот критерий не ломает.

## 2. Основной путь: поиск складки по всей высоте (`VertLineFinder`)

`VertLineFinder::findLines()` (`filters/page_split/VertLineFinder.cpp:25-196`).

### 2.1. Приведение к 100 dpi

```cpp
const int dpi = 100;
xform100dpi.preScaleToDpi(Dpi(dpi, dpi));          // VertLineFinder.cpp:31-34
const GrayImage gray100(transformToGray(image, xform100dpi.transform(), targetRect,
                                        OutsidePixels::assumeWeakColor(Qt::black), QSizeF(5.0, 5.0)));
```

Весь дальнейший анализ идёт на **серой копии 100 dpi**, масштаб берётся из **метаданных
DPI файла** (`ImageTransformation::preScaleToDpi`, `core/ImageTransformation.cpp:25-64`;
при `m_origDpi.isNull()` масштабирование просто не выполняется). Пиксели вне
изображения считаются **чёрными** (`assumeWeakColor(Qt::black)`).

### 2.2. Детектор вертикальных тёмных штрихов

```cpp
GrayImage hGradient(erodeGray(preprocessed, QSize(11, 1), 0x00));   // VertLineFinder.cpp:80
GrayImage vGradient(erodeGray(preprocessed, QSize(1, 11), 0x00));   // :81
grayRasterOp<GRopClippedSubtract<GRopDst, GRopSrc>>(hGradient, vGradient);  // :89
```

Внимание на соглашение ScanTailor: у них передний план — **чёрный**, поэтому
`erodeGray` — это **локальный максимум** (`Morphology.cpp:720-734` → `dilateOrErodeGray<Lighter>`),
а `dilateGray` — локальный минимум. Значит:

* `hGradient` = максимум яркости в горизонтальном окне 11 px;
* `vGradient` = максимум яркости в вертикальном окне 11 px;
* результат = `clip(maxH − maxV)` — велик там, где **в пределах ±5 px по горизонтали есть
  светлое, а по вертикали на ±5 px всё остаётся тёмным**. Это ровно «тонкий тёмный
  вертикальный штрих» — тень корешка.

Ключевое свойство: детектор измеряет **локальный контраст с апертурой 11 px @100 dpi
(≈2.8 мм)**, а не абсолютную темноту. Линия шире ~11 px в 100-dpi сетке даёт отклик
почти нулевой — `maxH` и `maxV` сравниваются.

Затем:

```cpp
const GrayImage rasterLines(closeGray(hGradient, QSize(1, 19), 0x00));  // :95  "short_segments_removed"
```

`closeGray` = min-фильтр, потом max-фильтр (`Morphology.cpp:865-875`). На карте откликов
(где «больше = сильнее») это **удаляет вертикальные фрагменты короче 19 px @100 dpi
(≈4.8 мм)**.

### 2.3. Преобразование Хафа

```cpp
const double lineThickness = 5.0;      // ширина корзины по расстоянию, px @100dpi
const double maxAngle = 7.0;           // градусы
const double angleStep = 0.25;         // → 57 углов, от −7° до +7°
HoughLineDetector lineDetector(rasterLines.size(), lineThickness, minAngle, angleStep, totalAngleSteps);
```
(`VertLineFinder.cpp:101-107`)

Накопление голосов — **по всем строкам, по всем столбцам кроме полей 3.5 мм**:

```cpp
const double marginMm = 3.5;
const auto margin = (int) std::floor(0.5 + marginMm * constants::MM2INCH * dpi);  // ≈14 px
const int xLimit = rasterLines.width() - margin;
const int height = rasterLines.height();
for (int y = 0; y < height; ++y, line += stride)          // ← ВСЯ высота кадра
  for (int x = margin; x < xLimit; ++x) {
    const unsigned val = line[x];
    if (val > 1) lineDetector.process(x, y, weight_table[val]);
  }
```
(`VertLineFinder.cpp:112-127`)

**Вот прямой ответ на вопрос про полосы: цикл по `y` идёт от 0 до `height` без каких-либо
исключений.** Обрезаются только левый и правый края.

Веса — почти логарифмические (`buildWeightTable`, `VertLineFinder.cpp:231-246`):

| уровень отклика | 0-1 | 2-4 | 5-10 | 11-22 | 23-46 | 47-94 | 95-190 | 191-255 |
|---|---|---|---|---|---|---|---|---|
| вес | (пропуск) | 3 | 4 | 5 | 6 | 7 | 8 | 9 |

Отклики 0 и 1 не голосуют вовсе. Всё остальное укладывается в диапазон весов 3…9, т.е.
**падение контраста в 4 раза стоит примерно 1-2 единицы веса (~20-30 %)**. Хаф здесь
куда чувствительнее к *длине* линии, чем к её контрасту.

Порог качества:

```cpp
const unsigned minQuality = (unsigned) (height * lineThickness * 1.8) + 1;   // = 9·height + 1
```
(`VertLineFinder.cpp:129`)

**`height` — это полная высота кадра в 100-dpi сетке, включая «уши».** Отсюда важное
следствие: любая добавленная сверху/снизу полоса поднимает планку пропорционально,
даже если сама голосов не даёт (см. §4.2).

Дальше пики группируются по перекрытию x-диапазонов (`LineGroup`,
`VertLineFinder.cpp:277-306`), берётся до `maxLines = 8` лидеров
(`PageLayoutEstimator.cpp:236`) и координаты переводятся обратно в исходные.

### 2.4. Выбор линии реза из кандидатов

`tryCutAtFoldingLine()` (`PageLayoutEstimator.cpp:227-283`), ветка «две страницы»:

```cpp
lines.erase(std::remove_if(lines.begin(), lines.end(),
                           BadTwoPageSplitter(virtualImageRect.width())), lines.end());
return autoDetectTwoPageLayout(lines, virtualImageRect);
```

`BadTwoPageSplitter` (`PageLayoutEstimator.cpp:192-209`) выбрасывает всё, что дальше
`0.6 · (W/2) = 0.3·W` от центра кадра. Из оставшихся `autoDetectTwoPageLayout()`
(`PageLayoutEstimator.cpp:129-151`) берёт **ближайшую к центру**, а не самую сильную.

> Полезное для нас: «мусорные» вертикали у краёв холста (например, край
> незаполненной чёрной зоны) в двухстраничном режиме автоматически отсеиваются, если
> они дальше 30 % ширины от центра. Ближе к центру — уже опасны.

Линия реза — **прямая с наклоном до ±7°**, задаётся двумя точками (`PageLayout` хранит
`QLineF`). Кривой линии реза в ScanTailor нет.

## 3. Резервный путь: рез по белому промежутку (`cutAtWhitespace`)

`PageLayoutEstimator::cutAtWhitespace()` (`PageLayoutEstimator.cpp:300-367`) — тоже
**по всей высоте кадра**.

1. **Бинаризация при 300 dpi** глобальным порогом Оцу
   (`to300DpiBinary`, `PageLayoutEstimator.cpp:436-453`). Порог считается один раз на
   стадии fix_orientation по **всему серому кадру**:
   `BinaryThreshold::otsuThreshold(data.grayImage())`
   (`filters/fix_orientation/Task.cpp:87`).
2. `removeGarbageAnd2xDownscale()` (`PageLayoutEstimator.cpp:455-492`) — даунскейл до
   150 dpi, выброс всего, что не связано с чёрточкой длиной ≥4 px, и вычитание «теней»,
   найденных как `openBrick(200×14)` ∪ `openBrick(14×300)` с последующим seed-fill.
3. Оценка перекоса `SkewFinder` и сдвиг (shear) кадра (`PageLayoutEstimator.cpp:327-358`) —
   применяется только при `confidence ≥ GOOD_CONFIDENCE`.
4. `cutAtWhitespaceDeskewed150()` (`PageLayoutEstimator.cpp:382-434`):
   * связные компоненты; **пропускаются меньше 5×5 px и с отношением `height/width > 6`**
     (`:398-402`) — т.е. высокие тонкие штрихи (в том числе остаток линии корешка)
     сознательно игнорируются;
   * оставшиеся заменяются на свои **bounding box'ы**, залитые чёрным (`ccImg`);
   * `SlicedHistogram(ccImg, COLS)` — сумма чёрных пикселей **по каждому столбцу на всю
     высоту** (`imageproc/SlicedHistogram.cpp:69-88`, область = `image.rect()`);
   * `ContentSpanFinder` (`minContentWidth = 2`, `minWhitespaceWidth = 8` px @150 dpi ≈ 1.35 мм)
     режет гистограмму на «полосы контента».

   ⚠️ **Промежуток засчитывается, только если в столбце ровно ноль чёрных пикселей**
   (`core/ContentSpanFinder.cpp:21-25`: `if (histogram[i] != 0) break;`). Допуска нет.
   Один чёрный пиксель в столбце — где угодно по высоте, в том числе в «ухе» — закрывает
   этот столбец как промежуток.
5. `processContentSpansTwoPages()` (`PageLayoutEstimator.cpp:641-732`): для каждого
   промежутка считается масса контента слева и справа, промежутки ранжируются по
   `min/max` этих масс (насколько симметрично он делит разворот). Если лучший
   `ratio < 0.25` — считается, что одна страница пустая. Иначе среди промежутков с
   `ratio ≥ 0.9·best` выбирается **самый широкий**, рез — по его центру.

## 4. Влияние нашей заливки «ушей» на основной путь

Напомню, что делает `crop_pixel_exact()` (`ocr_utils/scan_cropping/cropping.py:63-166`):
базовая заливка (`replicate` — продление краевых пикселей по нормали к сторонам
crop-зоны), затем размытие с σ до `blur_px = 48` px и выцветание к среднему цвету книги
с силой `fade_strength = 1.0`, оба — линейно по нормированному расстоянию
`norm = dist / dist_max`.

### 4.1. Геометрия: где именно проходит линия корешка через «уши»

Повёрнутый на θ crop-bbox `W×H` вписан в осевой холст `W' × H'`. Линия корешка
почти вертикальна и выходит из bbox через верхнюю и нижнюю стороны примерно посередине
их длины. Для правого треугольного «уха» с катетами `(W·cosθ, W·sinθ)` максимальное
расстояние от гипотенузы (стороны bbox) равно `W·sinθ·cosθ`; для «уха» у боковой
стороны — `H·sinθ·cosθ`. Значит:

* `dist_max ≈ max(W, H)·sinθ·cosθ` — нормировка в `cropping.py:151-154`;
* вдоль продолжения корешка расстояние доходит примерно до `(W/2)·sinθ·cosθ`;
* следовательно **на самом дальнем пикселе продолжения корешка**
  `norm ≈ W / (2·max(W, H))` — то есть **≈0.5 для landscape-разворота** (`W > H`) и
  ≈0.3-0.4 для более квадратного кадра.

Пример: `W=6000`, `H=4000`, θ=3° → `dist_max ≈ 6000·0.0523 ≈ 313` px,
глубина хода корешка в ухе ≈ 157 px, `norm_max ≈ 0.5`.

### 4.2. Насколько «уши» поднимают порог `minQuality`

Доля добавленной высоты: `W·sinθ / (W·sinθ + H·cosθ)`.

| θ | W=6000, H=4000 | прирост `minQuality` |
|---|---|---|
| 1° | 105 / 4104 | +2.6 % |
| 2° | 209 / 4207 | +5.0 % |
| 3° | 314 / 4308 | +7.3 % |
| 5° | 523 / 4508 | +11.6 % |

То есть даже при заметном наклоне планка растёт на единицы процентов. Настоящая линия
корешка, проходящая через всю высоту crop-зоны, обычно набирает **3-5-кратный запас**
над `minQuality` (≈5 голосующих пикселей на строку × вес 6-7 ≈ 35 против порога 9 на
строку). Прирост порога на 5-12 % такой запас не съедает.

### 4.3. Насколько размытие ослабляет голоса из «ушей»

Здесь важна деталь реализации (`cropping.py:156-159`):

```python
filled = filled * (1.0 - norm) + blur_downscaled(filled, blur_px, work_side) * norm
```

Это **линейный бленд, а не полное размытие**. Резкая компонента (тонкая тёмная линия)
сохраняется с амплитудой `(1 − norm)`. Размытая компонента при σ, сравнимой с апертурой
детектора (11 px @100 dpi), даёт отклик ≈0 — не отрицательный, просто ничего.

Дополнительно выцветание (`cropping.py:160-163`) при `fade_strength = 1.0` умножает
контраст ещё на `(1 − norm)`. Итого контраст линии в ухе:

```
контраст(norm) ≈ (1 − norm)²  ×  исходный
```

На самом дальнем пикселе продолжения корешка (`norm ≈ 0.5`) это **≈0.25 исходного
контраста**, у шва — 1.0. В среднем по «уху» — примерно 0.5.

Что это даёт в весах Хафа: отклик 80 → вес 7; отклик 20 → вес 5. **Потеря ~30 % на
пиксель**, а не 75 %. Голоса из «ушей» продолжают поступать; исчезают они только там,
где отклик падает до ≤1, т.е. при исходном отклике ≤4 — для настоящей тени корешка
это не наш случай.

### 4.4. Соотношение σ и апертуры детектора

`blur_px = 48` px в исходном разрешении. В 100-dpi сетке ScanTailor:
`σ₁₀₀ = 48 · 100 / dpi_orig`. При 400 dpi это 12 px — примерно равно апертуре 11 px.
Значит размытая компонента гарантированно даёт нулевой отклик при любом реалистичном
DPI, и весь вклад «уха» держится на резкой компоненте с множителем `(1 − norm)²`.
Это хорошая новость: **размытие может только разбавить голоса, но не исказить
геометрию линии**.

### 4.5. Численный расчёт голосов Хафа

Важная деталь, которую нельзя пропустить: Хаф копит голоса **по корзинам расстояния
шириной 5 px** (`lineThickness = 5.0`, `VertLineFinder.cpp:101`). Поэтому суммарный
отклик по всему сечению не значит ничего — размазанный по x отклик раскладывается по
разным корзинам и **не складывается** для одной линии. Считать надо сумму весов внутри
одной 5-px корзины.

Модель: сечение поперёк линии, бумага 225, дно тени корешка 115 (глубина 110), исходные
400 dpi; линейный бленд по `norm` + выцветание `fade`; даунскейл до 100 dpi; отклик
`max₁₁(I) − I`; веса по таблице `buildWeightTable`. `norm = 0.5` — самый дальний пиксель
продолжения корешка (см. §4.1). **Порог — 9 голосов на строку.**

Голоса в лучшей корзине на одну строку кадра, ширина корешка 1.5 мм, `norm = 0.5`:

| | fade=0 | fade=0.3 | fade=0.5 | fade=1.0 |
|---|---|---|---|---|
| **blur=0** | 35 | 35 | 35 | 32 |
| **blur=16** | 35 | 35 | 30 | 30 |
| **blur=32** | 33 | 30 | 30 | **28** |
| **blur=48** | 33 | 30 | 30 | **28** |

Та же таблица по ширине корешка (при `fade = 1.0`):

| корешок | norm | blur=0 | blur=16 | blur=32 | blur=48 | blur=64 |
|---|---|---|---|---|---|---|
| 0.5 мм | 0.25 | 27 | 27 | 27 | 27 | 27 |
| 0.5 мм | 0.5 | 25 | 24 | 22 | 22 | 22 |
| 1.0 мм | 0.25 | 33 | 33 | 33 | 33 | 33 |
| 1.0 мм | 0.5 | 31 | 28 | 28 | 28 | 26 |
| 2.0 мм | 0.25 | 35 | 34 | 32 | 30 | 30 |
| 2.0 мм | 0.5 | 30 | 30 | 25 | 25 | 25 |
| 3.0 мм | 0.25 | 30 | 30 | 30 | 30 | 30 |
| 3.0 мм | 0.5 | 30 | 28 | 25 | 25 | 25 |

Выводы:

* при `norm = 0` (у самого шва) размытие не влияет вообще — там его вес нулевой;
* **отклик насыщается при σ ≈ 16-32 px**; между 32 и 48 разницы нет ни в одной строке
  таблицы. Причина — бленд: резкая компонента выживает с амплитудой `(1−norm)`
  независимо от σ, а размытая при любой достаточно большой σ даёт нулевой отклик;
* разброс во всех клетках — 22…35 при пороге **9**. Даже худшая клетка держит
  2.4-кратный запас, и это на *самом дальнем* пикселе «уха»; ближе к шву запас больше;
* заметный вклад в потери даёт скорее `fade`, чем `blur` (столбец fade=0 vs fade=1.0
  при blur=0: 35 → 32; строка blur=0 vs blur=48 при fade=0: 35 → 33).

### 4.6. Итоговая оценка для основного пути

Суммарно: «уши» дают ~5-12 % высоты, их вклад ослаблен примерно на 10-25 %, порог поднят
на те же 5-12 %. **Итоговая потеря запаса по `minQuality` — порядка 10 %** при исходном
запасе 3-4 раза. Для кадра, где корешок вообще виден, это не решающий фактор.

**Решающие факторы — другие:**

1. **Изгиб продолженной линии.** Корзина Хафа по расстоянию — 5 px @100 dpi. Линия,
   уведённая в сторону больше чем на 5 px, раскладывает голоса по нескольким корзинам, и
   качество падает кратно числу корзин. Ровно это и делал `voronoi_fill` веером у
   выпуклых углов — уже описано в `background_fill.py:265-283` и вылечено переходом на
   `replicate`. Это на порядок опаснее размытия.
2. **Наклон книги > 7°.** Жёсткая отсечка: `maxAngle = 7.0`
   (`VertLineFinder.cpp:102`). При большем наклоне корешок не найдётся вообще, и
   ScanTailor свалится в резервный путь. У нас угол книги как раз и есть наклон линии в
   `pixel-exact`-холсте, так что это прямое ограничение на режим.
3. **Незаполненные чёрные области холста.** `crop_pixel_exact` заполняет их
   (`cropping.py:104-105`), и это критично: чёрный прямоугольник дал бы идеальные
   вертикальные края с максимальным откликом. Частично спасает отсечка «дальше 0.3·W от
   центра», но только частично.
4. **Отсутствие или неверный DPI в выходном файле.** Все пороги ScanTailor — в
   физических единицах: 3.5 мм поля, приведение к 100/150/300 dpi. `preScaleToDpi`
   (`ImageTransformation.cpp:25-28`) при нулевом DPI **не масштабирует вовсе**, и
   детектор с апертурой 11 px начинает смотреть на полноразмерный кадр, где тень
   корешка шире 11 px → `maxH ≈ maxV` → отклик схлопывается в ноль. Это отказ куда более
   тяжёлый, чем любое размытие. У нас DPI пишется только при `--force-dpi`
   (`image_io.py:37-57`) — под ScanTailor его надо задавать обязательно.

## 5. Влияние на резервный путь (по белым промежуткам) — размытие здесь скорее помогает

Резервный путь включается, только если корешок не найден. Продолженная в «ухо» тёмная
линия корешка попадает **ровно в тот столбец**, который должен быть белым промежутком, а
промежуток требует **строгого нуля** чёрных пикселей на всю высоту
(`ContentSpanFinder.cpp:21-25`). Спасает фильтр связных компонент: `height/width > 6` →
компонента игнорируется (`PageLayoutEstimator.cpp:400-402`).

Интуиция «размытие раздует линию и она перестанет отбраковываться этим фильтром»
**не подтверждается расчётом**. Размытие здесь — линейный бленд, и размытая компонента
получается не только шире, но и во столько же раз мельче: глубина гауссова следа от
полосы ширины `w₀` при σ равна примерно `A·w₀/(σ·√2π)`. При w₀ ≈ 2 px @150 dpi и σ₁₅₀ = 12
(это blur = 32 при 400 dpi) это ~6 % от `A` — глобальный порог Оцу такой след не берёт,
он остаётся белым. Чернеет только резкое ядро, а оно от размытия **сужается**, потому что
бленд уменьшает его амплитуду.

Расчёт для корешка 1.5 мм, глубина 110, бумага 225, порог Оцу 170, наклон 2°
(высота продолжения в «ухе» ≈ 39 px @150 dpi):

| blur | norm | ширина чёрного, px | h/w | что делает ScanTailor |
|---|---|---|---|---|
| 0 | 0.25 | 7 | 5.6 | **попадает в `ccImg`** → промежуток закрыт |
| 0 | 0.5 | — весь белый | — | промежуток цел |
| 16 | 0.25 | 5 | 7.9 | отбракован → промежуток цел |
| 32 | 0.25 | 5 | 7.9 | отбракован → промежуток цел |
| 48 | 0.25 | 5 | 7.9 | отбракован → промежуток цел |

То есть в этой модели **опасен как раз `blur = 0`**: там чёрное ядро шире, `h/w` падает
ниже 6, и bounding box линии закрывает нужный столбец. Небольшое размытие уводит `h/w`
обратно за порог.

Оговорка: `h/w` линейно зависит от высоты «уха», т.е. от наклона. При θ = 1° высота
≈20 px, и `h/w` мало́ при любом blur — линия попадёт в `ccImg`. Но при таком наклоне
«уши» и так почти отсутствуют, а корешок отлично находится основным путём.

Дополнительно: глобальный порог Оцу считается по **всему** кадру, включая заливку
(`fix_orientation/Task.cpp:87`). Светлая заливка на 5-12 % площади добавляет массы в
светлую моду гистограммы и слегка сдвигает порог. Эффект мал, но он есть — ещё один
довод не делать заливку резко отличающейся по яркости от бумаги.

## 6. Практические рекомендации для `--crop-mode=pixel-exact` под ScanTailor

| Параметр | Рекомендация | Почему |
|---|---|---|
| `--crop-fill-method` | `replicate` (текущий default) | Вороной загибает корешок веером у углов; 5-px корзина Хафа это наказывает кратно. Уже зафиксировано в `background_fill.py:265-283`. |
| `--crop-fill-blur-px` | **любое из 0…48, разница несущественна**; 16-32 чуть лучше нуля | Основному пути стоит ~10 % запаса (28-33 голоса против порога 9), причём отклик насыщается при σ≈16 и значения 32/48 неразличимы (§4.5). Резервному пути небольшое размытие даже помогает — сужает чёрное ядро и возвращает `h/w` за порог отбраковки (§5). |
| `--crop-fill-fade` | 0…0.5 вместо 1.0 | Из двух эффектов именно выцветание съедает больше голосов (§4.5, столбцы fade). Понижение до 0.3-0.5 возвращает 2-4 голоса на строку почти бесплатно. |
| `--force-dpi` | **обязательно задавать**, реальный DPI скана | Без DPI ScanTailor не приводит кадр к 100 dpi, апертура 11 px оказывается уже линии корешка и отклик схлопывается. Самая тяжёлая из возможных поломок. |
| Угол книги | следить, чтобы \|θ\| ≤ 7° | Жёсткий предел Хафа (`VertLineFinder.cpp:102`). При большем наклоне `pixel-exact` под ScanTailor неприменим, нужен `--crop-mode=rotate`. |
| Незалитые зоны | не допускать | Чёрные прямоугольники дают ложные вертикали максимальной силы. |

> ⚠️ Комментарий в `ocr_utils/scan_cropping/cropping.py:94-96` («под разбивку в
> ScanTailor размытие лучше держать в нуле») расчётом §4.5/§5 не подтверждается и его
> стоит поправить — но только после проверки на реальных кадрах (см. ниже), потому что
> модель не учитывает шум, JPEG-артефакты и неоднородность самой тени корешка.

### Как проверить на своих кадрах

ScanTailor умеет сбрасывать промежуточные картинки: `page_split/Task.cpp:97-99`
создаёт `DebugImagesImpl`, если включён debug-режим. Интересующие метки:
`gray100`, `vert_raster_lines`, `short_segments_removed`, `hough_space`, `vector_lines`
(`VertLineFinder.cpp:44,92,98,132,187`) и для резервного пути `bw300`, `no_garbage`,
`ccImg`, `spans`, `spans_refined` (`PageLayoutEstimator.cpp:314,319,408,420,431`).

Достаточно посмотреть `vector_lines` для двух вариантов кадра — с `--crop-fill-blur-px 0`
и с 48 — и сравнить, есть ли красная линия на корешке. Если линия есть в обоих случаях,
размытие для этого набора не критично; если пропадает — включается резервный путь,
и тогда стоит смотреть `spans_refined`.
