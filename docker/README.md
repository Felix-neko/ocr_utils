# Локальный CVAT для разметки архива МТС

Разметка растровых изображений (прямоугольники) и нежелательных объектов —
библиотечных печатей и рукописных надписей (кисть → битовая маска) на сканах
журнала «Материально-техническое снабжение».

## Что внутри

| Файл | Назначение |
|------|-----------|
| `.env` | Версия CVAT, хост, путь к картинкам, учётки, имя организации. |
| `docker-compose.override.yml` | Монтирует папку картинок в `/home/django/share` (ro); отключает аналитику (grafana/vector). |
| `up.sh` | Клонирует CVAT, поднимает контейнеры, заводит пользователей и организацию. |
| `down.sh` | Останавливает CVAT (`--wipe` — с удалением данных). |
| `create_users.py` | Django-скрипт: admin, user, организация, членства. |
| `cvat-src/` | Клон апстрим-CVAT (создаётся автоматически, в git не хранится). |

Картинки, проект, задачи и джобы готовит подсистема `ocr_utils.scan_markup`
(команда `to-cvat`), а не этот каталог: разбиение по годам и выпускам знает
только она. Здесь — сам сервер и учётки.

## Кто что видит

`admin` — владелец организации, видит проекты, задачи и джобы целиком. `user` — роль
**worker**, и она показывает только то, что назначено лично: вкладки Projects и Tasks у неё
всегда пусты, а работать надо во вкладке **Jobs**.

Джобы назначаются при заливке ключом `--annotator user` (`scan_markup to-cvat`). Без него
разметчик войдёт и не увидит ничего — ни ошибки, ни объяснения, просто пустой список.

Если удобнее ходить по годам и выпускам, а не по плоскому списку джобов, роль повышается до
**`maintainer`** — и только до неё. Проверено на живом сервере 2.70.0: `worker` и
`supervisor` видят ровно то, что назначено лично (`projects: 0, tasks: 0`), и разница между
ними не в видимости, а в праве заводить задачи. Список задач открывается лишь на
`maintainer`:

| роль | projects | tasks | jobs |
|---|---|---|---|
| worker | 0 | 0 | 123 (назначенные) |
| supervisor | 0 | 0 | 123 |
| maintainer | 1 | 11 | 123 |

```bash
# id членства — из /api/memberships?org=masochists
curl -s -u admin:admin -X PATCH "http://localhost:8080/api/memberships/<id>" \
     -H 'Content-Type: application/json' -d '{"role": "maintainer"}'
```

## Размечаем уменьшённые копии, а не оригиналы

**Разметка ведётся по уменьшенным копиям** (~1100×900 вместо ~4600×3600), а не по
оригиналам. Лежат они в `/home/felix/Projects/mts_markup/cvat_share` — на SSD, потому
что превью листаются постранично. На этот каталог указывает `IMAGES_DIR` в `.env`,
он же должен быть `--share-root` у `scan_markup to-cvat`, иначе сервер картинок не
найдёт: задачи заводятся «из share», по сети файлы не передаются.

Почему: CVAT не умеет масштабировать кадры сам. `image_quality` задаёт только
JPEG-качество пережатия, разрешение чанка всегда 1:1 с исходником. На
полноразмерных сканах CVAT считал `chunk_size` равным 5 кадрам и резал чанки на
лету (`storage_method=cache`), отчего листание тормозило.

> ⚠️ **Маски и прямоугольники приходят из CVAT в координатах уменьшенных кадров.
> Перед применением к оригиналам умножай на `divisor` из базы: он свой у каждой
> полосы, `round(dpi / 75)` — для 600 dpi это 8.**

Оригиналы лежат в синхронизируемой папке Яндекс.Диска — писать туда ничего
нельзя, улетит в облако. Поэтому копии кладутся рядом, на SSD.

> ⚠️ **Каталог `IMAGES_DIR` нельзя переименовывать при живых контейнерах.** Docker
> разрешает bind-mount в inode при СОЗДАНИИ контейнера, а не при каждом обращении.
> Переименуете `IMAGES_DIR` или любого его родителя (например, ради бэкапа) — и
> `/home/django/share` внутри контейнера останется висеть на старом каталоге, хотя
> `docker inspect` покажет новый путь. Снаружи всё выглядит правильно, а `to-cvat`
> падает на создании задачи с `FileNotFoundError: /home/django/share/...`.
>
> Проверка — сравнить inode снаружи и внутри:
> ```bash
> stat -c '%i' /home/felix/Projects/mts_markup/cvat_share
> docker exec cvat_mts_server stat -c '%i' /home/django/share
> ```
> Лечится пересозданием контейнеров: `./down.sh` (без `--wipe`, данные сохраняются),
> затем `./up.sh`. И проверьте, не осталась ли в CVAT задача с нулём кадров от упавшего
> прогона — её надо удалить, иначе `to-cvat` примет её за готовую.

Готовит их `scan_markup to-cvat` (идемпотентно, готовые файлы пропускаются);
целевое разрешение задаётся опцией `--cvat-dpi` на шаге `detect`.

## Запуск

```bash
cd docker
./up.sh
```

Первый запуск долгий: тянутся docker-образы (несколько ГБ) и генерируются
чанки для ~6500 картинок. Скрипт идемпотентен — можно перезапускать.

Остановка:

```bash
./down.sh          # данные сохраняются
./down.sh --wipe   # полный сброс (БД, разметка, чанки). Оригиналы не трогаются.
```

## Где размечать

1. Открыть **http://localhost:8080**.
2. Войти как **user / user**.
3. Вверху переключиться на организацию **«Клуб мазохистов»**.
4. Вкладка **Tasks** → своя задача (назначена автоматически) → **Job**.
5. В редакторе:
   - **Растровое изображение** — инструмент прямоугольника;
   - **Библиотечная печать**, **Рукописная надпись** — кисть (brush),
     результат сохраняется как битовая маска.

Администрирование (создание проектов/задач, панель Django) — под **admin / admin**,
в т.ч. `http://localhost:8080/admin`.

## Разбиение на задачи

1 задача = годовой комплект, внутри по одному job'у на выпуск (границы задаются
`job_file_mapping` при создании задачи). Заводит их `scan_markup to-cvat` «из share» —
файлы не загружаются через браузер, CVAT читает их с диска и делает свои копии-чанки.

## Заметка о правах `user`

Ограничение «только разметка» реализовано ролью **worker** в организации
«Клуб мазохистов»: worker видит лишь назначенные ему job'ы и не может создавать
задачи/проекты внутри организации. На уровне инстанса CVAT не запрещает любому
залогиненному пользователю заводить проекты в личном пространстве — жёсткий
запрет потребовал бы правки OPA-политик. Для сценария «вся работа в организации»
роли worker достаточно.
