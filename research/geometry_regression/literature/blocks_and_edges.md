# Обзор: сегментация текстовых блоков и меры ровности кромок

Контекст: бинарные рендеры 150–300 dpi, пара «до/после» коррекции FineReader, нужно поймать случай «строки выровнялись, а кромка выключенного блока стала рваной/наклонной». В единицах: pitch — межстрочный шаг (≈ 1.2–1.4 высоты строки), x-height, ширина пробела.

---

## Тема 1. Сегментация страницы на связные (невыпуклые) текстовые блоки

### 1.1 RLSA / smearing (Wong, Casey, Wahl 1982) и адаптивный ARLSA (Nikolaou, Gatos 2010)
**Суть.** Бинарную маску «замазывают» по горизонтали (заполняют белые пробеги короче C_h) и по вертикали (короче C_v), берут AND, затем связные компоненты (СК) — это блоки. Вертикальный порог задаёт, какие межстрочные/межабзацные «ямы» сливаются. ARLSA заменяет фиксированные C на условия по паре соседних СК: отношение высот ≤ T_height (≈2.5), горизонтальная дистанция ≤ min(h1, h2), вертикальная ≤ max(h1,h2)/2 — так не склеиваются строка с заголовком и колонка с соседней.
**Параметры.** C_h ≈ 1–1.5 высоты строки (сшивает слова, не колонки: межколонник обычно ≥ 2–3 x-height); C_v ≈ k·pitch, k = 2–3 — ровно ваша «не проваливаться в 2–3 интервала».
**Реализация.** `pythonRLSA` (чистый Python, медленно), но по сути это `cv2.morphologyEx(MORPH_CLOSE)` с прямоугольным ядром (1×C_h) и (C_v×1) — своё на OpenCV быстрее и на порядок. ARLSA — только в статьях ([Nikolaou et al.](https://www.sciencedirect.com/science/article/abs/pii/S0262885609002005)).
**Применимость.** Плюс: даёт именно невыпуклую связную область, контур которой обходит абзацные отступы и висячие строки (после закрытия по вертикали высотой 2–3 pitch отступ в 1 строку заполняется, дыра под заголовок в 5 pitch — нет). Минус: чувствителен к наклону (колонки при скосе > 1–2° начинают сливаться), а вам как раз нужно ловить наклон кромки — поэтому пороги брать по pitch, а не «на глаз», и делать сглаживание на масках *обеих* версий одинаково. Лучший кандидат на «липкую ленту» по бинарной маске.

### 1.2 XY-cut / проекции (Nagy, Seth) и whitespace-cuts (Baird)
**Суть.** Рекурсивно режут страницу по самым широким пустым полосам в проекциях. Результат — только прямоугольники (Manhattan layout).
**Реализация.** Тривиально на numpy; есть в `layoutparser`/`pdfminer`-подобных обвязках.
**Применимость.** Для вашего случая не годится как финальный контур (блок с отступами и рваной кромкой у него всё равно прямоугольник), но полезен как грубое деление на колонки перед 1.1 — вертикальная закрытая маска тогда не перепрыгнет через межколонник.

### 1.3 Docstrum (O'Gorman 1993)
**Суть.** Bottom-up: для каждой СК k ближайших соседей (k≈5), гистограммы углов и расстояний → оценка скоса, межсимвольного и межстрочного шага; транзитивное замыкание пар «в одной строке» → строки; строки сливаются в блоки по порогам параллельности и перекрытия.
**Параметры.** k, порог расстояния «в строке» (≈ 1–2 межсимвольных шага), «между строками» (≈ 1–1.5 pitch) — всё измеряется самим методом по гистограммам.
**Реализация.** Готового поддерживаемого Python-пакета нет; есть учебные реализации (упоминания в [BobLd/DocumentLayoutAnalysis](https://github.com/BobLd/DocumentLayoutAnalysis), «simple-docstrum» для PDF); на scipy `cKDTree` пишется за вечер.
**Применимость.** Плюс: устойчив к скосу, сам оценивает pitch — полезно как калибратор параметров для 1.1/1.9. Минус: выход — группы строк, контур блока всё равно надо строить отдельно (обычно берут объединение bbox строк, т.е. невыпуклость есть, но абзацные отступы торчат).

### 1.4 Area Voronoi (Kise, Sato, Iwata 1998)
**Суть.** По точкам с контуров СК строится диаграмма Вороного, рёбра внутри СК удаляются; остальные рёбра помечаются расстоянием между СК и отношением площадей; по гистограмме расстояний находятся пороги Td1 (межсимвольный), Td2 (межстрочный), отношение площадей Ta; ребра с меньшими значениями удаляются — оставшиеся рёбра и есть границы блоков (произвольной формы, не Manhattan, устойчиво к скосу).
**Параметры.** Шаг выборки точек по контуру, Td1/Td2 из гистограммы (ищутся автоматически), Ta ≈ 40.
**Реализация.** [IPOL 2026, Gardella & Ramírez](https://www.ipol.im/pub/art/2026/591/) — воспроизводимый код с демо (архив на странице); в [сравнении Shafait–Keysers–Breuel DAS 2006](http://keysers.net/daniel/files/Shafait--Layout-Analysis-Comparison--DAS2006.pdf) — один из лучших классических методов.
**Применимость.** Плюс: границы блока — ломаная линия из рёбер Вороного, по определению «липкая»: идёт по середине зазора и не заходит в межстрочные промежутки, если они меньше Td2. Минус: чувствителен к пунктуации, буквицам, таблицам (отмечено в IPOL-статье); граница проходит *между* блоками, а не по кромке текста — для вашей меры нужно потом взять точки, ближайшие к рёбрам. Дороже RLSA, но лучше держит наклон.

### 1.5 Maximal whitespace rectangles (Breuel 2002) → OCRopus `gpageseg` / `kraken.pageseg`
**Суть.** Branch-and-bound поиск максимальных пустых прямоугольников на фоне; высокие узкие — межколонники; далее строки ищутся с ограничением «не пересекать межколонник». В ocropy/kraken legacy: `compute_white_colseps`/`compute_black_colseps`, масштаб = медианный размер СК, потом «gradmaps» и сегментация строк.
**Параметры.** Минимальные ширина и высота/aspect межколонника (в единицах scale), максимальное число колонок.
**Реализация.** [kraken/pageseg.py](https://github.com/mittagessen/kraken/blob/main/kraken/pageseg.py) (Python 3), [ocropy gpageseg](https://github.com/ocropus-archive/DUP-ocropy/blob/master/ocropus-gpageseg); статья [Breuel «Two geometric algorithms»](https://link.springer.com/chapter/10.1007/3-540-45869-7_23).
**Применимость.** Даёт колонки и строки, не полигон блока. Полезен как надёжный делитель на колонки перед морфологией. Kraken legacy сегментер выдаёт bbox строк — годится как источник x_left/x_right для меры темы 2, но у вас уже есть surya-строки.

### 1.6 Tesseract: tabfind → ColPartition (Smith, ICDAR 2009 «Hybrid page layout analysis via tab-stop detection»)
**Суть.** По кромкам СК ищут вертикальные «табуляторы» (TabVector) двух типов: **aligned** (кромки на одной вертикали) и **ragged** (крайние кромки строк, образующие рваную границу). Затем СК группируются в ColPartition (фрагменты строк), партиции — в колонки; для каждой партиции отмечается, к каким табуляторам она прижата слева/справа. Далее в `paragraphs.cpp` по lmargin/rmargin строк определяется JUSTIFICATION_LEFT/RIGHT/CENTER и различаются «ragged-right» (eop_threshold = 0) и «justified» (eop_threshold > 0 — короткая строка означает конец абзаца).
**Параметры** ([alignedblob.cpp](https://github.com/tesseract-ocr/tesseract/blob/main/src/textord/alignedblob.cpp), [tabfind.cpp](https://github.com/tesseract-ocr/tesseract/blob/main/src/textord/tabfind.cpp)): допуск aligned-табулятора `kAlignedFraction = 1/32` разрешения (≈9 px при 300 dpi ≈ 0.8 мм), минимум `kMinAlignedTabs = 4` точки, `kMinRaggedTabs = 5`; обязательный «жёлоб» слева/справа от табулятора: 0.75 высоты блоба (aligned), 1.0 (ragged); вертикальный поиск 3–12 высот блоба, для ragged до 25; `kMaxSkewFactor = 15`. В [paragraphs.cpp](https://github.com/tesseract-ocr/tesseract/blob/main/src/ccmain/paragraphs.cpp) допуск выравнивания строки = `InterwordSpace` блока.
**Реализация.** Только внутри Tesseract (C++), через API наружу выходят блоки/параграфы и `justification` (`ResultIterator`/hOCR), табуляторы — нет. Наиболее готовая инженерная модель «aligned vs ragged» из всех.
**Применимость.** Пороги Tesseract — хороший ориентир для калибровки: кромка «ровная», если ≥ 4 строки укладываются в ±res/32; допуск отступа = ширина пробела. Сам движок для парного сравнения запускать накладно и нестабильно (выход меняется от версии к версии).

### 1.7 Нейросетевые сегментаторы с полигонами: kraken blla, dhSegment, P2PaLA, Laypa
**Суть.** Пиксельная семантическая сегментация (регионы/базовые линии) → тепловая карта → пороговая бинаризация → СК → контур/полигон (в Loghi/Laypa — по столбцам, в kraken — `vectorize_regions`). Регионы получаются произвольной формы, границы «липнут» к тексту ровно настолько, насколько научили.
**Реализация.** [kraken](https://kraken.re/6.0.0/advanced/segmentation.html) (модели для печатных страниц есть, `blla.mlmodel`), [Laypa](https://dl.acm.org/doi/fullHtml/10.1145/3604951.3605520), dhSegment, [YALTAi](https://arxiv.org/pdf/2207.11230).
**Применимость.** Минус для вашей задачи: граница региона задаётся сетью с тепловой картой на пониженном разрешении — сама кромка сглажена и не годится как мера; плюс: полигон региона — хорошая маска «где блок», дальше кромку мерить по СК/строкам внутри неё.

### 1.8 Детекторы раскладки (прямоугольные): DocLayout-YOLO, LayoutParser/Detectron2, docTR, surya layout
**Суть.** Object detection по классам DocLayNet/PubLayNet: text, title, table, figure, list. Только bbox.
**Реализация.** [DocLayout-YOLO](https://arxiv.org/html/2410.12628v1) (mAP 79.7 DocLayNet, 85 fps), `layoutparser` (Detectron2 модели), docTR, surya (уже в проекте).
**Применимость.** Как затравка «где блоки» — да, особенно surya, который у вас уже кэшируется по вариантам страницы. Как контур — нет: рваная кромка и отступы в bbox не видны, наклон на ±0.5° — тоже.

### 1.9 Alpha-shape / concave hull по облаку точек
**Суть.** Alpha-shape (Edelsbrunner): из триангуляции Делоне выкидывают треугольники с описанной окружностью радиусом > 1/α — «диск радиуса r = 1/α вырезает пустоты, куда пролезает». Варианты: χ-shape (Duckham et al. 2008, удаление длинных внешних рёбер Делоне; так же устроен `shapely.concave_hull(ratio)` из GEOS ≥ 3.11); k-NN concave hull (Moreira & Santos 2007; `concaveman`, `concave_hull`, `concavity`); ball-pivoting в 2D — то же, что alpha-shape с радиусом шара.
**Параметры.** Радиус r: диск входит в щель шириной > 2r. Чтобы не проваливаться в межстрочные промежутки до 3 pitch, но проваливаться в дыры побольше: r ≈ 1.5 pitch. Отступ абзаца (высота 1 строка, глубина ≈ 1 em) диском такого радиуса не берётся — контур идёт по огибающей. `shapely.concave_hull(ratio)` параметризуется не в мм, а долей между min и max длиной ребра — для калиброванной задачи неудобен; `alphashape.alphashape(points, alpha)` — alpha = 1/r в пикселях.
**Реализация.** [alphashape](https://alphashape.readthedocs.io/en/latest/readme.html) (медленный на 10⁴+ точках, но точек можно брать 4 угла bbox каждой СК/слова — это сотни), [shapely.concave_hull](https://shapely.readthedocs.io/en/2.1.2/reference/shapely.concave_hull.html), [concave-hull (Rust, k-NN)](https://github.com/EthanJamesLew/concave-hull), [concavity](https://github.com/mlichter2/concavity), [обзор алгоритмов в JTS](http://lin-ear-th-inking.blogspot.com/2022/01/concave-hulls-in-jts.html).
**Применимость.** Плюс: изотропен — не зависит от скоса, параметр физически прозрачен (радиус диска). Минус: точки нужно подавать по блоку, а не по странице (иначе alpha-shape сольёт колонки, если межколонник < 2r; при r = 1.5 pitch ≈ 6–7 мм это реальный риск в журнале). То есть блоки всё равно сначала выделять (1.1/1.4), а alpha-shape применять к их точкам как чистовой контур. Для наклонных блоков — лучше морфологии.

### 1.10 Морфологическое закрытие + контур (прямая реализация «липкой ленты»)
**Суть.** Та же идея, что 1.1, но на маске *слов/строк* (после горизонтального RLSA): `MORPH_CLOSE` анизотропным ядром высотой k·pitch и шириной ~1 em, затем `cv2.findContours` с `CHAIN_APPROX_NONE`, при желании `MORPH_OPEN` ядром ~ (1 em × 1 pitch), чтобы срезать одиночные «усы» — висячие короткие строки, если их не нужно учитывать.
**Параметры.** Высота ядра закрытия h = k·pitch — ровно порог «ямы»: полости высотой ≤ h заполняются, больше h — остаются (щель под подзаголовок в 4–5 pitch останется, и блок распадётся на два). Ширина ядра w — глубина отступа, которую надо «залипить» (1–1.5 em; больше — залипнет межколонник).
**Реализация.** OpenCV/scikit-image (`skimage.morphology.closing` с `rectangle(h, w)`), всё есть.
**Применимость.** Самый дешёвый и предсказуемый способ; недостаток — оси ядра привязаны к пикселям, при скосе > 1° замыкание по вертикали начинает захватывать межколонник (если w велика) или пропускать (если строки уезжают). Лечится оценкой скоса (Docstrum/проекции) и поворотом маски перед закрытием — вам нужен наклон *кромки относительно строк*, так что поворот на общий скос ничего не портит.

### 1.11 Активные контуры: morphological snakes, Kass-snake с жёсткостью
**Суть.** `skimage.segmentation.morphological_chan_vese` / `morphological_geodesic_active_contour` — эволюция бинарной маски через дилатацию/эрозию с параметром `smoothing` (число проходов кривизны) и `balloon` (±давление). Классический Kass-snake `skimage.segmentation.active_contour(alpha, beta)`: alpha — натяжение (упругость), beta — жёсткость (штраф за изгиб) — это буквально «резиновая лента с жёсткостью».
**Параметры.** Для GAC на бинарной маске: инициализация — выпуклая оболочка блока, balloon < 0 (сжимается), smoothing 1–4; но масштаб «сколько pitch не проваливаться» задаётся косвенно (через число итераций/сглаживание), физического параметра «радиус» нет. У Kass-snake beta регулирует кривизну, но снаружи блока нет «края» в терминах градиента — нужно строить edge-map через distance transform.
**Реализация.** [scikit-image morphsnakes](https://scikit-image.org/docs/stable/auto_examples/segmentation/plot_morphsnakes.html), [Borda/morph-snakes](https://github.com/Borda/morph-snakes).
**Применимость.** Минус: параметры не калибруются в pitch; результат зависит от инициализации и числа итераций; на бинарной маске текста (штрихи, а не сплошная область) GAC «протекает» между буквами. Для отчётов/картинок можно, для метрики — нет. Не рекомендую.

## Тема 2. Меры ровности кромок и наклона; парное сравнение

### 2.1 Tesseract: aligned vs ragged табулятор + justification в paragraphs.cpp
**Суть/параметры.** См. 1.6: кромка считается «выровненной», если ≥ 4 кромок строк укладываются в ±res/32 вокруг прямой (с допуском на общий скос до `kMaxSkewFactor`) и слева/справа от неё есть жёлоб ≥ 0.75 высоты блоба; «ragged» — ≥ 5 крайних кромок с допуском в ширину пробела. В paragraphs.cpp допуск выравнивания = interword space блока; justified отличают от ragged-right по тому, что «первое слово следующей строки влезло бы в остаток предыдущей» (`FirstWordWouldHaveFit`).
**Применимость.** Готовой функции нет, но это лучшие «отраслевые» пороги: 0.8 мм на 300 dpi для выровненной кромки; всё, что хуже ширины пробела, — рваное. Патенты Xerox/Adobe ([US 5848184](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/5848184), [US 7555711](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/7555711)) описывают ту же схему: левые/правые кромки строк проверяют на попадание на прямую, блок «justified», если ≥ 50 % строк прижаты к обеим сторонам. Публикаций ABBYY по этой части нет (закрытый движок); в их патентах по раскладке — та же логика «margin = линия по началам строк».

### 2.2 Робастная прямая по началам/концам строк: Theil–Sen, Siegel, RANSAC, Huber
**Суть.** x_i = координата левой (правой) кромки строки i, y_i = её baseline. Прямая x = a·y + b: `scipy.stats.theilslopes` (медиана попарных наклонов, breakdown 29 %), `scipy.stats.siegelslopes` (повторная медиана, breakdown 50 % — лучше, когда половина строк «короткие»), `sklearn.linear_model.RANSACRegressor`/`skimage.measure.ransac(LineModelND)` с residual_threshold в пикселях. Меры: **tilt** = atan(a) в градусах (или мм на высоту блока), **roughness** = MAD/std остатков (px, доля x-height), **доля инлайеров** при допуске res/32.
**Параметры.** Допуск инлайера — res/32 (Tesseract) или 0.25·x-height; для justified-блока исключать последние строки абзацев (ширина строки < 0.9 ширины блока или зазор до правой кромки > 1 пробела); для левой кромки исключать первые строки абзацев (отступ ≈ 1 em) — проще: брать оба края и в каждом отбрасывать 10–20 % крайних значений или использовать Siegel.
**Реализация.** scipy/sklearn/scikit-image, всё есть.
**Применимость.** Основа метрики. Наклон и разброс разделяются явно: «строки выровнялись, кромка стала наклонной» = |tilt_B| − |tilt_A| > порог; «рваной» = MAD_B − MAD_A > порог.

### 2.3 Локальное «дрожание» соседних строк: successive differences / von Neumann ratio
**Суть.** Помимо остатков от прямой, считают Δx_i = x_{i+1} − x_i: MSSD = mean(Δx²)/2, отношение фон Неймана VN = MSSD/var (≈2 для белого шума, ≈0 для плавного тренда/волны, ≈4 для «зигзага»). Плавно ломаная кромка (низкочастотная порча, VN мал, MAD от прямой велик) и рваная кромка (высокочастотная, медиана |Δx| велика) — разные симптомы коррекции FineReader; порча «ломаный край» проявится как рост MAD остатков при малом росте |Δx|; «рваный» — наоборот.
**Реализация.** numpy; тест — [DescTools VonNeumannTest](https://andrisignorell.github.io/DescTools/reference/VonNeumannTest.html) (R, для справки).
**Применимость.** Дешёвая добавка к 2.2, даёт две ортогональные шкалы: jitter = median|Δx| (в долях x-height) и wave = MAD остатков от прямой.

### 2.4 Page frame detection (Shafait, van Beusekom, Keysers, Breuel, IJDAR 2008)
**Суть.** Рамка страницы = прямоугольник, подбираемый геометрическим matching'ом (RAST, branch-and-bound) так, чтобы максимизировать число начал/концов текстовых строк, лежащих вблизи левой/правой сторон рамки (эксплуатируется свойство «выровненности» текста в структурированных документах); без предположения о белом зазоре между шумом и текстом, без подстройки параметров. Развитие: [для разворотов](https://www.researchgate.net/publication/220933023_Page_frame_detection_for_double_page_document_images), [для камерных снимков (Bukhari 2011)](https://link.springer.com/chapter/10.1007/978-3-642-29364-1_10), [робастная версия для исторических документов 2018](https://www.researchgate.net/publication/329760609_A_Robust_Page_Frame_Detection_Method_for_Complex_Historical_Document_Images).
**Параметры.** Допуск попадания кромки строки на сторону рамки (в оригинале — доли высоты строки), допустимый угол.
**Реализация.** Кода нет (внутри старого OCRopus на C++ был RAST); в Python это RANSAC/Theil–Sen из 2.2 по двум сторонам одновременно. [Статья](https://link.springer.com/article/10.1007/s10032-008-0071-7).
**Применимость.** Идейно ровно ваша задача (fit прямой к кромкам строк с максимизацией числа «прижатых» строк), но на уровне страницы. По блокам — 2.2 с той же целевой функцией: число строк в допуске.

### 2.5 Метрики оценки dewarping
- **Stamatopoulos, Gatos, Pratikakis (ICDAR 2009 / [IET IP 2012](https://digital-library.theiet.org/doi/10.1049/iet-ipr.2011.0208))**: мера DW ∈ [0, 100 %] — отклонение выпрямленных строк (аппроксимированных кубическими кривыми через SIFT-сопоставление точек) от горизонтальной прямой, интеграл по кривым; одна ручная разметка на изображение. Только строки, кромки не оцениваются.
- **UVDoc line straightness ([Verhoeven et al. 2023](https://arxiv.org/pdf/2302.02887), [код](https://github.com/tanguymagne/UVDoc))**: на синтетике к варпу применяют предсказанное unwarping и меряют среднее std координат горизонтальных и вертикальных линий 1 px. Нужна GT-функция варпа — у вас её нет, но сама мера «std вертикальной линии после преобразования» напрямую переносится: если взять кромку блока в A как «вертикальную линию» и отобразить её в B полем смещений (у вас в geometry_regression уже есть поле смещений по парам), std по x и есть «порча кромки коррекцией».
- **DocUNet MS-SSIM / LD ([Ma et al. 2018](https://arxiv.org/pdf/2207.11515)), AD ([Jiang et al. CVPR 2022](https://arxiv.org/abs/2203.16850))**: LD — среднее смещение плотного SIFT-flow между результатом и сканом-эталоном; AD — то же после глобального выравнивания и с весом по градиенту (чтобы не наказывать сдвиг целиком). Это *парные* меры двух версий страницы — прямой аналог вашего «до/после»: LD/AD между A и B, ограниченные полосой кромки блока, дадут «сколько сдвинулась кромка относительно строк». Но SIFT-flow на бинарных рендерах шумит; поле смещений по СК (которое у вас уже есть) надёжнее.
- **[Новая метрика PRL 2025](https://www.sciencedirect.com/science/article/abs/pii/S0167865525001801)** «Enhancing document dewarping evaluation» — доступ закрыт (403), по аннотации — согласованность с восприятием и скорость; для вашей задачи ничего нового не ожидается.
- **Kil, Seo, Koo, Cho 2017 «Robust dewarping using text-lines and line segments»** — используют прямолинейность отрезков (рамки, линейки) как часть оценки; идея «прямые должны остаться прямыми» — та же, что в вашем v14 для таблиц.

**Применимость.** Стандартной меры «margin straightness» в литературе по dewarping нет — везде строки или плотное поле. Собственная мера через кромки строк (2.2–2.3) ближе к Tesseract/page-frame традиции, чем к dewarping-бенчмаркам.

### 2.6 Парное сравнение двух версий одной страницы
Три способа, от простого к дорогому:
1. **Соответствие по строкам.** Один и тот же блок в A и B находится по surya/RLSA; строки сопоставляются по порядку (число строк совпадает, т.к. коррекция геометрическая) или по вертикальному перекрытию после сдвига. Дальше — разности метрик 2.2–2.3: Δtilt, ΔMAD, Δjitter, Δinliers. Требует, чтобы пороги были в единицах бумаги (мм или x-height), а не пикселях: масштаб у версий может слегка отличаться.
2. **Контуры «липкой ленты».** Полигоны блока A и B (1.10 или 1.9), выровненные по строкам; мера — направленное расстояние Хаусдорфа / среднее расстояние по левой и правой стороне контура (`shapely`, `cv2.matchShapes` не подходит — он инвариантен к аффинным искажениям). Даёт «где именно», но чувствителен к тому, как контур обходит висячие строки в каждой версии.
3. **Поле смещений (LD/AD-подход).** Уже есть у вас: сдвиг СК A→B; для СК на кромке (первое/последнее слово строки) смотрят компоненту сдвига по x относительно средней по строке: если коррекция сдвинула начало строки не так, как её середину — кромка поехала. Это ровно «std вертикальной линии» из UVDoc без синтетики.

## Рекомендации

### Сегментация блоков («липкая лента» по бинарной маске)
1. **Морфология в единицах pitch (1.1 + 1.10), основной вариант.** Оценить pitch и высоту строки (по СК/Docstrum-гистограмме или из surya). Шаги: (а) выровнять по общему скосу (проекции), (б) горизонтальное закрытие ядром (1 × 1.5·h_line) — слова слипаются в строки, межколонник (≥ 2–3 x-height) остаётся; (в) вертикальное закрытие ядром (k·pitch × 1) с **k = 3**: полости высотой ≤ 3 pitch заполняются, ямы больше остаются — блок разваливается на два по подзаголовку; (г) закрытие ядром (1 pitch × 1.5 em) залипляет абзацные отступы и короткие последние строки; (д) `findContours`. Опционально `MORPH_OPEN` (1 pitch × 1 em) — снять одиночные «усы». Параметры: k (глубина ямы), ширина ядра (г) = максимальный отступ, который считаем «не кромкой».
2. **Alpha-shape по углам bbox строк/слов (1.9), чистовой контур на наклонных блоках.** Точки — только внутри блока из п. 1; `alphashape` с alpha = 1/r, **r = 1.5·pitch**: диск не входит в щели уже 3 pitch и не берёт отступ в 1 строку, но проваливается в дыру ≥ 3 pitch. Изотропно, скос не мешает. На сотнях точек быстро.
3. **1D-огибающая по строкам (для метрики, не для картинки).** Последовательности x_left[i], x_right[i] по строкам блока; 1D морфологическое закрытие по индексу строки окном 2–3 (`scipy.ndimage.grey_closing`, size=3) залипляет отступы; разрыв в последовательности baseline > 3 pitch рвёт блок. Это та же «липкая лента», но с параметрами буквально «в строках», и именно она подаётся в метрику.

### Мера ухудшения кромки (парная)
1. **Робастная прямая + два разброса (2.2 + 2.3).** По каждой кромке блока (левая по всем строкам, правая — только по «полным» строкам justified-блока): Siegel/Theil–Sen прямая → tilt (°); MAD остатков (в долях x-height) → «ломаность»; median|Δx_i| → «рваность». Вердикт «коррекция испортила кромку»: Δtilt > ~0.3° **или** ΔMAD > ~0.25·x-height **или** Δjitter > ~0.25·x-height — при том, что мера прямолинейности строк (уже есть) не ухудшилась. Пороги — калибровать по распределению на паке, как по CLAUDE.md; ориентир Tesseract: res/32 ≈ 0.8 мм для «выровненной» кромки.
2. **Доля строк в допуске (page-frame стиль, 2.4).** inliers_A vs inliers_B при допуске res/32 вокруг робастной прямой — самая интерпретируемая цифра («было 38/40 строк на кромке, стало 21/40»).
3. **Std кромки по полю смещений (UVDoc-стиль, 2.5/2.6-3).** Для крайних СК каждой строки: смещение по x минус медианное смещение строки; std по блоку. Использует уже готовый механизм geometry_regression и не зависит от того, как построен контур.

Сегментацию для отчётов/оверлеев брать п. 1 (морфология), для метрики — п. 3 (1D огибающая) + меры 1–2; п. 3 меры — как независимую проверку.
